Object storage from scratch

Object storage is the layer that will hold almost every byte of the lake: tick files, Iceberg tables, loan-tape PDFs, model artefacts and backups. It is familiar as Amazon S3, where AWS runs it for you. On-prem, the team has to pick a product, size disks and failure domains, and own its failure modes, so this section builds the model from the API down to the disks.

The four nouns: bucket, key, object, metadata

Object storage is a storage system that keeps whole blobs of bytes, each addressed by a name, behind an HTTP API. Four nouns describe it.

  • A bucket is a named container. Most settings live at bucket level: access policy, versioning, lifecycle rules, replication and object lock. Example: lake-bronze.
  • A key is the full name of one object inside a bucket. On AWS it can be up to 1,024 bytes. Example: ticks/nse/dt=2026-10-13/symbol=RELIANCE/part-00001.parquet.
  • An object is the stored bytes for one key plus its metadata. On AWS a single object can be up to 48.8 TiB (as of Oct 2026).
  • Metadata is a set of name-value pairs stored with the object. System metadata includes size, last-modified time, content type and the ETag, an identifier of the content (for a simple single-part upload it is usually the MD5 hash of the bytes). User metadata is whatever you attach, for example x-amz-meta-source=nse-bhavcopy.

The namespace is a flat namespace: there are no directories. The slash in ticks/nse/dt=2026-10-13/ is an ordinary character in the key. A prefix is any leading part of a key, such as ticks/nse/. When you ask the store to list keys under a prefix and pass a delimiter (usually /), it groups keys by the next slash and returns "common prefixes". Consoles draw those as folders, which is why S3 feels like a filesystem until you try to rename one.

Objects are immutable: once written, the bytes of an object never change in place. To change one byte of yesterday's RELIANCE tick file you write a whole new object, either under the same key (which replaces the old one) or under a new key. Almost every design choice in the rest of this group follows from that one property.

The verbs: PUT, GET, LIST, DELETE, multipart and range reads

The S3 API has a few dozen operations, and a data lake leans on about seven of them.

OperationWhat it doesWhat matters in a lake
PUTWrites a whole object. Replaces any object already at that key.A reader never sees half a file: the PUT completes or it does not. Two writers that PUT the same key race, and the last one wins silently.
GETReads an object. With a Range header it reads only a byte range.Query engines rarely read whole Parquet files. They issue many small range GETs.
HEADReturns metadata only (size, ETag, last-modified).Engines call it to learn a file's size before reading its footer, unless table metadata already holds the size.
LIST (ListObjectsV2)Returns keys under a prefix in sorted order, up to 1,000 per page, with a continuation token for the next page.Pages are sequential round trips. Listing 10 million keys means about 10,000 calls. Keep LIST out of query planning.
DELETE / DeleteObjectsRemoves one object, or up to 1,000 keys per batch call. With versioning on, it adds a delete marker instead.Snapshot expiry and orphan cleanup are mostly batch deletes.

Multipart uploadCreate, upload parts (in parallel), then Complete or Abort.Needed for large files. Parts of an unfinished upload keep using space until someone aborts it.

A multipart upload splits one large object into parts that upload in parallel and are stitched together by a final Complete call. AWS limits (as of Oct 2026): up to 10,000 parts, each part 5 MiB to 5 GiB (the last part can be smaller), and AWS suggests considering multipart once an object reaches 100 MB. Iceberg's own S3 client (S3FileIO) uploads parts progressively as each part fills, with a default part size of 32 MB. On-prem stores implement the same calls, though limits can differ, so read your product's docs.

A range GET is a GET with a Range: bytes=start-end header. It is how columnar engines read. Parquet is the columnar file format of the lake. A Parquet file is split into row groups (horizontal slices of rows), and each row group holds one column chunk per column. The footer at the end of the file records where every column chunk starts plus min and max statistics per chunk. A query such as average last traded price for INFY on one day reads the footer with one range GET at the end of the file, skips row groups whose symbol statistics exclude INFY, then range-GETs only the price and symbol column chunks of the remaining row groups. Two columns out of forty is a small fraction of the bytes, but the request count stays roughly the same per file, which is why the number of files matters as much as their size.

A conditional write is a PUT that succeeds only if a condition on the current object holds. AWS added If-None-Match (write only if the key does not exist, August 2024) and If-Match (write only if the ETag still matches, a compare-and-swap, November 2024). These let a writer build put-if-absent or compare-and-swap logic directly on the store. On-prem support varies by product and version, so test it before any design depends on it.

Consistency: what strong read-after-write buys you

A consistency model says what a reader is guaranteed to see after a write. Under strong read-after-write consistency, once a PUT (or overwrite, or DELETE) returns success, every later GET and LIST from any client reflects it. Under eventual consistency, other clients may see the old state for a while.

AWS S3 has been strongly consistent for all requests since December 2020. Before that, a Spark job could LIST a prefix right after another job wrote to it and miss new files, and the Hadoop world built workarounds such as S3Guard, which tracked listings in a DynamoDB table. Old blog posts still describe those workarounds, so date-check anything you read.

On-prem, the answer depends on the product and the topology:

  • Ceph's object gateway (RGW) sits on RADOS, Ceph's strongly consistent object layer, so a single-site cluster gives read-after-write. Ceph multisite replicates between zones in the background, and its sync status reports shards that are "behind", so a reader at the second site can see older data.
  • Garage exposes the trade-off as a setting: consistency_mode defaults to consistent, while degraded and dangerous lower quorums and give up read-after-write consistency.
  • For any product, practitioners verify it under load: one client PUTs, another immediately GETs and LISTs, in a loop, while a node is being restarted.

Strong consistency is a per-key guarantee. A Spark job that writes 300 files for one partition cannot make all 300 appear at the same instant, and a reader that lists the prefix halfway through sees some of them. Multi-file atomicity has to come from a layer above the store, which is the subject of the next subsection.

No rename, no append: why table formats and catalogs exist

A Hive-style table is the older way to put a table on files: the table is a directory, each partition is a subdirectory such as dt=2026-10-13/, and the table's contents are whatever files are in those directories when a reader lists them. Writers commit by writing into a temporary directory and then renaming it into place.

On HDFS that works, because a rename is one metadata operation on a single server and is atomic. On object storage a "directory rename" is a COPY plus DELETE for every object under the prefix. The Hadoop S3A documentation states that directory renames take time proportional to the number and size of files and can fail partway through, so a commit protocol cannot rely on them. Hadoop added special "S3A committers" to work around it.

There is also no append on general-purpose S3 buckets. A stream of ticks cannot grow one file through the day; each micro-batch becomes a new object. That is where the small-file problem comes from.

A table format solves both problems with metadata. Apache Iceberg is the table formon-prem is considering. Its layers, from the bottom:

  • Data files: Parquet (or ORC or Avro), each written once under a unique name and never modified.
  • A manifest: an Avro file listing data files with per-file statistics (partition values, row counts, column min and max).
  • A manifest list: one per snapshot, listing the manifests that make up that version of the table.
  • A metadata file (metadata.json): the schema, partition spec, properties and the list of snapshots. A snapshot is the complete state of the table at one commit.

A catalog is the service that maps a table name such as markets.ticks_nse to the location of its current metadata file, and that swaps the pointer atomically on commit. A commit therefore writes only new objects (immutability is fine with that) and finishes with one atomic compare-and-swap of a pointer. Readers ask the catalog for the pointer, read the metadata tree, and get an exact file list without any LIST call.

Concurrent writers use optimistic concurrency: each writer prepares its commit assuming nobody else committed, and the catalog rejects the swap if the table moved underneath it. In the Iceberg REST catalog spec, a commit carries requirements such as assert-ref-snapshot-id, and a failed requirement returns HTTP 409, after which the client may retry. Iceberg's Java default is four retries (commit.retry.num-retries).

Object, block, file and HDFS

Block storage presents raw fixed-size blocks as a disk device: AWS EBS, a SAN volume, or Ceph RBD. Usually one host mounts it, and a filesystem or database sits on top. File storage is a shared filesystem with directories, rename, append and locks that many hosts mount at once: AWS EFS, an NFS server, CephFS. HDFS (Hadoop Distributed File System) is the Hadoop-era distributed filesystem: a NameNode holds the whole directory tree in memory, and DataNodes store files as large blocks (128 MB by default) with three replicas by default.

The industry moved lakes from HDFS to object storage for three reasons. HDFS ties compute to storage, because DataNodes run on the same hosts as the jobs. The NameNode's memory caps the number of files. And object storage plus a table format lets storage and compute scale separately. The Lakehouse paper (CIDR 2021) is the standard argument for building warehouse features on open formats over low-cost object storage.

The S3 API as the de facto standard

The S3 API is the HTTP interface AWS defined for S3, and every engine on a typical shortlist speaks it: Spark (through Hadoop S3A or Iceberg S3FileIO), Trino, StarRocks, Doris, ClickHouse, DuckDB and PyIceberg. That is why an on-prem lake is built on an S3-compatible store: the engines need no special connectors, and a later move between stores is a data copy.

Two details trip up first-time on-prem builds.

  • Signature Version 4 (SigV4) is how every request is authenticated: the client signs the request, including a timestamp, with a key derived from its secret access key, and the server recomputes the signature. Amazon S3 rejects a request whose timestamp is more than 15 minutes away from its own clock (error RequestTimeTooSkewed); AWS's general SigV4 guidance for most other services is tighter, at five minutes. S3-compatible stores generally apply a window similar to S3's.
  • Path-style addressing puts the bucket in the URL path (https://s3.lake.internal/lake-bronze/key). Virtual-hosted-style addressing puts it in the hostname (https://lake-bronze.s3.lake.internal/key), which needs wildcard DNS and a wildcard TLS certificate. On-prem teams usually choose path-style and set it in every client: s3.path-style-access in Iceberg and Trino, fs.s3a.path.style.access in Hadoop.

"S3-compatible" is a claim about a subset. The full API is large, and stores differ on conditional writes, object lock, STS (temporary credentials), server-side encryption (SSE) modes, lifecycle actions and bucket notifications. The habit that saves months: run each engine's own read and write path against the candidate store in the POC (proof of concept), because Java, C++ and Python S3 clients exercise different corners of the API.

Field notes
  • A common day-one failure: an engine defaults to virtual-hosted style, there is no wildcard DNS, and every call fails with a DNS or "bucket not found" error. Set path-style everywhere.
  • Internal TLS needs the internal CA in each Java engine's truststore. "PKIX path building failed" in a Trino or Spark log means exactly this.
  • Many stores let the admin pick any region name, but the client must sign with the region string the server expects, because the region is part of what SigV4 signs. A mismatch shows up as a signature error, which sends people chasing credentials.
  • A load balancer in front of the gateways with a short idle timeout cuts long part uploads and slow range reads. Set its timeouts longer than your slowest part upload.
  • Number to remember: LIST returns at most 1,000 keys per page. Any design that lists millions of keys per query is already broken.

Senior lens

The S3 API is the exit door that makes "no vendor lock-in" real: if the engines and the catalog only speak S3 and Iceberg REST, switching stores later is a bulk copy plus a pointer update, so the store decision is reversible at a known cost. The irreversible part is operational: who is paged at 2 a.m. when a Ceph placement group (its unit of data placement, covered below) is stuck or a filer database is corrupt. A senior engineer prices the product by team skill and support, compares two or three candidates in a POC that includes failure drills, and keeps the store's feature use to the common subset (multipart, range GET, versioning, lifecycle, object lock) so the exit door stays open. MinIO's path from open source to archived in about a year is the case study for checking a project's governance and funding as well as its features.

Inside a self-hosted object store

Every self-hosted object store has three jobs, whatever the product calls them.

  • The gateway speaks the S3 API: it terminates TLS, checks the SigV4 signature, applies bucket policies and routes the request. Gateways are usually stateless, so you run several behind a load balancer.
  • The metadata store answers "which bytes belong to this key, which versions exist, what are its tags and locks". The per-bucket part of it is the bucket index, which is what LIST reads.
  • The data nodes hold the bytes on disks, either as full replicas or as erasure-coded chunks, and run background repair and checksums.

CRUSH is Ceph's placement algorithm: given an object name and the cluster map, every client and OSD computes the same set of disks for that object, so no central lookup table sits in the data path.

Where each part limits a lake:

  • Gateway CPU is spent on TLS, signature checks and, in some designs, erasure encoding. Large sequential reads are cheap per byte; thousands of tiny requests are expensive per byte.
  • The metadata store limits LIST speed and small-object PUT rate. Ceph's docs advise no more than 100,000 entries per bucket-index shard; Ceph reshards automatically above that (dynamic resharding is on by default), and writes to that bucket can pause briefly while it happens.
  • Disks limit throughput for large objects (bandwidth) and for small objects (IOPS). An HDD that streams a 512 MB Parquet file well will struggle with thousands of 100 KB reads.
Field notes
  • Ceph's hardware guide says RGW index and log pools belong on enterprise SSDs even when bulk data sits on HDDs, and HDD OSDs gain from moving their write-ahead log and database (BlueStore WAL and DB) to a shared SSD. The usual on-prem pattern is NVMe for metadata, HDD for bulk.
  • One bucket holding tens of millions of objects is a known Ceph pain point: listing slows and resharding events appear in logs. Plan bucket count and expected object count together.
  • In SeaweedFS the filer store is the metadata store. Back it up and monitor it like a production database, because losing it means losing the names of every file.
  • Gateways scale horizontally; metadata usually does not scale as easily. When LIST or small-PUT latency rises while disk utilisation is low, look at the metadata tier first.
  • SeaweedFS packs small files into large append-only volume files (its design follows Facebook's Haystack paper), so it handles millions of small objects better than designs that create one or more disk files per object.

Durability: replication and erasure coding

Durability is the probability that stored data is never lost. Availability is the probability that you can read or write it right now. A cluster can be durable but unavailable (data safe, too many nodes down to serve it). Two methods protect data.

Replication stores full copies on different disks or hosts. Three copies (a replication factor of 3) survive two failures and cost 3x raw capacity. Reads can go to any copy, and rebuilding a lost copy reads one surviving copy.

Erasure coding (EC) splits data into k data chunks and computes m parity chunks, usually with Reed-Solomon codes. Any k of the k+m chunks rebuild the data. The arithmetic every operator carries:

  • Raw overhead is (k+m)/k. A 4+2 layout costs 1.5x; 8+3 costs 1.375x; 10+4 costs 1.4x.
  • It survives m lost chunks, as long as each chunk sits in a different failure domain.
  • Rebuilding one lost chunk reads k chunks from k other places. In 8+3 that is 8x the lost data crossing the network, against 1x for replication. Rebuilds are slower and noisier.
  • A write touches k+m disks and a read touches at least k, so the slowest of those disks sets the latency.

Failure domains are the things that fail together: a disk, a host, a rack, a power feed, a room, a site. If the failure domain is "host", a 4+2 layout needs at least six hosts so each chunk sits on a different one, and a seventh so the cluster can rebuild a dead host's chunks somewhere legal. With exactly six hosts, losing one leaves the pool degraded until the host returns. Ceph's docs recommend setting an EC pool's min_size (the minimum number of chunks a placement group needs before it serves I/O) to k+1 or more, to prevent loss of writes and data. For a 4+2 pool that means any placement group missing two chunks stops serving reads and writes until one comes back.

The small-object penalty: EC cuts every object into k+m chunks. A 64 KB object in 8+3 becomes eleven 8 KB chunks, eleven disk writes and eleven entries to track, with padding up to the stripe unit (4 KB by default in Ceph). Small objects are cheaper to replicate. SeaweedFS sidesteps this by erasure-coding whole sealed volumes in 1 GB chunks, so small files never pay per-object EC cost. A common Ceph pattern is a replicated NVMe pool for indexes and small objects, and an EC HDD pool for large data files. Parquet files of 128 MB to 1 GB suit EC well.

Bit rot is silent corruption: a disk returns wrong bytes without reporting an error. Stores defend with checksums on every chunk and scrubbing, a background job that reads stored data and compares copies or checksums. Ceph's defaults: a light scrub of each placement group between daily and weekly (osd_scrub_min_interval 1 day, osd_scrub_max_interval 7 days) and a deep scrub, which reads all data and verifies checksums, weekly (osd_deep_scrub_interval 7 days). Deep scrubs cost disk bandwidth, so operators confine them to quiet hours, which means after the evening reconciliation and outside MCX trading hours.

A worked sizing example

Assume 40 TB of logical data today and a plan for 80 TB within three years (my assumption, for illustration). With EC 4+2: 80 x 1.5 = 120 TB raw. Clusters must not run full, because a host failure needs free space on the survivors for the rebuild; Ceph warns at 85% full by default (mon_osd_nearfull_ratio 0.85), and a common planning ceiling is about 70% (a rule of thumb). That gives 120 / 0.7, about 171 TB raw. With 3x replication the same data needs 240 / 0.7, about 343 TB raw. At this scale the host count is set by failure domains (seven hosts for 4+2) and by throughput, and capacity per host comes out small. In my view that makes an all-flash design worth pricing against HDD before assuming HDD is cheaper per useful IOPS.

Incident

Symptom. Median query time on lake tables is unchanged, but p99 latency (the slowest 1% of requests, the tail latency) for range GETs climbs from tens of milliseconds to seconds. Dashboards that run many small queries feel sluggish; averages look fine. Diagnosis. In an EC pool every read waits for k chunks from k disks, so one degrading disk sits on the read path of a large share of objects. Per-disk latency shows one outlier (in Ceph, ceph osd perf lists commit and apply latency per OSD), and its SMART counters (the drive's self-reported health statistics) show growing reallocated or pending sectors. The disk has not failed, so nothing marked it out. Fix. Mark that OSD out so data rebalances away from it, throttle backfill so the rebalance does not hurt market-hours traffic, then replace the drive. Lesson. Alert on per-disk latency outliers and tail percentiles; a cluster average hides one slow disk among a hundred. A slow disk hurts EC more than a dead one, because a dead disk is excluded and a slow one is waited for.

Incident

Symptom. An ingestion task fails intermittently with HTTP 403 RequestTimeTooSkewed or signature errors, only when its pod lands on one particular compute node. If a host that runs a Ceph monitor drifts the same way, Ceph raises a MON_CLOCK_SKEW health warning. Diagnosis. After a reboot, the time daemon on that node did not start (or cannot reach its server), and the node's clock drifted. SigV4 signatures carry a timestamp, and S3 rejects requests more than 15 minutes off its clock (S3-compatible stores apply a similar window). Ceph monitors warn at a far smaller drift: mon_clock_drift_allowed defaults to 0.05 seconds. Fix. Run chrony or ntpd on every host from configuration management, point them at internal time servers with several upstream sources, and alert on clock offset. Lesson. Time sync is part of the storage stack. Check the client's clock before debugging credentials when signatures fail.

Common mistake

Choosing an erasure-coding width for its storage saving alone. A 10+4 layout looks cheap at 1.4x, but with "host" as the failure domain it needs at least 14 hosts, rebuilds read 10x the lost data, and every small object turns into 14 tiny writes. For a cluster of six to ten hosts, 4+2 for large data files plus a replicated pool for indexes and small objects is a common and defensible choice. A related mistake is treating key prefixes as directories: "renaming the 2025 folder" on object storage copies every byte under it.

Say this

"Object storage gives you immutable objects under keys in a flat namespace, behind the S3 API. Two properties shape the whole lake: there is no rename and no append, and consistency is per key. On product choice, I should correct something from my an earlier design: MinIO's community edition was archived in April 2026, so I would compare Ceph RGW and SeaweedFS instead. I have not run either in production, so I would decide with a POC: run warp and the real engines against each, measure p99 range-GET latency and small-PUT rate, and, most important, pull a disk and a whole node mid-test and watch rebuild time and query tail latency. A suitable object-storage setup for the lake

Choosing the store is half the decision. The other half is the layout on top of it: which buckets and prefixes, who can touch what, how long objects live, and how big the files are. These choices decide whether a query over three years of NIFTY options ticks takes seconds or minutes, and whether the team can hand an auditor the exact trade file it received in 2026. At under 40 TB most of this is cheap to get right on day one and expensive to change later.

A zone is a stage of the lake with its own rules for format, writers, readers and retention. Scratch and logs get their own buckets because their life is different: high churn, short expiry, no value in DR. Some engines stage intermediate data on object storage, for example Trino's fault-tolerant execution writes exchange data to a configured exchange location, and that belongs in scratch.

Versioning, object lock and lifecycle

Versioning keeps every version of an object. An overwrite creates a new current version and keeps the old one as a noncurrent version; a DELETE adds a delete marker and keeps the data. It protects against mistakes, and it costs storage until noncurrent versions are expired.

Object lock makes object versions undeletable for a retention period, which gives WORM storage (write once, read many). It requires versioning. In governance mode, users with a special permission can override the lock; in compliance mode, nobody can shorten or remove it, including administrators. A legal hold locks an object with no end date until it is released. Ceph RGW implements the S3 object lock API, and recent Ceph releases allow enabling it on an existing versioned bucket (older ones required it at bucket creation). In a multisite setup, check that the lock configuration and retention are in force on the secondary site before relying on them there.

A lifecycle rule is a bucket-level policy the store runs in the background: expire objects after N days, expire noncurrent versions after N days, abort multipart uploads left incomplete, or transition objects to another storage class. Tiering is that last action: moving data between pools, for example from NVMe to HDD. In Ceph a transition moves the object's data to the pool of another storage class while its key stays the same, so readers, Iceberg metadata included, keep working.

Why no object lock on the Iceberg warehouses: Iceberg needs to delete files. Compaction rewrites small files into large ones, snapshot expiry deletes files no snapshot references, orphan cleanup deletes failed-write leftovers. A locked warehouse turns every one of those into an error and storage grows without limit. Keep the legally immutable copy as source files in lake-records. For "show me the book as of 31 March", use Iceberg tags (named snapshots with their own retention), which keep a table version readable without locking objects.

SEBI and other regulators set retention periods by record type. The numbers come from the compliance team and go into the lock configuration; the platform's job is to make them enforceable and auditable.

Incident

Symptom. Queries on the bronze bhavcopy table for dates before July fail with NoSuchKey or file-not-found errors; recent dates work. Diagnosis. Someone added a lifecycle rule "expire objects under bronze/ older than 90 days", meant for raw CSV staging. The Iceberg table's current snapshot still referenced Parquet files written more than 90 days ago, because old partitions are never rewritten. The store deleted live data that only Iceberg metadata knew was live. A second common variant: remove_orphan_files run with a one-hour threshold while a three-hour backfill was still writing, so the backfill's not-yet-committed files looked orphaned and were deleted, and its commit then pointed at missing files. Iceberg's docs warn about exactly this and default to 3 days. Fix. Remove the rule. Restore the deleted objects from noncurrent versions if versioning was on, or from the DR copy. If neither exists, roll the table back to a snapshot whose files all exist and re-ingest from landing. Lesson. Only Iceberg's own maintenance (snapshot expiry, orphan cleanup with a threshold longer than the longest write) may delete from a warehouse prefix. Retention by age is a table operation: delete the rows, then expire snapshots.

Incident

Symptom. The store's used capacity is about twice the sum of table sizes reported by the catalog, and growing faster than ingest. Diagnosis. Versioning is on for the warehouse buckets with no noncurrent-version rule. Nightly compaction rewrites recent partitions; snapshot expiry then deletes the replaced files, but each DELETE only adds a delete marker, and every compacted file lives on as a noncurrent version. A table compacted weekly can hold several full copies of its history. Incomplete multipart uploads from killed jobs add more hidden bytes. Fix. Add NoncurrentVersionExpiration and AbortIncompleteMultipartUpload rules, wait for the lifecycle run, and track "versioned bytes minus current bytes" as a capacity metric. Lesson. Versioning without a noncurrent-version rule is a storage leak. Decide the undo window on purpose and encode it.

Disaster recovery and site replication

RPO (recovery point objective) is how much recent data you can afford to lose; RTO (recovery time objective) is how long you can be down. Site replication copies objects from one cluster to another, usually asynchronously, so the RPO equals the replication lag at the moment of disaster.

  • Ceph RGW multisite: a realm holds zonegroups, a zonegroup holds zones, each zone is its own Ceph cluster. Zones are active-active by default (a secondary can be made read-only), and metadata operations such as creating users go through the master zone.
  • SeaweedFS: filer.sync replays each filer's change log into another cluster, one-way or both ways, and keeps checkpoints so it can resume.
  • RustFS lists bucket and site replication as available.

Iceberg adds three traps that plain bucket replication does not handle.

  1. The catalog is state too. If the catalog's database (Postgres for Polaris or Lakekeeper, for example) is not backed up and restored in step with the buckets, the DR site has data with no table pointers, or pointers to metadata that has not arrived yet.
  2. Replication order is not commit order. A metadata.json can arrive at the DR site before the data files it references. A reader there sees a table that fails on missing files. At failover, register each table at the newest snapshot whose files all exist at the DR site.
  3. Iceberg metadata stores absolute paths, bucket and endpoint included. If the DR site uses different bucket names or a different endpoint, every path breaks. Keep names identical across sites, or plan to use Iceberg's rewrite-table-path action. Relative paths are part of the not-yet-adopted v4 spec work, and Iceberg 1.12.0 (Sep 2026) contains the first v4 code (as of Oct 2026).
Field notes
  • Run the DR drill with queries: fail over, point a Trino or StarRocks instance at the DR catalog, and run the gold queries that matter (yesterday's NAV, today's P&L). Checking that replication is "green" proves only that bytes moved.
  • Scratch and logs need no DR copy. Excluding them saves link bandwidth for what matters.
  • Replication lag is a metric to alert on. A replication backlog after month-end compaction (which rewrites a lot of data at once) is a common surprise.
  • The landing zone is the cheapest DR insurance: if raw files survive, everything downstream can be rebuilt, slowly.

The object store knows buckets and keys; it knows nothing about tables, columns or rows. If an engine holds a key that can read lake-gold/*, the store cannot stop it reading the investor table. Two consequences follow. Table, column and row rules (mask PAN numbers, restrict investor records to the fund operations team) must be enforced in the catalog and the engines. Credential vending is the catalog's answer. When an engine loads a table from an Iceberg REST catalog, it can send the header X-Iceberg-Access-Delegation with vended-credentials (the catalog returns short-lived credentials scoped to that table's location) or remote-signing (the catalog signs each request). The engine then holds no standing access to the bucket. On-prem this needs both halves: a catalog that supports vending against S3-compatible stores, and a store that can mint scoped temporary credentials through STS. Test both in the POC, because this is where "S3-compatible" claims often fall short.

For internal AI agents, the rule I would argue for: agents never get object-store credentials. They query through an engine or catalog that enforces table, column and row policies and logs every query under the agent's identity.

Performance: file sizes, small files and compaction

The single biggest performance lever in a lake is file size. Working ranges practitioners use:

  • Parquet data files of roughly 128 MB to 1 GB. Iceberg's Java default target is 512 MB (write.target-file-size-bytes), with 128 MB row groups and zstd compression by default.
  • The Parquet project recommends large row groups of 512 MB to 1 GB, a recommendation written for HDFS block reads. Engines that prune by row-group statistics often do better with somewhat smaller row groups, which is why Iceberg's default is 128 MB.
  • Small tables do not need large files. A daily NAV table of a few megabytes is fine as one file per day.

The small-file problem is the cost of having many files far below the target. It hurts in four ways:

  • Request overhead: each file costs at least a footer read and a few range GETs, each with its own latency, regardless of how few bytes it holds.
  • Planning time: every file is one manifest entry with statistics, so the planner reads and filters more metadata.
  • Metadata growth: frequent commits create a new metadata file, manifest list and manifest each time.
  • Worse compression and weaker pruning: small files compress less well and their min/max ranges overlap.

The 3 ms figure is an assumption for illustration; engines parallelise these requests, which shrinks the wall-clock time and moves the cost onto the store's gateways and metadata tier.

Compaction rewrites many small files into fewer large ones and commits the swap as a new snapshot. Two strategies: bin-packing just combines files up to the target size (cheap), while sort compaction also orders rows, for example by symbol and timestamp, so each file covers a narrow range of symbols and min/max statistics prune well (more CPU, much better reads). Who can run it, as of Oct 2026: Spark's rewrite_data_files procedure, Trino's optimize, StarRocks' compaction API (added in 4.0), and SeaweedFS table buckets do it server-side. Incident

Symptom. Two weeks after go-live, a query for one day of RELIANCE ticks takes 40 seconds and query planning alone takes most of it. The catalog's commit endpoint is slow and the metadata prefix holds thousands of files. Diagnosis. The feed handler commits to Iceberg every minute. The NSE normal session runs 09:15 to 15:30, which is 375 commits a day, and the table was partitioned by day and symbol, so each commit wrote one small file per active symbol: for a few hundred symbols that is tens of thousands of files a day of a few hundred KB each (illustrative). Every commit also left a metadata file, a manifest list and a manifest, and nothing expired snapshots. Fix. Partition by day only and sort by symbol inside files; buffer ticks and commit every 5 to 15 minutes, or keep the intraday hot path in the MPP engine's native tables and land to Iceberg in larger batches; schedule sort compaction after the close, then snapshot expiry and manifest rewrite; enable metadata cleanup after commit. Lesson. Commit frequency times partition count equals file count. Decide freshness per table on purpose; minute-level freshness on the lake is rarely worth what it costs.

Performance: the request path, rate limits and LIST

Engines get throughput from object storage through parallelism: many range GETs in flight across many files and connections. AWS's guidance is to spread requests over many connections and, for objects uploaded with multipart, to read in part-sized ranges aligned to part boundaries. Three settings govern it on the client side.

  • A connection pool is the set of HTTP connections a client keeps open to the store. Each client has a maximum (in Hadoop S3A it is fs.s3a.connection.maximum). Too small and threads queue for connections while the network idles; too large and the gateways drown in connections.
  • Read parallelism: how many range GETs each worker issues at once.
  • Retries with backoff. Iceberg S3FileIO defaults to 5 retries (s3.retry.num-retries); its docs suggest 32 for workloads that hit throttling, so the store has time to recover.

Rate limits differ by platform. AWS S3 supports at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per partitioned prefix and answers bursts beyond that with HTTP 503 "Slow Down". On-prem stores have no per-prefix figure. Their limits come from gateway CPU (TLS, signatures, encoding), the metadata tier (bucket-index shards in Ceph, the filer database in SeaweedFS) and disk IOPS. The symptom is the same: rising latency, then 503s or timeouts. The store's own metrics show which tier is saturated.

Avoiding LIST is the other half. A Hive-style table is discovered by listing directories, so query planning cost grows with partition count. Iceberg plans from manifests and never lists data prefixes, which is the main reason it scales on object storage.

Incident

Symptom. Every morning around 09:00 the whole lake slows: dashboards time out, ingestion PUTs retry, the gateways show high CPU and the bucket-index tier is saturated, while disks are mostly idle. Diagnosis. A legacy Hive-style table of ticks is partitioned by date and symbol: three years of trading days times a couple of thousand symbols is over a million partition prefixes (illustrative). The morning job runs partition discovery (an MSCK REPAIR TABLE-style scan or a crawler), and an analyst's query without a date filter makes the engine list every partition. At 1,000 keys per page, that is a very large number of sequential LIST calls hammering the metadata tier. Fix. Migrate the table to Iceberg (planning from manifests), partition by day only, and replace discovery scans with explicit commits. Until then, rate-limit the discovery job and run it off-hours. Lesson. On object storage, LIST is the expensive verb. A design that lists at query time puts every user on one shared bottleneck.

Performance: caching, network and hardware

A local cache keeps recently read object data on the compute node's memory or NVMe so repeat reads skip the network. For a lake on object storage it is the difference between a dashboard that runs at memory speed and one that re-reads the same files from HDD every refresh.

Alluxio is a distributed caching layer that sits between engines and storage. A shared cache tier helps when several engines read the same hot data; it is also one more stateful system to run, and since Trino 482 dropped its Alluxio file system support, check how each engine would reach a shared tier before planning one. A reasonable default (my judgement): start with each engine's local NVMe cache and add a shared tier only if measurements show repeated cross-engine reads of the same data.

Network arithmetic

Line rate converts to bytes per second by dividing by 8: 25 GbE is about 3.1 GB/s per port, 100 GbE about 12.5 GB/s. A node with one 25 GbE port can scan at most about 3 GB/s from remote storage, so scanning 1 TB takes at least about five and a half minutes on one node, and about 80 seconds across four nodes if the storage side can deliver 12 GB/s. The storage side has its own ceiling: the sum of what its disks deliver under the actual access pattern (large sequential reads of 512 MB Parquet files, or scattered small range GETs) and its gateways' network ports. The network team's leaf-spine fabric needs enough capacity between the compute racks and the storage racks for both query traffic and rebuild traffic at the same time.

Hardware shape

  • NVMe for anything metadata: Ceph's RGW index and log pools and BlueStore WAL/DB, SeaweedFS's filer database, Garage's LMDB store.
  • HDD or high-capacity flash for bulk data in an erasure-coded pool. Datasheets for 7,200 rpm enterprise HDDs list sustained transfer rates in the low hundreds of MB/s and random reads in the low hundreds of IOPS (rule of thumb from vendor datasheets), so HDD pools need many spindles and large files.
  • Match EC to object size: large Parquet files on EC, small objects and indexes on replicated NVMe.
  • NVMe on the compute nodes for engine caches and spill.

Senior lens

Most lake performance problems are layout problems (file size, partitioning, LIST) and metadata problems (bucket index, filer database, catalog), and very few are raw disk speed. So a senior engineer spends the hardware budget in a particular order: enough failure domains for the chosen EC layout, NVMe for every metadata tier, NVMe caches on compute, then network headroom for rebuilds during market hours, and only then more bulk capacity. The same engineer treats maintenance as a platform product: compaction, snapshot expiry and orphan cleanup run as owned, monitored Prefect flows with SLOs, because a lake with no owner for maintenance degrades a little every day until someone notices a 40-second query. Finally, every engine identity is attributable in the store's logs, so when the lake is slow the first question ("which engine, which job") has an answer in minutes.

Field notes
  • Cache hit ratio is the first metric to read when the same dashboard is fast at 10:00 and slow at 10:05: a full cache disk or an eviction storm after a large backfill query looks like a storage problem but is a cache-sizing problem.
  • After a node failure, rebuild traffic can take most of the storage network. Throttle recovery during market hours and let it run fast overnight.
  • Backfills (reloading three years of ticks) are the workload that finds every limit at once: file counts, gateway CPU, catalog commits. Run them in a dedicated window, in large batches.
  • Watch request counts per second as well as bytes per second. A store at 30% bandwidth can be saturated on requests.

Benchmarking before you buy

Benchmarks answer one question: does this store, on this hardware, meet the workload with a disk and a node missing? Three tools cover the layers.

  • warp is an S3 load generator from MinIO (AGPLv3, still maintained in its own repository as of Oct 2026). It runs get, put, mixed, list, delete, multipart and versioned workloads against any S3 endpoint, and has added Iceberg catalog read and commit benchmarks (its README names MinIO AIStor Tables and Apache Polaris as the supported catalogs).
  • fio measures raw disk performance before any storage software is installed, which tells you what each drive can do on its own.
  • weed benchmark is SeaweedFS's built-in small-file write and read benchmark.
# Raw drives first, read-only, before installing the store
fio --name=hdd-seq --filename=/dev/sdX --rw=read --bs=1M --iodepth=32 \
    --ioengine=libaio --direct=1 --runtime=120 --time_based --readonly
fio --name=nvme-rand --filename=/dev/nvme0n1 --rw=randread --bs=4k --iodepth=64 \
    --numjobs=4 --ioengine=libaio --direct=1 --runtime=120 --time_based \
    --group_reporting --readonly

# Then the S3 layer (credentials omitted)

Common mistake

Copying a Hive habit and partitioning tick tables by symbol as well as date. It feels natural ("queries filter by symbol"), but it multiplies files by the number of symbols, creates thousands of tiny files per day, and makes every ingest commit touch hundreds of partitions. Partition by day (Iceberg's days(ts) hidden partitioning) and sort by symbol inside files; min/max statistics then prune symbols nearly as well, with a few large files per day. A second common mistake is benchmarking only a healthy cluster: the first real disk failure then becomes the first degraded-mode test, during market hours.

Say this

"I would set the lake up with a few buckets by zone and sensitivity: landing for files exactly as received, bronze, silver and gold as Iceberg warehouses, a separate WORM bucket for records we must retain, a restricted warehouse for investor data, and scratch and log buckets with short expiry. Each engine gets its own service account scoped to the prefixes it needs, and ideally the catalog vends short-lived credentials so engines hold no standing keys; AI agents query through the engine and hold no store credentials. On performance, the main lever is file layout: around 512 MB files, which is Iceberg's default, partition ticks by day and sort by symbol, and compact after the close, because a once-a-minute ingest otherwise creates tens of thousands of small files a day. Reads plan from Iceberg metadata with no LIST calls, and each engine gets a local NVMe cache. The traps I would guard against are lifecycle rules or orphan cleanup deleting files a live table still references, and versioning quietly doubling storage. I have not operated this on-prem; this is how I would design it and what I would monitor."
