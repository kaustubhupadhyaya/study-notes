Distributed databases from scratch

A distributed database spreads one logical database over several machines that cooperate across a network. Every engine on a typical shortlist (ClickHouse, Apache Doris, StarRocks) and the Trino query engine is a distributed system, so each topic rests on four ideas from this section: how data is split, how it is copied, how the machines agree, and what happens when one of them dies.

Why distribute at all

A node is one server, physical or virtual, running a database process. A cluster is a group of nodes that present themselves to users as one database. A distributed database is a database whose data and work are spread over the nodes of a cluster.

There are three reasons to distribute:

  1. Size. The data no longer fits on one machine's disks, or the working set no longer fits in its memory.
  2. Throughput. One machine cannot scan or compute fast enough. Splitting the work so that N machines each do a fraction of it is called scale-out (horizontal scaling). Buying a bigger single machine is called scale-up (vertical scaling).
  3. Availability. If the only machine dies, the database is down. Keeping copies of data and metadata on other machines lets service continue through a failure.

An MPP database (massively parallel processing database) is an analytical database that runs a single query on many nodes at once. Each node works on its own slice of the data, and the partial results are combined at the end. Redshift and Snowflake, a common managed warehouse, are MPP systems. So are ClickHouse, Doris and StarRocks. Trino is an MPP query engine with no storage of its own: it reads files that live somewhere else.

Assume the data is under about 40 TB. That is small by MPP standards: a single modern server can hold 40 TB of flash. So size alone does not force a cluster. Two other things do. The first is availability: with one box, one failed power supply means no P&L report in the morning. The second is concurrency: the overnight risk run, the morning PM dashboards and, later, the internal AI agents will all hit the same data at the same time. My view is that the honest order of reasons is availability and workload isolation first, scan speed second, and raw size a distant third.

A small piece of illustrative arithmetic shows why scale-out helps scan speed. Suppose a query must read 2 TB of compressed columns and each node can read its local flash at 4 GB/s (an assumed figure for the example; measure your own hardware). One node needs 2,000 GB ÷ 4 GB/s = 500 seconds. Six nodes, each reading one sixth, need about 83 seconds plus the time to combine results. That near-linear speed-up only happens when the data is spread evenly, which is the subject of the next subsection.

Field notes
  • The first question when a cluster is slow is "which resource is the bottleneck": disk reads, CPU, memory, network, or metadata. Each one has a different fix, and adding nodes only helps some of them.
  • Distribution adds failure modes a single box never has: partial failures, one slow node (a straggler) holding up every query, and network splits. A parallel query finishes when its slowest piece finishes.
  • In analytics, the unit of parallelism is a chunk of data (called a tablet, a part or a file split depending on the engine; the next subsection defines each). Evenly sized chunks keep every core busy. Uneven chunks leave most of the cluster idle while one node grinds.

Partitioning and sharding: how the data is split

Partitioning means splitting a table's rows into groups using a rule on one or more columns, called the partition key. Sharding is partitioning where the groups live on different nodes. One such group is a shard. Different engines use different words for the same ideas, so the table further down maps them.

There are three basic rules for assigning a row to a group:

  • Hash partitioning: compute a hash of the key and take it modulo the number of groups. Rows spread evenly when the key has many distinct values that appear with similar frequency. Hashing on instrument ID spreads INFY, RELIANCE and TCS rows across groups. It is good for even spread and for joins on that key. It is poor for range filters on the key, because neighbouring values land in different groups.
  • Range partitioning: each group holds a contiguous range of values, for example one month of trade_date. It is good for time filters and for data lifecycle (drop or archive an old month in one step). Its weakness is that all new writes go to the newest range, which becomes a hot spot: a single place that receives a disproportionate share of the load.
  • List partitioning: each group holds an explicit list of values, for example asset class EQ, FO, MCX or CREDIT. It suits a small, known set of categories.

StarRocks and Doris use a two-level design. First a table is partitioned, usually by time. Then each partition is split into buckets, usually by hash of a key. Each bucket of each partition is stored as a tablet, and the tablet is the unit that is stored, copied and moved between nodes. The two levels do different jobs. Partitions give partition pruning: the planner skips partitions that cannot match the WHERE clause, so a query for one week of NIFTY option ticks never opens other months. Buckets give spread: one day's data is cut into many tablets that sit on different nodes and are scanned in parallel. StarRocks (as of Oct 2026) offers expression partitioning (partitions created automatically during loading), range and list partitioning, and hash or random bucketing (random bucketing only for Duplicate Key tables; range-based bucketing was added in v4.1). Its docs recommend keeping tablets roughly between 1 GB and 10 GB, and since v2.5.7 it can choose the bucket count for you.

ClickHouse splits differently. On one server, a MergeTree table's PARTITION BY clause splits data into partitions, and every INSERT writes a new immutable part: a directory of compressed column files that background merges later combine into bigger parts. Across servers, sharding is explicit. You create a local table on every shard and a Distributed table on top. The Distributed table stores no data itself. It sends each inserted row to a shard chosen by a sharding_key, and it sends each SELECT to all shards and combines the answers. Adding a shard does not move existing data; the docs say you steer new data to the new shard by giving it a higher weight.

Trino stores nothing. It reads tables from a data lake: data files, usually in the columnar Parquet format, kept in object storage (an S3-style store that holds whole files, called objects, under keys). Trino lists a table's files, cuts them into splits (byte ranges of files), and hands splits to workers. With Apache Iceberg, an open table format that records which files make up each version of a table, the table carries a partition spec such as days(trade_ts) and bucket(16, instrument_id), which writers use to lay out files and readers use to prune them.

Skew, and why the bucket key matters

Data skew means some groups hold far more rows than others. Market data is naturally skewed. If NIFTY index options produce far more ticks than an illiquid single-stock option, then hashing ticks only on the underlying symbol puts all NIFTY option ticks for a day into one bucket. That tablet becomes many times larger than the rest, and the node that holds it does most of the work for every query that touches it. The fix is a bucket key with high cardinality and even frequency, such as the instrument token (each strike and expiry of an option is a separate instrument), or random bucketing for append-only fact tables where you do not need bucket-aligned joins.

The bucket key also decides how joins run. A shuffle moves rows over the network so that rows with the same join key meet on the same node. A broadcast join copies a small table (say, the 5,000-row instrument master) to every node so the big table never moves. A colocated join happens when two tables are bucketed the same way on the join key, so each node joins its local tablets with no network traffic. StarRocks and Doris support this through colocation groups (the colocate_with table property). A senior engineer chooses bucket keys with the most frequent large join in mind, for example trades and positions both bucketed on account_id.

Field notes
  • Before choosing a bucket key, run a frequency check: SELECT key, count(*) FROM t GROUP BY key ORDER BY 2 DESC LIMIT 20. If the top value holds a large share of the rows, it is a poor hash key on its own.
  • Tablet count multiplies quickly. Daily partitions × 64 buckets × 3 replicas × 5 years is 1,825 × 64 × 3 = 350,400 tablet replicas, each tracked in the memory of the frontend (FE), the process that holds the cluster's metadata (covered under consensus below). Small tables do not need daily partitions or many buckets.
  • Time partitioning plus an entity bucket key is the usual starting point for tick, trade and position tables: PARTITION BY trade_date (or month), buckets on instrument or account.
  • In ClickHouse the same mistake shows up as too many parts. Many tiny inserts create many tiny parts. As of Oct 2026 the MergeTree defaults delay inserts at 1,000 active parts in one partition (parts_to_delay_insert) and reject them at 3,000 (parts_to_throw_insert). Batch inserts into large blocks.
Incident

Symptom. A morning query over F&O ticks takes four minutes while similar queries on equities take ten seconds. One backend node sits at 100% CPU and the others are nearly idle. Diagnosis. The query profile shows one scan instance reading most of the rows. Listing tablet sizes for the table shows a handful of tablets many times larger than the rest. The table was bucketed on the underlying symbol, so every NIFTY option tick for a day landed in the same tablet. Fix. Create a new table bucketed on the instrument token, copy the data with INSERT INTO ... SELECT, and swap the table names in one atomic statement (both StarRocks and Doris have one). Lesson. A key that is natural for humans (the underlying) is often a bad hash key. Check frequency distribution before choosing, and recheck when trading patterns change, for example after a new weekly expiry product launches.

Incident

Symptom. Over a few months, DDL statements (schema changes such as CREATE and ALTER) get slow, query planning takes seconds, and the FE (the metadata process) shows long Java garbage-collection pauses. Diagnosis. Dozens of small reference and position tables were created with daily partitions and 32 buckets each, by copying one template. The cluster now tracks hundreds of thousands of tablets, most of them a few megabytes. Fix. Rebuild the small tables with monthly partitions or none, and let the engine choose bucket counts. Lesson. Size partition and bucket counts from data volume, and graph tablet counts as a cluster metric.

Common mistake

Partitioning on the column people filter by most, without checking its cardinality. Partitioning ticks by symbol creates thousands of partitions; hashing them by trade date puts a whole day in one bucket. The safe pattern is the reverse: partition by time (low cardinality, natural lifecycle), bucket by a high-cardinality entity key.

Replication: keeping copies

A replica is a copy of some data kept on another node. The replication factor (RF) is the number of copies. In a leader-follower scheme (also called primary-secondary) one copy accepts writes and the others follow it. In a multi-leader scheme any copy can accept writes and the copies exchange changes.

The timing of the copy matters. With synchronous replication the write is acknowledged only after the copies have it, which is safer and slower. With asynchronous replication the write is acknowledged first and copied afterwards, which is faster and leaves a window in which a copy is behind. That gap is replica lag. A write quorum is the number of copies that must confirm before the write counts as done.

How the shortlisted engines do it (as of Oct 2026):

  • StarRocks, shared-nothing mode. Each tablet has replicas on different backend nodes. The table property replication_num defaults to 3. The property write_quorum (since v2.5) defaults to MAJORITY, so a load succeeds when most replicas confirm; ONE and ALL are the alternatives, and the docs warn that a low quorum raises the risk of data becoming inaccessible or even lost. Each load also carries a label, a unique name that makes retrying the same load safe: a label that already succeeded is rejected.
  • Doris, coupled mode. The same tablet-replica model. The Doris planning guide says production uses 3 replicas. The replication_allocation property can place replicas on groups of backends tagged by location.
  • ClickHouse. Replication is set per table with the ReplicatedMergeTree engine family. The docs describe it as asynchronous and multi-master: you can insert into any replica and the others fetch the new part. By default an INSERT waits for one replica only, so a part can be lost if that server dies before others copy it. The insert_quorum setting makes the insert wait for more replicas. Only inserted data crosses the network; each replica runs its own merges. Reads never touch the coordination service.
  • Shared-data modes (StarRocks with compute nodes, Doris decoupled). The durable copy lives in object storage, which does its own replication or erasure coding (splitting each object into data and parity chunks; the capacity plan below works through it). Compute nodes hold only a cache, so there are no database-level replicas to repair. The architectures section covers this in depth.

Symptom. Two analysts run the same intraday P&L query a minute apart and get different totals. Nothing errors. Diagnosis. The query goes through a ClickHouse Distributed table, which picks one replica per shard. Consensus and quorum in plain words

Consensus is the problem of getting a group of nodes to agree on one value, or one ordered list of changes, even when some nodes fail or messages are delayed. A quorum is the minimum number of nodes that must agree before a decision counts. Most systems use a majority quorum: more than half, which for n nodes is floor(n/2) + 1.

Raft is a widely used consensus algorithm, published by Diego Ongaro and John Ousterhout in 2014. In plain words: one node is the leader. Every change goes to the leader, which appends it to its log and sends it to the followers. Once a majority have stored the change, it is committed and can be applied. If followers stop hearing from the leader, they hold an election; a candidate needs votes from a majority to become the new leader, and each election starts a new numbered term so old leaders can be recognised and ignored. The Raft site states the property operators rely on: a cluster of 5 servers keeps working with 2 failed, and if more fail it stops making progress but never returns a wrong result.

Split brain is the failure consensus exists to prevent: two parts of a cluster lose contact, each believes it is in charge, and both accept conflicting writes. Majority rules make split brain impossible, because two separate groups cannot both contain more than half of the nodes. The minority side stops accepting writes instead.

It helps to separate two planes. The control plane is metadata: which tables and tablets exist, where replicas live, which transactions committed, which nodes are members. The data plane is the rows and columns themselves. Consensus is used for the control plane because metadata is small and must never diverge. The data plane uses cheaper replication because it is large.

  • StarRocks FE. Frontend nodes store metadata in BDB JE (Berkeley DB Java Edition). The leader applies changes and replicates them; a write counts only after more than half of the follower FEs have it. Observer FEs replay the log and serve reads but do not vote. The docs recommend an odd number of followers, with 3 for high availability.
  • Doris FE. The same design (master, follower, observer), since StarRocks began in 2020 as a fork of Doris. The Doris planning guide asks for 3 or more followers in production. In compute-storage decoupled mode, a stateless Meta Service keeps metadata in FoundationDB, a distributed transactional key-value store with its own replication.
  • ClickHouse Keeper. A ZooKeeper-compatible coordination service written in C++ that uses Raft (through the NuRaft library). It stores replication metadata: which parts exist, each replica's queue of work, and hashes used to drop duplicate inserts. It can run inside clickhouse-server or as a separate process. The docs note a 3-node Keeper keeps working with 1 node down.
  • Trino. No consensus at all: there is one coordinator. Recovery from its loss is a restart.
  • Iceberg catalogs (the services that map each table name to its current metadata file). Consensus is delegated to the catalog's own database. An Iceberg commit is an atomic compare-and-swap of the table's current-metadata pointer, so a REST catalog backed by Postgres inherits Postgres's guarantees and Postgres's availability.

Field notes
  • Metadata nodes need low-latency fsync more than big disks. A Keeper or FE log on a busy shared disk shows up as slow DDL, slow inserts and spurious leader elections.
  • Treat frequent leader changes as a symptom to investigate. Common causes: network drops, an overloaded host, or (for the Java-based FE) long garbage-collection (GC) pauses that make a healthy leader look dead.
  • Three voters in one rack, or on one hypervisor host, give you the arithmetic of three nodes and the failure behaviour of one.
Incident

Symptom. Inserts into the ClickHouse tick tables start failing with Keeper errors. After a server restart, system.replicas shows is_readonly = 1 for every replicated table. Queries still work. Diagnosis. Two of the three Keeper nodes were virtual machines on the same physical host, which was rebooted for a firmware update. Consistency trade-offs: CAP and PACELC for analytics

Three words first. In this context consistency means every read sees the latest committed write, as if there were a single copy. Availability means every request to a working node gets a non-error answer. A network partition is a split in which groups of nodes cannot reach each other.

The CAP theorem (Eric Brewer's conjecture of 2000, proved by Seth Gilbert and Nancy Lynch in 2002) says that during a network partition a system must give up either consistency or availability. Daniel Abadi's 2012 IEEE Computer paper points out what people often miss: CAP only constrains behaviour during a failure. He extends it to PACELC: if there is a Partition, choose Availability or Consistency; Else, in normal running, choose Latency or Consistency. The everyday trade-off is the second half. Waiting for every copy makes writes slower.

Translated into analytics terms:

  • Metadata is consistency-first. FE quorums, Keeper and catalogs refuse writes when they lose a majority, which is the right choice: diverging table definitions would be far worse than a pause.
  • ClickHouse replicated data chooses latency. Inserts are acknowledged by one replica by default and copied afterwards, so a read can be stale.
  • StarRocks and Doris loads are atomic. A load commits as one transaction and becomes visible all at once, so a reader never sees half of a load.
  • Iceberg gives snapshot isolation. A reader sees one table snapshot for the whole query. A writer prepares new files, then atomically swaps the metadata pointer; if another writer got there first, the writer re-checks its changes against the new state and retries the commit, and the commit fails only if the two changes truly conflict (optimistic concurrency).

The questions that matter are concrete. A NAV for the upcoming mutual fund must be computed from one consistent set of holdings and prices for a date. A P&L report must not mix positions loaded before and after a correction. The standard pattern is write-audit-publish: load into a staging table or an Iceberg branch, run validations, then publish in one atomic step (a partition swap, an INSERT OVERWRITE, or fast-forwarding the Iceberg main branch). Readers only ever see the published state.

Common mistake

Quoting CAP as "pick any two of three" for a cluster in one data centre. CAP only applies while a partition is happening. For an analytical cluster on one site, the decisions you actually make daily are PACELC's "else" half: how many replicas must confirm a write, whether reads may come from a lagging copy, and when a batch becomes visible.

Node roles per engine

Each engine divides work among a few kinds of process. Knowing the roles tells you what to size, what to place carefully, and what can be thrown away and recreated.

  • StarRocks. The FE (frontend) holds metadata, parses and plans SQL, and coordinates queries. FEs are leader, follower or observer. The BE (backend) stores data on local disks and executes query fragments; it is used in shared-nothing mode. The CN (compute node) executes queries like a BE but keeps no primary data; data lives in object storage or HDFS (the Hadoop Distributed File System) and CNs cache it locally. CNs are used in shared-data mode.
  • Apache Doris. FE and BE, with the same roles as StarRocks in coupled mode. In compute-storage decoupled mode, BEs become compute that cache data from shared storage, a stateless Meta Service manages metadata on FoundationDB, and a Recycler deletes data that is no longer referenced. BEs are grouped into compute groups, each usable as an isolated tenant.
  • ClickHouse (open source). Every clickhouse-server both stores and computes. Servers are arranged into shards, each with one or more replicas, declared in the cluster configuration. Keeper coordinates replication. Distributed tables route queries across shards. There is no separate metadata master for queries.
  • Trino. One coordinator parses, plans and schedules; many workers read data and compute. Neither stores table data. Table metadata comes from a catalog: a service such as an Iceberg REST catalog or a Hive Metastore that maps table names to files.

What happens when a node dies

This is where design choices turn into minutes of outage or none. Walk through each role.

A StarRocks or Doris backend dies (shared-nothing)

  1. The FE stops receiving heartbeats and marks the backend as dead.
  2. Queries keep running: each tablet has other replicas, and the planner reads from them. Queries already running on the dead node fail and must be retried by the client.
  3. Loads keep working while the number of healthy replicas still meets the write quorum.
  4. The FE's tablet scheduler finds tablets with too few healthy replicas. After a configurable grace period (so a quick reboot does not trigger a full copy; in StarRocks tablet_sched_be_down_tolerate_time_s, 900 seconds by default for non-colocated tables), it clones each missing replica from a healthy copy onto another backend. In StarRocks you can watch this in information_schema.fe_tablet_schedules; in Doris, SHOW PROC '/cluster_health/tablet_health' compares total and healthy tablet counts per database.
  5. If the node comes back, its replicas catch up or are dropped as redundant.

To remove a backend on purpose, StarRocks recommends DECOMMISSION, which copies replicas away first and then removes the node. DROP removes it at once and leaves the cluster to rebuild the lost replicas, which the docs call a dangerous operation.

An FE dies

If it is a follower or observer, nothing visible happens while a majority of followers remain. If it is the leader, the followers elect a new one in seconds and clients reconnect. If two of three followers are lost at once, there is no majority: metadata cannot change, so DDL and loads stop. That case is an incident in the architectures section.

A ClickHouse replica dies

Distributed queries skip to the other replica of that shard, chosen by the load_balancing setting. Inserts can go to the surviving replica. When the dead server returns, it compares its parts with the state in Keeper, fetches what it missed, and moves broken or unexpected parts to a detached folder rather than deleting them. If its data differs too much, it refuses to start until an operator sets the force_restore_data flag. If every replica of one shard is down, queries fail unless you allow partial answers with skip_unavailable_shards, which for a P&L number is usually wrong.

A Trino node dies

If a worker dies, the queries using it fail, unless fault-tolerant execution is on. With retry-policy=TASK, intermediate data is spooled to an exchange manager (S3 or S3-compatible storage, Azure Blob Storage, Google Cloud Storage, HDFS, or a local filesystem that every node shares, which the docs advise only for non-production clusters), and failed tasks rerun elsewhere. With retry-policy=QUERY, the whole query reruns. The default is NONE. If the coordinator dies, every running query is lost and no new query is accepted until it restarts. As of Oct 2026 Trino has no built-in coordinator failover; teams run two or more clusters behind Trino Gateway (an open-source proxy that routes queries across several Trino clusters) for that.

A compute node dies (shared-data)

No data is lost, because the durable copy is in object storage. The work is reassigned to other compute nodes, whose caches do not yet hold that data, so the first queries afterwards run at object-storage speed until the cache warms.

Incident

Symptom. During month-end, every running Trino query fails at once and the BI tool reports connection errors for two minutes. Diagnosis. The coordinator ran out of memory planning a very large ad hoc query that listed hundreds of thousands of small files, and the process was killed. Workers were healthy. Fix. Restart the coordinator, raise its memory, add limits on query planning (for example, on the number of splits), and compact the small files in the lake. Senior lens

For this size, the senior questions are about failure behaviour and team load more than raw speed. RF 3 on shared-nothing triples flash cost but makes node loss boring; RF 2 halves the cost and makes every maintenance window a risk. Three voting metadata nodes are mandatory, and where they sit matters more than how big they are. Re-replication after a failure competes with the morning reporting peak, so the grace period and repair throttles are business decisions as much as technical ones: do you prefer an hour at reduced safety or slower dashboards? Finally, every extra component with its own quorum (FE, Keeper, FoundationDB, the catalog's Postgres, the object store) is another thing a small team must understand at 3 a.m. Fewer quorums is a legitimate design goal.

Say this

"I haven't operated ClickHouse, Doris or StarRocks myself; I've worked with managed warehouses, and I'd reason about them the same way. The way I reason about any of them is the same four questions. How is data split: partition by time for pruning, bucket by a high-cardinality key like instrument or account so work spreads evenly. How is it copied: tablet replicas with a write quorum in StarRocks and Doris, asynchronous per-table replication in ClickHouse, or object storage as the durable copy in shared-data mode. How do the nodes agree: a small Raft-style quorum for metadata, so three voting nodes in three separate failure domains. And what happens when a node dies: queries move to replicas, and the cluster re-copies data after a grace period. I would care most about the last one, because the morning P&L must not depend on every box being up."

Bare metal, virtual machines or Kubernetes

Bare metal means the database runs directly on the server's operating system. A hypervisor is software that splits one physical server into several virtual machines (VMs), each with its own operating system. A container is a packaged process with its own filesystem view that shares the host's kernel. Kubernetes (K8s) schedules containers, grouped into pods, across a pool of machines and restarts them when they fail. This layer is familiar from managed Kubernetes services.

Running databases on Kubernetes needs a few more pieces:

  • A StatefulSet runs pods with stable names (be-0, be-1) and gives each its own storage that follows it across restarts.
  • A PersistentVolume (PV) is a piece of storage; a PersistentVolumeClaim (PVC) is a pod's request for one; a StorageClass says what kind of storage to provide.
  • A local PersistentVolume is a disk physically inside one machine. It is fast, and it ties the pod to that machine.
  • A PodDisruptionBudget (PDB) limits how many pods of a group can be taken down at once by voluntary actions such as draining a node for patching.
  • Anti-affinity and topology spread rules tell the scheduler to keep pods of one group on different machines or racks.
  • An operator is a controller that encodes a product's operational procedures (create, scale, upgrade, replace) and acts on a custom resource, a new object type you describe in YAML, such as "a StarRocks cluster with 3 FEs and 6 BEs".

Why stateful systems on Kubernetes are harder

  1. Pods are meant to be disposable; database data is not. With local PVs, a pod is pinned to one machine. If that machine dies, Kubernetes cannot just start the pod elsewhere: the replacement has an empty disk and the database must rebuild it from replicas.
  2. Routine maintenance can break quorums. Draining two nodes at once can take down two FEs or two replicas of the same tablets. A PDB with maxUnavailable: 1 per component prevents that.
  3. Memory limits kill processes outright. A container that exceeds its memory limit is killed by the kernel's out-of-memory (OOM) killer (exit code 137), which for a backend means aborting every query and merge on it.
  4. CPU limits throttle. Kubernetes enforces CPU limits through the Linux scheduler's quota, so a busy pod is paused for the rest of each scheduling period. For a query engine that shows up as latency spikes. Many teams set memory request equal to limit and avoid CPU limits on database pods (a common practice; test it on your own workload).
  5. The operator becomes critical software. Its bugs and upgrades now affect the database.
  6. Network-attached volumes add latency. Data directories belong on local NVMe; network volumes suit small things like logs.

Network: the part people under-buy

North-south traffic flows between clients and the cluster. East-west traffic flows between servers inside the cluster. In an MPP database east-west traffic dominates: joins shuffle rows between nodes, every load is copied to each replica, a failed node's data is re-copied, and in shared-data designs every cache miss is a read from the object store over the network.

A few more terms. A NIC is a server's network interface card. GbE means gigabit Ethernet, so 25 GbE is 25 gigabits per second. A top-of-rack (ToR) switch connects the servers in one rack; a leaf-spine design connects many ToR (leaf) switches through a layer of spine switches so any two servers are a fixed number of hops apart. Bonding (often with the LACP protocol) combines two NIC ports, ideally cabled to two different switches, so one cable or switch can fail. Oversubscription is when the uplinks out of a rack carry less than the sum of the server links inside it. The MTU (maximum transmission unit) is the largest packet a link carries; jumbo frames raise it from the usual 1,500 bytes to about 9,000.

Compare them with storage: one PCIe 4.0 x4 NVMe drive has an interface ceiling near 8 GB/s, so a server with four NVMe drives can read data far faster than a 25 GbE link can carry it. In shared-nothing designs most scans stay local, so this matters mainly for shuffles and repair. In shared-data designs, the network is the path to the data, so it often becomes the bottleneck.

My view: two 25 GbE ports per server, bonded across two ToR switches; 100 GbE between switches; object-storage servers on 25 GbE or more; and a separate low-speed network for out-of-band management (the server's BMC, the baseboard management controller that gives remote power and console access even when the OS is down).

Field notes
  • East-west bandwidth sets how long a cluster runs at reduced redundancy after a failure. Faster repair means a shorter window in which a second failure loses data.
  • Join-heavy queries without colocation shuffle large volumes. If network graphs peak exactly when the morning risk reports run, the cheaper fix may be aligning bucket keys so those joins run colocated; faster switches come second.
  • Check the whole path: a 25 GbE server behind an oversubscribed ToR uplink behaves like a slower server whenever several racks talk at once.
Incident

Symptom. After new servers are added, small queries work but large result transfers and replica copies to the new nodes stall and time out. Ping works. Diagnosis. Disks: which kind for which job

A hard disk drive (HDD) stores data on spinning platters, so every random read waits for a mechanical seek. A solid-state drive (SSD) stores data in flash chips; a SATA SSD uses the older SATA interface. An NVMe drive is flash attached directly over PCIe lanes, with far higher throughput and lower latency. IOPS is the number of read or write operations per second, throughput is bytes per second, and latency is the time one operation takes. Endurance is how much a flash drive can be written over its life, often quoted in DWPD (full drive writes per day over the warranty). fsync is the system call that forces data to stable storage; logs that must survive power loss call it on every commit.

RAID or JBOD

RAID combines several disks into one logical volume with redundancy (RAID-1 and RAID-10 mirror; RAID-5 and RAID-6 use parity). JBOD ("just a bunch of disks") presents each disk separately. When the database already replicates across nodes, JBOD is common: each disk becomes a separate data directory, you keep full capacity and avoid parity write overhead, and a failed disk loses only the tablets on it, which are re-copied from replicas. StarRocks accepts several storage paths per BE, and ClickHouse storage policies can spread a table over several disks. The ClickHouse docs, for their part, describe double replication with RAID on each server as a reasonable production setup. Both are defensible; pick one and make repair procedures match it.

Free space is part of capacity

Columnar engines rewrite data constantly. ClickHouse merges need room to write the merged part before deleting the inputs, and by default a single merge can combine up to 150 GiB of parts when space allows. StarRocks and Doris compaction does the same for tablets. Doris documents explicit thresholds. By default the FE stops choosing a disk as a target for balancing, colocation relocation or decommission once it passes the high watermark (above 85% usage or under 2 GB free). The FE flood stage is usage above 95% together with under 1 GB free, where loads, replica repair and restores onto that disk are refused. Each BE also enforces its own flood stage at 90% usage with under 1 GB free, blocking writes, compaction and clones. A disk at 90% is already a problem.

Field notes
  • Put metadata logs (FE, Keeper, FoundationDB) on drives with low and predictable fsync latency, separate from data disks that merges keep busy.
  • Compaction and merges multiply writes. Choose data drives rated for mixed workloads rather than read-optimised drives, and graph media wear.
  • Drives bought in one batch, with one firmware version, tend to age and fail together. Stagger purchases where you can and apply firmware updates deliberately.
  • Alert on disk usage well before engine thresholds, for example at 70% and 80%, because a big backfill or a failed node can add several percent in hours.
Incident

Symptom. During a one-off backfill of five years of MCX commodity ticks, inserts on one ClickHouse server start failing with not-enough-space errors, and parts start piling up. Diagnosis. system.disks shows the data disk nearly full; system.merges shows large merges in progress, each needing free space for its output. The backfill wrote faster than merges could compact, and the merges themselves needed headroom the disk no longer had. Fix. Pause the backfill, drop or move old partitions to another volume, add a disk to the storage policy, then resume the backfill in smaller batches. Lesson. Plan backfills as capacity events. Failure domains and rack awareness

A failure domain is a set of components that can fail together because they share something: a power feed, a switch, a hypervisor host, a room. The blast radius of a failure is everything it takes down. Domains nest: a disk sits in a server, a server in a rack with its PDU (power distribution unit) and ToR switch, a rack in a room, a room in a site. Rack awareness means the system knows which rack each node is in and places copies in different racks. A correlated failure is several components failing at once for one shared reason, which is exactly what replication assumes will not happen.

How each engine expresses placement (as of Oct 2026):

  • StarRocks: since v3.2.8, backends can carry a labels.location such as rack:rack1, and a table's replicas are spread round-robin across labels, so one rack failure leaves the other copies intact.
  • Doris: backends carry a location tag, and the replication_allocation property says how many replicas go to each tag. Tagging backends by rack and allocating one replica per tag gives rack placement (my mapping of the feature to racks).
  • ClickHouse: placement is manual. You decide which servers are replicas of which shard in the cluster configuration, and you place Keeper nodes yourself.
  • Object stores such as Ceph use a placement map with a configurable failure domain (host or rack) for their own copies or erasure-coded chunks.

The two-rack trap

Three voting metadata nodes across two racks means one rack holds two of them. If that rack loses power, the survivor is a minority and metadata stops. The same arithmetic applies to RF 3 data across two racks: one rack holds two copies of some tablets, so losing it leaves one copy. To survive the loss of any single rack, you need three failure domains for the voters. The third does not have to be a full rack: a small server on separate power and a separate switch, in another row or room, can host the third voter.

The same data in a shared-data design

In a shared-data design the database keeps no replicas of its own; the object store protects the data. With erasure coding, the store splits each object into k data chunks and m parity chunks and can rebuild it from any k of them. A 4+2 scheme stores 1.5 bytes per byte and survives two lost chunks; with the host as the failure domain it needs at least 6 storage hosts. Year-3 compressed data is 7.5 TB × 2.197 = 16.5 TB, which becomes 16.5 × 1.5 = 24.7 TB on disk, or about 35 TB of raw capacity at a 70% ceiling. Add a cache on each compute node large enough for the hot set. If the hot set is the last three months of ticks plus all positions, say 20% of compressed data (an assumption to measure), that is about 3.3 TB in year 3, so four compute nodes with 2 TB of NVMe cache each give comfortable room.

The lake itself, holding everything as Iceberg tables plus documents, would be about 7.5 TB of Parquet plus 10 TB of documents today, 38 TB in year 3, and with 4+2 erasure coding and a 70% ceiling about 82 TB of raw object-storage capacity.

CPU and memory

The StarRocks planning guide (3.4 docs) suggests 8 cores and 16 GB of RAM per FE and 16 cores and 64 GB per BE, with at least three follower FEs and at least three BEs; it gives no separate figure for CNs. Those are floors. My view: small dedicated FE machines, and backends with 32 to 64 cores and 256 GB of RAM, because concurrency from dashboards and agents and the large joins in risk reporting are memory-bound long before they are disk-bound.

Senior lens

A senior engineer asks the clarifying questions before doing arithmetic: is 40 TB raw or compressed, does it include PDFs, do we keep full-depth ticks or minute bars after a year, how many concurrent users and agents, what RPO and RTO. Then they separate what must be hot (recent ticks, positions, P&L, NAV inputs) from what only needs to exist (old ticks, documents), because that split moves the hardware bill more than any engine choice. They also price the whole life: flash for RF 3, spare parts, the second site, support contracts, and people. At under 40 TB, hardware is a modest cost; the platform team's time is the dominant one, which argues for fewer components and one primary engine.

Day-2 operations

Day-2 operations are everything after installation: upgrades, backups, monitoring, security and incident response. This is where self-hosting costs are actually paid.

Rolling upgrades

A rolling upgrade replaces software one node at a time so the service stays up. The order matters, and each engine documents it (as of Oct 2026):

  • StarRocks: upgrade BEs and CNs first, then FEs, followers before the leader. The docs say an inverted order can make FEs and BEs incompatible and crash the service. Move one minor version at a time; when crossing several, run ALTER SYSTEM CREATE IMAGE between steps. Downgrades reverse the component order: FEs first (followers, then the leader), then BEs and CNs.
  • Doris: disable replica repair and balancing, upgrade one BE as a canary, then the other BEs one by one, then FEs (observers and followers first, master last), then re-enable repair and balancing. Go one minor version at a time (for example 3.0, then 3.1, then 3.2). In decoupled mode the order is Meta Service, Recycler (if deployed separately), BE, FE. On Kubernetes, the Doris Operator docs say to change images in the order CN/BE, then FE, then broker, waiting for each to finish.
  • ClickHouse: upgrade one replica of each shard at a time, wait for it to rejoin and catch up, then the next. Read the backward-incompatible-changes part of the release notes for every version you cross. As of Oct 2026 the current releases are v26.9 stable and v26.8 LTS; my view is that a small team should prefer long-term-support releases.

Backup and restore

  • StarRocks shared-nothing: BACKUP DATABASE ... SNAPSHOT ... TO repo, where the repository can be AWS S3, an S3-compatible store such as MinIO, Google Cloud Storage or HDFS. Backups are full, at database, table or partition level; the docs suggest backing up only new partitions to approximate incremental backups. Shared-data clusters cannot use BACKUP/RESTORE; they use Cluster Snapshot (a beta feature since v3.4.2), which stores a metadata snapshot in object storage and keeps the data snapshot in the same location as the original data files. Only the latest automated snapshot is retained, so it gives one recovery point and no history.
  • ClickHouse: BACKUP ... TO S3(...) with incremental backups through base_backup, and ON CLUSTER for a whole cluster. Restoring an incremental backup needs the whole chain.
  • The lake: Iceberg snapshots let you read old versions and undo a bad write, but they live in the same bucket and snapshot expiry deletes them. If the bucket or the store is lost, they go with it, so replicate the bucket to a second site.

Common mistake

Shared-memory, shared-disk, shared-nothing and shared-data

These four names describe what the nodes of a database share: memory, disks, nothing, or one common data store. The choice decides how a system scales, how it recovers from failure, what it costs and how hard it is to run. StarRocks and Doris each offer both a shared-nothing and a shared-data mode, so "which one, and why" is the central architecture question reviewers are likely to press on.

Four ways to share, defined

In 1986 Michael Stonebraker's short paper "The Case for Shared Nothing" named three ways to build a multiprocessor database:

  • Shared-memory (SM): many processors share one central memory and the same disks. Today this is simply one large server.
  • Shared-disk (SD): each processor has private memory, and all of them share one collection of disks.
  • Shared-nothing (SN): each node has its own processors, memory and disks, and nodes cooperate only by sending messages over the network.

His examples were from the hardware of the day (Synapse and IBM/AP for shared-memory, VAXcluster for shared-disk, Tandem and Tolerant for shared-nothing), and he argued that shared-nothing is the preferred approach. His argument rests on an idea worth remembering. He called a database problem "delightful" when the data can be partitioned so that every transaction runs on a single site, and observed that most applications are nearly delightful. His conclusion: for such databases, shared-nothing has no apparent disadvantage compared with the alternatives.

Thirty years later, the cloud produced a fourth design. Shared-data, also called storage-compute separation or disaggregated storage, keeps one durable copy of the data in a shared store (in practice an object store such as S3) and runs compute nodes that hold only caches. The compute nodes still divide each query among themselves like a shared-nothing system. What they share is the durable data, through a metadata service that records which files make up each table version. Snowflake's SIGMOD 2016 paper named this the multi-cluster, shared-data architecture.

Shared-disk and shared-data sound alike, and an interviewer may test whether you can separate them. In shared-disk, nodes read and write the same mutable disk blocks, so every node's memory cache must be kept consistent with every other node's: when one node changes a block, others must not use a stale copy. That coherence traffic is what limits scaling. In shared-data, the files in the object store are immutable. A write creates new files and then commits a new table version in the metadata service. Caches of immutable files never go stale, so compute nodes can cache freely without talking to each other. Immutability is the trick that lets shared-data scale where shared-disk struggled.

Shared-memory and shared-disk: where it started

A shared-memory system today is one server with many cores, all of which see all memory. It is the simplest design: no network inside a query, no distributed transactions, no rebalancing. Its limit is the largest machine you can buy and the fact that it is one failure domain. It remains a fair baseline. A team mart of a few hundred gigabytes is often served faster and more cheaply by one large DuckDB or Postgres server than by any cluster, and a senior engineer will say so rather than distribute everything by reflex.

Oracle RAC (Real Application Clusters) is the best-known shared-disk database. Several Oracle instances on different servers open one database whose files sit on shared storage. Cache Fusion keeps their memory caches coherent: when one instance needs a block that another holds in memory, the block is shipped over a private interconnect, and global services track which instance owns which block. RAC's strengths are failover (any surviving instance can serve any data) and transparency for OLTP applications. Its costs are expensive shared storage, a dedicated low-latency interconnect, and coherence traffic that grows when several instances update the same blocks. Analytical systems mostly moved away from this design because scans of large data sets want local, sequential reads more than a shared block pool.

Sources: Oracle RAC database (Oracle 26 docs) · Stonebraker (1986)

Shared-nothing: the MPP workhorse

In a shared-nothing MPP database, each table is partitioned across nodes (the partitioning and bucketing of the first section) and each node scans its own partitions from local disk. The commercial line runs from Teradata in the 1980s, which hashed rows across processing units joined by a dedicated interconnect, through Greenplum (an MPP database built on Postgres), Vertica (whose original Enterprise mode is shared-nothing) and Redshift's DC2 nodes with local SSDs, to today's open-source ClickHouse, StarRocks with BEs, and Doris in coupled mode.

Strengths, as operators experience them:

  • Fast, predictable scans. Data is on local NVMe next to the CPU. Latency does not depend on a cache being warm.
  • Few moving parts. No object store and no separate metadata store in the data path. For ClickHouse, only Keeper sits beside the servers.
  • Maturity. This is the design these engines were built and tuned for first.

Weaknesses, as the Snowflake paper lists them for the cloud:

  • Heterogeneous workload. One hardware shape must serve bulk loading (heavy I/O, light compute) and complex queries (light I/O, heavy compute), so it is a compromise with low average utilisation.
  • Membership changes. Adding or losing a node forces large amounts of data to be reshuffled, by the same nodes that are serving queries.
  • Online upgrade. Upgrading node by node without downtime is possible but hard when everything is tightly coupled.

The paper then adds a line that matters on-prem: "In an on-premise environment, these issues can usually be tolerated." Its reasoning is that on-prem clusters are a small fixed pool, upgrades are rare, and resizing is rare. Snowflake built shared-data because cloud conditions made those problems constant. An on-prem firm should weigh the same problems at on-prem frequency.

Incident

Symptom. The team adds three backends to a six-backend StarRocks cluster on a Friday evening to make room for tick history. On Monday morning, dashboards are several times slower than usual, network links between racks are saturated, and loads are falling behind. Diagnosis. Tablet balancing is enabled by default (tablet_sched_disable_balance is false), so the tablet scheduler is moving about a third of all tablets onto the new nodes. information_schema.fe_tablet_schedules shows thousands of balance clone tasks. Each clone reads from an old node, crosses the network and writes to a new one, competing with queries, loads and compaction. Fix. Pause balancing during market hours (set tablet_sched_disable_balance to true), resume it overnight, and lower scheduling concurrency so the move takes several nights instead of one burst. Lesson. In shared-nothing, adding capacity is a data migration. Schedule it like one, with a throttle and a calendar.

Field notes
  • ClickHouse behaves the opposite way: adding a shard moves nothing. Old shards stay full and busy, the new shard sits nearly empty, and old data stays skewed until you move it yourself (re-insert, or copy partitions) or wait for it to age out. Shard weights only steer new writes.
  • In shared-nothing, decommissioning is also a migration. Use the engine's decommission command so replicas are copied off before the node leaves.
  • Soft isolation exists inside shared-nothing clusters: StarRocks resource groups and Doris workload groups cap CPU and memory shares per workload. They protect dashboards from a runaway batch reasonably well, though both still share the same disks and network.

Shared-data: separating storage from compute

In a shared-data system, compute nodes keep no primary data. The durable copy lives in an object store, a metadata service records which immutable files form each table version, and each compute node caches hot files in memory and on local NVMe. The main systems, in the order they appeared:

  • Snowflake (SIGMOD 2016). Data lives in S3. Compute comes in virtual warehouses, each a cluster with a local-disk cache of table file headers and columns, managed with a simple least-recently-used policy. Files are assigned to workers by consistent hashing on file names, so the same worker tends to read the same file. When a warehouse is resized, nothing is shuffled: the assignment changes and caches refill gradually. Metadata lives in a transactional key-value store in the cloud services layer. Many warehouses read the same data, which is how Snowflake isolates workloads. The NSDI 2020 follow-up studied 70 million queries over 14 days to examine caching, elasticity and intermediate data on this design.
  • Amazon Redshift RA3 (announced December 2019). Data lives in Redshift Managed Storage, backed by S3, with large local SSDs as caches. The SIGMOD 2022 paper notes that because compute nodes are practically stateless, an in-place resize becomes a pure metadata operation.
  • Vertica Eon mode. Data in communal object storage with a local cache (the depot); the older Enterprise mode stays shared-nothing. Vertica documents both modes as deployable on-prem or in the cloud.
  • StarRocks shared-data. FEs plus stateless CNs; data in object storage or HDFS; caching in memory and on local disk, with hot data served from cache and cold data fetched and then cached, plus prefetching. Tables created with caching enabled write to both local disk and object storage.
  • Apache Doris decoupled mode (since Doris 3.0, 2024). BEs hold no primary data and keep a file cache; shared storage (S3 or HDFS) is primary; a stateless Meta Service keeps metadata in FoundationDB; compute groups act as isolated tenants. The 3.0 release notes report query performance (on a 1 TB TPC-DS benchmark) on par with coupled mode when the cache is fully warm, about 10% lower when it is partially hit, and about 35% lower when it misses completely. Those are vendor-reported figures, and they show the real dependency: the cache.
  • ClickHouse Cloud's SharedMergeTree. Data in object storage, metadata in Keeper, replicas that talk only through shared storage and Keeper, and many replicas per table. It powers ClickHouse Cloud and is not part of the open-source build.
  • Trino or Spark over an Iceberg lake. The extreme case: the engine owns no storage and no table metadata. The table format (Iceberg) and its catalog play the role of the metadata service, and any engine that speaks Iceberg can read the same tables. The Lakehouse paper (CIDR 2021) argues for exactly this: warehouse features built on open file formats in object storage, with a transactional metadata layer and caching to recover performance.

Open-source ClickHouse can put MergeTree data on S3-type disks with a local cache disk, but zero-copy replication has been disabled by default since 22.8 and the docs do not recommend it for production. The docs describe zero-copy as replicating only part metadata and leave the alternative implicit. My inference from that: without it, each replica of a ReplicatedMergeTree table stores its own copy of every part, so two replicas on one object store keep the data twice. In practice, open-source ClickHouse is a shared-nothing engine that can tier cold data to object storage; its true shared-data engine is cloud-only.

What shared-data gives you:

  • Independent scaling. Add compute for month-end without buying disks; add storage for tick history without buying CPUs.
  • Hard workload isolation. Separate compute groups read the same tables without competing for CPU or cache.
  • Cheaper durability. One erasure-coded copy (for example 1.5 bytes per byte with 4+2) replaces three full copies on NVMe.
  • Fast failure recovery. A dead compute node loses only cache; there is no re-replication storm.
  • Simpler upgrades. Stateless compute nodes can be replaced rather than nursed.

What it costs you:

  • Cache dependence. Performance is good when the hot set is cached and drops to object-store speed when it is not, for example after restarts, upgrades or a sudden shift to old data.
  • The network becomes the data path. Every cache miss crosses it.
  • The object store becomes a critical system. On-prem, someone must run it: its capacity, its disks, its upgrades, its request-rate limits.
  • More metadata machinery. FoundationDB in Doris decoupled mode, or a catalog and its database for a lake, are additional quorums to place and monitor.
  • Write latency and small files. Each commit writes new objects; frequent small loads create many small files that must be compacted.

Field notes
  • The number to watch in shared-data mode is the cache hit ratio per workload, next to object-store read latency. When dashboards slow down, check those two before anything else.
  • Size the cache from the hot set, measured from query logs (which partitions are read in a typical week), with room to spare. A cache slightly smaller than the hot set thrashes: files are evicted just before they are needed again.
  • Object stores have request-rate limits as well as bandwidth limits. AWS documents at least 3,500 write and 5,500 read requests per second per partitioned prefix (as of Oct 2026). An on-prem store's limits come from its own hardware and gateways, so load-test them with realistic object sizes before go-live.
  • Many small files hurt twice: more requests per query and more metadata per table. Frequent small loads need regular compaction, whichever engine owns the files.
  • Freshly written data may be served from object storage on first read unless the engine writes it through the cache. Check how your engine treats newly loaded data before promising sub-second latency on it.

What independent scaling really buys on-prem

In the cloud, independent scaling means renting compute by the minute and storage by the gigabyte, separately. On-prem, the hardware is bought up front either way. You cannot scale past the servers in the rack, and idle compute costs the same as busy compute. So the honest on-prem case for shared-data rests on five narrower benefits:

  1. Workload isolation. The overnight risk batch and the morning dashboards get separate compute groups over the same data.
  2. Durability cost. One erasure-coded copy on cheaper media instead of three copies on NVMe. At this size this saves tens of terabytes of flash, a real but modest sum.
  3. Stateless compute. Replacing or upgrading a compute node needs no data movement.
  4. Shared compute pool. Compute nodes can run on the same Kubernetes pool as other jobs and shift between uses over the day.
  5. Storage growth without CPU purchases. Years of tick history can grow on dense storage servers.

Against those, on-prem shared-data adds an object store the team must run well. Combined with the Snowflake paper's own remark that on-prem clusters tolerate shared-nothing's problems, my view is that shared-data is a second-phase optimisation, worth adopting once the object store has a track record, and the open table format is a bigger lever against lock-in than the storage mode of the serving engine.

Hybrid patterns that work

  1. Lake as source of truth, hot serving tables on top. Every dataset lands in Iceberg. The MPP engine holds native tables only for what needs sub-second latency: recent ticks, current positions, P&L and NAV marts. Serving tables can always be rebuilt from the lake, which also makes the MPP engine replaceable. Record the Iceberg snapshot ID each serving table was built from, so any number on a dashboard can be traced to an exact lake version.
  2. Query the lake in place for colder data. StarRocks and Doris read Iceberg through external catalogs, and (as of Oct 2026) both can build asynchronous materialized views over those tables, so analysts query old history without loading it. StarRocks refreshes such views on a schedule or on demand, and a commit to the lake does not trigger a refresh by itself; check how your Doris version detects lake changes. In both engines, partition-level refresh supports only some Iceberg partition layouts.
  3. Tiering inside one engine. Keep recent partitions on local NVMe and age older ones to object storage: shared-data caches do this automatically; ClickHouse storage policies can move old partitions to an object-storage disk by TTL.
  4. Write to the lake from the engine where supported. Engines differ widely here (as of Oct 2026): Doris supports INSERT, INSERT OVERWRITE, UPDATE, DELETE and MERGE INTO on Iceberg; StarRocks supports INSERT and INSERT OVERWRITE (Parquet), hidden-partition writes and a compaction API since 4.0, and DELETE through position delete files since 4.1; ClickHouse INSERT into Iceberg is beta since 26.2 behind allow_insert_into_iceberg=1, with UPDATE and MERGE unsupported. A common, safer choice is to let pipelines (Spark, PyIceberg or the engine with the strongest support) own lake writes, and let serving engines read.

Incident

Symptom. Every load and every DDL statement on the analytics cluster fails; Prefect flows that publish the day's positions go red one after another. Diagnosis. Two of the three FE followers ran as VMs on the same hypervisor host, which lost power. The surviving follower is a minority, cannot elect itself leader, and cannot commit metadata changes, which every load needs. Fix. Restore the host so a majority returns and a leader is elected. If both lost FEs had been unrecoverable, the last resort is the documented metadata recovery procedure, which restarts one FE as leader from its local metadata (risking the most recent changes) before new followers are added. Afterwards, move the FEs to three separate hosts in three failure domains and back up FE metadata images. Lesson. A quorum of three placed in one failure domain is a quorum of one. Draw failure domains before placing voters, and rehearse recovery on staging.

Common mistake

Treating shared-data as a free upgrade over shared-nothing. It moves the hard problems: rebalancing storms become cache warm-ups, replica repair becomes object-store operations, and a single FE quorum becomes an FE quorum plus a metadata store plus the object store's own quorum. On-prem, where elasticity is limited by the hardware you own, those trades must be argued for each workload.

Senior lens

A senior architect separates three decisions that juniors merge. First, where the source of truth lives: an open table format on object storage keeps the platform free to change engines, which speaks directly to its lock-in concern. Second, how the serving engine stores its hot data: shared-nothing is simpler and faster on-prem, shared-data buys isolation and cheaper durability at the cost of a cache and an object store to run. Third, how many quorums and stateful systems the team can operate at 3 a.m. They would also keep the decision reversible: if serving tables are always rebuildable from the lake, switching a serving engine from shared-nothing to shared-data later only moves copies, while the lake keeps the authoritative data throughout.

Say this

"Shared-nothing means each node owns a slice of the data on local disk; scans are fast and predictable, but adding or losing a node means copying data around while the cluster is serving queries. Shared-data keeps one durable copy in object storage and makes compute nodes stateless with a local cache; you get independent scaling, workload isolation and cheaper durability, but performance now depends on cache hit rate and on running an object store well. Snowflake's own paper says on-prem clusters can usually tolerate shared-nothing's problems, because resizes and upgrades are rare. So for a platform under 40 TB with a small team, I'd make the Iceberg lake the source of truth, serve hot data from one MPP engine in shared-nothing mode with three replicas, and revisit shared-data once the object store has a track record. I haven't operated either mode myself; this is how I'd reason about the trade."
