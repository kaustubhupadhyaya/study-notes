Iceberg tables from the inside

Apache Iceberg is a table format: a set of rules for describing one table as immutable data files plus a tree of metadata files on object storage, so that many engines can read and write the same table safely. It is the layer that lets StarRocks or Doris, Trino, Spark and plain Python all work on the same tick, position and net asset value (NAV) tables on the on-prem store without copying them. This section builds the format from the problem it solves down to how it handles a single corrected trade.

The problem: a table that is just a directory

Before table formats, a lake table was a Hive-style table: a directory of files on HDFS or S3 plus an entry in the Hive Metastore (HMS), a database-backed service from the Hadoop world that records each table's schema, its root directory and its list of partitions. A partition is a group of rows stored together so a query can skip the rest. In Hive each partition is a subdirectory named after its value, such as positions/trade_date=2026-10-13/, and the table's contents are whatever files a reader finds when it lists those directories.

That design worked on HDFS, where listing and renaming a directory are cheap, single-server operations. On object storage it has five problems that every later design choice answers.

  1. Listing is slow. To plan a query the engine lists every matching partition directory. Iceberg's own reliability notes describe this as O(n) listing calls in the number of partitions. An S3 LIST returns at most 1,000 keys per page, so a year of futures and options (F&O) ticks split by date and underlying means thousands of LIST round trips before any data is read.
  2. No atomic multi-file commit. A job that rewrites a partition deletes old files and writes new ones as separate object operations. A reader in the middle sees a mix of old and new files, or an empty partition. There is no rename on object storage to make the switch in one step.
  3. Partition values live in paths. The partition value is a directory name, so users must filter on trade_date explicitly. A query that filters only on the tick timestamp ts scans the whole table. Changing the scheme from daily to hourly breaks every saved query.
  4. Schema changes are unsafe. Hive matches file columns to table columns by name or by position, depending on format and settings. Rename a column, or drop one and add another, and old files can return the wrong column's values or silent nulls.
  5. Concurrent writers have no protocol. Files and the metastore are updated separately. Two jobs writing the same partition race, and the last one to touch the metastore wins.
Incident

Symptom. On a Tuesday morning the risk dashboard shows desk P&L for 13 October about 40% lower than the official report; an hour later it matches. Diagnosis. The nightly job overwrites positions/trade_date=2026-10-13/ on a Hive-style table by deleting the old Parquet files and then writing new ones. The dashboard query ran between the two steps and summed only the files that existed at that moment. Nothing failed, so no alert fired. Fix. As a stopgap, write each night's output to a new prefix and repoint the partition's location in the metastore in one update. The real fix is a table format whose commit is a single atomic pointer swap. Lesson. On object storage, a directory is never a transaction boundary. If readers can run while writers write, the table needs snapshot isolation.

The metadata tree, from the top

Iceberg describes a table with five layers of files plus one pointer. Each layer exists so a reader can skip work at the layer below.

  • The catalog is a service that maps a table name such as markets.fo_ticks to the location of the table's current metadata file, and that changes that pointer atomically. The catalogs section covers it in depth.
  • The metadata file (NNNNN-uuid.metadata.json) is a JSON document that describes the whole table at one version: its schemas (every schema the table has ever had, each with an ID), its partition specs (rules for deriving partition values, also versioned), its sort orders, its table properties (settings such as target file size), the list of valid snapshots, named references (branches and tags) and a log of earlier metadata files. Every commit writes a new metadata file; the old one stays until it is cleaned up.
  • A snapshot is the complete state of the table after one commit. In the metadata file each snapshot records a snapshot-id, its parent's ID, a sequence number (a counter that increases with every commit and orders files by age), a timestamp, the schema it was written with, the location of its manifest list and a summary: the operation (append, overwrite, delete, replace) plus counts such as added records and added bytes.
  • The manifest list is one Avro file per snapshot. It has one row per manifest that makes up the snapshot, and each row carries a partition summary (the lowest and highest value of each partition field in that manifest, and whether it contains nulls), file and row counts, the manifest's sequence number and whether it tracks data files or delete files.
  • A manifest is an Avro file that lists data files or delete files, one entry per file. Each entry holds the file path, format, partition values, record count, file size and per-column statistics: value counts, null counts, and lower and upper bounds. Manifests are reused across snapshots, which is why an append can commit by adding one small manifest and pointing at all the old ones.
  • Data files hold the rows, usually as Parquet. Delete files record rows that later commits removed without rewriting the data file (covered below). Optional Puffin files hold extra statistics such as distinct-value sketches, and in format v3 they also hold deletion vectors.

Field notes
  • Every commit rewrites the whole metadata file. Its size grows with the number of retained snapshots, schemas and references, so a table that commits every few seconds and never expires snapshots ends up with a metadata file that every reader and writer must download and parse.
  • Paths inside metadata are absolute (s3://lake-silver/...) in formats v1 to v3. Renaming a bucket therefore means rewriting metadata (Iceberg ships a rewriteTablePath action for copies). The S3 endpoint hostname lives in client configuration, so moving the store to new hardware with the same bucket names does not touch metadata. Choose bucket names once.
  • Column statistics are collected for the first 100 columns by default (write.metadata.metrics.max-inferred-column-defaults) in truncate(16) mode, which keeps the first 16 characters of string bounds. A loan tape with 300 columns gets no min/max on column 250 unless you name it with write.metadata.metrics.column.<col>.
  • You can query the tree directly. Trino exposes "fo_ticks$snapshots", $manifests, $files, $partitions, $history and $refs; Spark exposes the same as markets.fo_ticks.snapshots and so on. Most diagnosis starts there.

Walking one query down the tree

Take a table of NSE F&O ticks, markets.fo_ticks, partitioned by day(ts) and bucket(16, underlying) and sorted inside each file by underlying, contract, ts. An analyst asks for traded value of NIFTY options in the first hour of 13 October 2026.

SELECT contract, sum(price * qty) AS traded_value
FROM markets.fo_ticks
WHERE underlying = 'NIFTY'
  AND ts >= TIMESTAMP '2026-10-13 09:15:00 Asia/Kolkata'
  AND ts <  TIMESTAMP '2026-10-13 10:15:00 Asia/Kolkata'
GROUP BY contract;

The counts below are illustrative, chosen to show the shape of the work.

  1. Catalog. One call returns the location of 00042-...metadata.json.
  2. Metadata file. The engine reads it, finds the current snapshot, the schema and the partition specs, and gets the manifest list location. No other snapshot is touched.
  3. Manifest list. Suppose it lists 40 manifests. The engine turns the filter on ts into a filter on the partition field ts_day (Iceberg calls this an inclusive projection: any row that matches the query must sit in a matching partition) and computes bucket(16, 'NIFTY'). Partition summaries show 38 manifests cover other days, so they are never opened.
  4. Manifests. The two remaining manifests list, say, 3,000 files. Partition values cut that to the 60 files for 13 October in NIFTY's bucket. Column bounds on ts and underlying cut it again: because files are sorted, most files cover a narrow time slice, and only 6 overlap 09:15 to 10:15.
  5. Data files. For each of the 6 files the engine issues a range GET for the Parquet footer, then range GETs for only the price, qty, contract, ts and underlying column chunks of row groups whose statistics overlap the filter.
  6. Deletes. If any delete files or deletion vectors apply to those 6 files, the engine reads them and drops the deleted rows.
flowchart TD
  Q["Query NIFTY 09:15 to 10:15 on 13 Oct"] --> C["Catalog returns pointer to metadata v42"]
  C --> M["metadata.json picks current snapshot"]
  M --> L["Manifest list with 40 manifests"]
  L -->|"partition summaries"| S1["38 manifests skipped"]
  L --> F["2 manifests opened listing 3000 files"]
  F -->|"partition values"| P["60 files for the day and bucket"]
  P -->|"min and max on ts"| R["6 files read"]
  R -->|"footer stats"| G["Only matching row groups and 5 columns fetched"]

Without the sort order, step 4 prunes much less: if each file holds ticks from the whole day, every file's ts range overlaps the hour and all 60 files are read. Partitioning decides which files are candidates; sorting decides how tight each file's statistics are.

Field notes
  • Planning usually happens on one node (the Trino coordinator, the StarRocks or Doris frontend (FE) node, the Spark driver). Spark can switch to distributed planning for very large tables (read.data-planning-mode), and a REST catalog may offer server-side planning, but the single-node case is the common one. When queries are slow before any data moves, the cause is usually metadata: thousands of manifests, a large metadata file, or a cold metadata cache.
  • The Iceberg Java library reports scan metrics such as scanned and skipped data manifests, result data files, skipped data files and delete files used. REST catalogs can receive these reports through a metrics endpoint, which is a cheap way to see pruning effectiveness per table.
  • A filter wrapped in a function that Iceberg cannot project (for example a cast of ts to a string) often defeats pruning. Engines differ in what they can push down, so check the plan.
  • Bucket pruning works only for equality and IN filters. underlying LIKE 'NIFTY%' cannot use bucket(16, underlying).

Commits: optimistic concurrency and the pointer swap

Iceberg never locks a table for the length of a job. It uses optimistic concurrency: each writer assumes nobody else will commit, does all its work, and checks only at the end. A write goes through six steps.

  1. Load the table: the current metadata file is v41 and the current snapshot is S41.
  2. Write new data files (and delete files, if the operation removes rows).
  3. Write a new manifest that lists the new files.
  4. Write a new manifest list: the manifests of S41 plus the new one.
  5. Write metadata file v42, which adds snapshot S42 with parent S41.
  6. Ask the catalog to change the table's pointer from v41 to v42 only if it still points at v41. This compare-and-swap is the commit. Until it succeeds, nobody sees the new files; after it succeeds, every reader that loads the table sees S42.

If the swap fails because another writer committed first, the writer reloads the table, checks that its assumptions still hold, rewrites only its small metadata files (the manifest list and metadata file, plus any manifests it merges) on top of the new state, and tries again. Data files are reused across retries, so a retry costs a few small metadata writes. The Java defaults are 4 retries (commit.retry.num-retries), waits from 100 ms up to 60 seconds, and 30 minutes in total.

Each catalog type implements the swap differently, and that difference decides whether concurrent writers are safe.

Catalog typeHow the swap is made atomic
JDBC (Postgres)An UPDATE of the table's row that sets the new metadata location WHERE the stored location still equals the old one; one row updated means success.

The spec says file-system tables need atomic rename, which object stores do not offer, so this type is unsafe for concurrent writers on S3-compatible storage. The spec also marks this commit scheme deprecated and slated for removal in v4.

What two concurrent writers see

Both writers below start from snapshot S41 of risk.positions_eod.

  • Two appends. The equities loader and the MCX loader both append rows for 13 October. The equities loader commits S42. The MCX loader's swap fails, it reloads, sees that an append makes no assumption about existing files, rebuilds its manifest list on top of S42 and commits S43. Both succeed; the only cost is one retry.
  • A correction against a late append. An end-of-day (EOD) job runs MERGE to correct quantities for book B7 on 13 October, reading S41. Meanwhile a late trade file for the same date is appended as S42. When the MERGE tries to commit, Iceberg checks whether any data file matching the MERGE's filter was added since S41. One was, so under the default serializable isolation the commit fails with a validation error and the job must rerun. Under snapshot isolation (write.merge.isolation-level=snapshot) it would commit, and the late trades would never have been seen by the correction.
  • Compaction against a delete. A compaction job rewrites files F1 and F2 into one larger file while a DELETE removes a cancelled trade from F1. Compaction's assumption is that F1 and F2 are still live with no new deletes; if the DELETE committed first, that compaction group fails and is retried later.
flowchart LR
  A["Writer A MERGE book B7 from S41"] --> CA["Swap v41 to v42"]
  B["Writer B late trades from S41"] --> CB["Swap v41 to v42"]
  CB -->|"wins first"| S42["S42 committed"]
  CA -->|"409 conflict"| RV["Reload S42 and validate"]
  RV -->|"new files in same filter"| X["Serializable fails, rerun"]
  RV -->|"no overlap"| S43["Rebase and commit S43"]

In summary: readers get snapshot isolation (each query reads one committed snapshot and never blocks or is blocked), and commits to one table form a single linear history. For row-level writes Iceberg Java defaults to serializable validation for delete, update and merge. Core Iceberg has no multi-table transaction: each table commits on its own. The REST catalog spec defines a /transactions/commit endpoint for atomic commits across tables, which a catalog may implement, and Nessie offers commits that span tables on one branch.

Incident

Symptom. The mutual fund's NAV inputs table shows two copies of 13 October holdings for one scheme, and the computed NAV per unit is wrong. Diagnosis. The load task's commit call timed out at a load balancer (HTTP 504). The REST spec treats 500, 502 and 504 on commit as CommitStateUnknown: the commit may or may not have landed. The orchestrator retried the whole task, which appended the same rows again. The $snapshots table shows two append snapshots a few seconds apart with identical record counts. Fix. Roll back to the snapshot before the duplicate, then make the load idempotent: overwrite that date's partition, or MERGE on the holding key, or stamp each commit's summary with a run ID and check for it before appending. Lesson. A commit with an unknown outcome must be checked before any retry. The Iceberg Java client deliberately keeps the written files in this state because the commit may have succeeded.

Snapshots, time travel, rollback, branches and tags

Because every commit produces a new snapshot and old files stay until they are expired, you can read the table as it was at any retained snapshot. That is time travel.

-- Spark SQL
SELECT * FROM mf.nav_inputs VERSION AS OF 8812034412233;
SELECT * FROM mf.nav_inputs TIMESTAMP AS OF '2026-09-30 23:59:59';
-- Trino
SELECT * FROM mf.nav_inputs FOR VERSION AS OF 8812034412233;
SELECT * FROM mf.nav_inputs FOR TIMESTAMP AS OF TIMESTAMP '2026-09-30 23:59:59 Asia/Kolkata';

Rollback moves the table's current snapshot back to an earlier one, for example after a bad load: in Spark, CALL lake.system.rollback_to_snapshot('mf.nav_inputs', 8812034412233). It is a metadata commit; no data is copied.

Iceberg also keeps named references to snapshots. A tag is a fixed name for one snapshot, such as eom-2026-09, with its own retention, so the month-end state survives routine snapshot expiry. A branch is a movable name for a line of snapshots; main is the branch everyone reads by default. Branches carry their own retention settings (minimum snapshots to keep, maximum snapshot age, maximum age of the reference itself).

-- keep the September month-end state for a year (Spark SQL)
ALTER TABLE mf.nav_daily CREATE TAG `eom-2026-09` AS OF VERSION 8812034412233 RETAIN 365 DAYS;
-- an audit branch retained for 7 days (RETAIN sets the branch's maximum age; snapshot expiry removes it after that)
ALTER TABLE risk.positions_eod CREATE BRANCH `audit-20261013` RETAIN 7 DAYS;

Write-audit-publish

Write-audit-publish (WAP) is a pattern for keeping bad data away from readers: write the new data somewhere readers do not look, run checks on it, and publish only if the checks pass. Iceberg supports it two ways.

  • Branch style. Set write.wap.enabled=true, create an audit branch, point the writer at it with spark.wap.branch, validate the branch, then move main to the branch head with CALL lake.system.fast_forward('risk.positions_eod', 'main', 'audit-20261013').
  • Staged-snapshot style. With spark.wap.id set, a write creates a snapshot that is not made current. After validation, publish_changes (or cherrypick_snapshot) makes it current. Only append and dynamic-overwrite snapshots can be published this way.

Schema evolution by field IDs

Every column in an Iceberg schema has a field ID, an integer assigned when the column is created and never reused. Iceberg writers store these IDs inside each Parquet file's schema, and readers match file columns to table columns by that ID alone. That one rule makes the following changes metadata-only, with no data rewritten:

  • Add a column (old files read it as null, or as its default in v3).
  • Drop a column (the bytes stay in old files until they are rewritten; readers ignore them).
  • Rename a column or nested field.
  • Reorder columns.
  • Widen a type: int to long, float to double, decimal(P,S) to a larger P with the same scale. Format v3 also allows date to timestamp or timestamp_ns.

Format v3 adds default values: an initial-default that old rows read for a newly added column, and a write-default used when a writer omits it. Files that were written without field IDs (for example Parquet from an old Hive table brought in with add_files) need a name mapping, a table property that maps column names to IDs.

Common mistake

Dropping a column and adding a new one with the same name to "reset" it. The new column gets a new field ID, so every existing row reads null for it, and the old values are still sitting in the old files. The reverse also bites: dropping investor_pan from a mutual fund table does not erase anyone's PAN (the Indian tax identifier). To remove personal data you must rewrite the affected files, expire the snapshots that reference the old files, and let orphan cleanup delete them.

Hidden partitioning and partition evolution

In Iceberg a partition spec is a list of partition transforms, functions that derive a partition value from a column. Iceberg computes the value on write, stores it in the manifest, and converts query filters on the source column into partition filters. Users filter on ts and never see a trade_date partition column. That is hidden partitioning.

Partition evolution means changing the spec on a live table. Each change creates a new spec with a new ID. Existing files keep the spec they were written with, new files use the new one, and the planner evaluates each manifest against its own spec (Iceberg calls this split planning). Nothing is rewritten unless you choose to compact old data into the new layout.

-- Spark SQL: ticks grew, so move from daily to hourly partitions from now on
ALTER TABLE markets.fo_ticks REPLACE PARTITION FIELD ts_day WITH hours(ts);
-- give the planner a sort order to keep file statistics tight
ALTER TABLE markets.fo_ticks WRITE ORDERED BY underlying, contract, ts;

How fine to partition is a judgement call. My rule of thumb, derived from the 512 MB default target file size: if a partition would receive less than one target-size file of data per load cycle, it is too fine, and the sort order should do the rest of the pruning. A daily NAV table for a handful of schemes is a few thousand rows a year and should not be partitioned at all.

Field notes
  • Engines spell bucket differently. Spark writes bucket(16, underlying); Trino's table property is partitioning = ARRAY['day(ts)', 'bucket(underlying, 16)'] with the arguments reversed.
  • Changing the number of buckets is a partition evolution. Old files keep the old bucket count, so a lookup by key may have to check both layouts until old data is rewritten.
  • Partition on what queries filter by, sort on what they filter by next. For ticks that is usually time first, then underlying or symbol.
  • Trino limits how many partitions one writer task handles (iceberg.max-partitions-per-writer, default 100). A backfill that touches a year of daily partitions in one INSERT can fail on this limit.
Incident

Symptom. Simple queries on the options tick table spend most of their time in planning, and the object store reports millions of tiny objects under one table. Diagnosis. The table was partitioned by day(ts) and identity(contract). Thousands of option contracts trade each day, many with few ticks, so each load cycle wrote one small file per contract per partition. Manifests grew with every file, and planning read them all. Fix. Evolve the spec to day(ts) plus bucket(16, underlying), set a sort order of underlying, contract and ts, and compact recent partitions into the new spec with the rewrite job's output spec option. Lesson. High-cardinality columns belong in a bucket transform or in the sort order. Identity partitioning on them recreates the small-files problem inside the metadata.

Row-level changes: copy-on-write, merge-on-read and three kinds of delete

Data files are immutable, so changing one row needs a strategy. A trade is cancelled, a price is corrected, a loan prepays. Iceberg offers two families.

  • Copy-on-write (CoW): rewrite every data file that contains an affected row, minus the deleted rows or with updated values. Writes are expensive (a 512 MB file is rewritten to change one row); reads cost nothing extra. It is the Iceberg Java default for delete, update and merge (write.delete.mode, write.update.mode, write.merge.mode).
  • Merge-on-read (MoR): leave the data file alone and write a small delete record; readers merge the two at query time. Writes are cheap; reads pay until compaction folds the deletes in.

MoR has three encodings of "this row is gone".

Sequence numbers decide which deletes apply to which files. A position delete or DV applies to data files with a sequence number less than or equal to its own; an equality delete applies only to data files with a strictly smaller sequence number. All three apply only within their own partition, with one exception: an equality delete stored with an unpartitioned spec applies to the whole table. That is why a row re-inserted after an equality delete survives. It is also why the compaction job, by default, commits its new files with the sequence number of the snapshot it started from (use-starting-sequence-number): equality deletes committed while it ran still apply to the compacted rows.

Field notes
  • Choose per table. Append-only ticks need neither mode. EOD positions with daily whole-partition reloads suit INSERT OVERWRITE. Trade corrections a few times a day suit MoR plus nightly compaction. A table updated row by row all day long belongs in Postgres or in a primary-key table of the massively parallel processing (MPP) engine, with periodic export to Iceberg.
  • MoR moves cost from writers to every reader. Watch the count of delete files per partition in $files (content 1 is position deletes, 2 is equality deletes) and compact before readers feel it.
  • Equality deletes are the most expensive to read. The v4 draft bans writing new ones, a clear signal that the community is moving away from them.

Format versions: what v3 adds and what v4 proposes

A table's format version (property format-version) says which spec rules its metadata follows. v1 covered analytic tables, v2 added row-level deletes and is the Java default since Iceberg 1.4.0, and v3 extends types and capabilities. An engine that does not understand a table's version must refuse to read it.

Iceberg, Delta Lake and Hudi

Putting it together

Senior lens

Iceberg is a protocol between engines, and the table is only as correct as its least careful writer. That drives four decisions. First, pick the format version and features by the weakest engine that must write, which in Oct 2026 probably means v2 for shared tables. Second, give each table one owning writer pipeline and let other engines read, because concurrent writers from different engines multiply commit conflicts and semantic surprises. Third, treat metadata as the new bottleneck: the small-files problem has moved from HDFS NameNode memory into manifests and metadata files, and it is paid for in planning time and maintenance compute. Fourth, keep row-at-a-time work out of Iceberg: positions updated per trade belong in Postgres or an MPP primary-key table, with Iceberg receiving batched snapshots.

Common mistake

Treating an Iceberg table like an OLTP table: committing every tick batch every few seconds, or updating single rows as trades arrive. Each commit is a snapshot plus new metadata files, so this creates thousands of snapshots a day, tiny files and growing metadata. Buffer in the MPP engine or a queue and commit to Iceberg every few minutes, or at least once per load cycle.

"I haven't run Iceberg in production, so let me explain how I reason about it. Iceberg turns a table into a tree of immutable files: a metadata file per version, a manifest list per snapshot, and manifests that carry per-file partition values and column statistics. A query walks that tree and prunes at each level, so it never lists directories. A commit writes new files and then does one compare-and-swap of the table's pointer in the catalog, which gives readers snapshot isolation and writers optimistic concurrency with retries. On top of that you get time travel, rollback, branches for write-audit-publish, schema evolution by field ID and partition evolution without rewrites. I'd keep shared tables on format v2 until every engine in the POC handles v3, give each table a single owning writer, and choose copy-on-write or merge-on-read per table based on how often rows change."

Running Iceberg in production

An Iceberg table decays as it is used: every commit adds files and metadata, and nothing is removed until a maintenance job removes it. Running Iceberg well is mostly running those jobs on a schedule, sizing them, and watching the few numbers that say a table needs attention. On a managed service someone else does this; on a self-hosted lake it is a platform service the data team owns from day one.

Why tables decay

The small-files problem is the core of it: many files far below the target size. Each file costs a manifest entry at planning time, an object open and footer read at query time, and a request against the object store. Small files come from frequent appends (an ingestion job committing every few seconds), from over-fine partitions, and from merge-on-read writes that add delete files. Snapshots pile up for a related reason: every commit keeps the previous state alive for time travel until it is expired.

The maintenance jobs

Expire snapshots

Snapshot expiry removes old snapshots from the table metadata and then deletes every data, delete and manifest file that no retained snapshot, branch or tag still references. It is how storage is ever freed. Java defaults: expire snapshots older than 5 days (history.expire.max-snapshot-age-ms) but always keep at least 1 (history.expire.min-snapshots-to-keep). Branches and tags carry their own retention; the main branch never expires. Setting gc.enabled=false blocks garbage collection altogether (snapshot expiry and orphan removal refuse to run), which you want on tables that share files with another table (for example one created by Iceberg's snapshot or migrate procedures).

-- Spark: keep 7 days, but never fewer than the last 50 snapshots
CALL lake.system.expire_snapshots(
  table => 'markets.fo_ticks',
  older_than => TIMESTAMP '2026-10-07 00:00:00',
  retain_last => 50,
  stream_results => true);
-- Trino: retention must be at least iceberg.expire-snapshots.min-retention (default 7d)
ALTER TABLE markets.fo_ticks EXECUTE expire_snapshots(retention_threshold => '7d');

A related setting cleans old metadata files. Each commit leaves the previous metadata.json behind; with write.metadata.delete-after-commit.enabled=true the writer deletes the oldest tracked one after each commit, keeping write.metadata.previous-versions-max (default 100). The default is false, so tables that never set it accumulate one metadata file per commit forever.

Remove orphan files

An orphan file is a file under the table's location that no metadata references: output of a failed or killed write, or a metadata file that dropped out of the tracked log. remove_orphan_files lists everything under the table location, compares it with every file referenced by any metadata, and deletes unreferenced files older than a threshold. The threshold is the safety mechanism: a file being written by a job that has not committed yet is indistinguishable from garbage, except by age. Defaults: 3 days in Spark (older_than; the SQL procedure also refuses any window shorter than 24 hours, although the Java action API does not check), a 7-day minimum in Trino (iceberg.remove-orphan-files.min-retention), 7 days in StarRocks, 72 hours in SeaweedFS's maintenance worker.

-- Spark: always dry-run first and read the list
CALL lake.system.remove_orphan_files(table => 'markets.fo_ticks', dry_run => true);
-- Trino
ALTER TABLE markets.fo_ticks EXECUTE remove_orphan_files(retention_threshold => '7d');

Rewrite data files (compaction)

Compaction rewrites groups of files into fewer, larger, better-ordered files and, on the way, applies pending deletes. Spark's rewrite_data_files has two strategies: bin-pack (the default: combine small files without reordering rows) and sort (rewrite in the table's sort order or a given one). The sort strategy also accepts multi-column orderings, zorder(...) or hilbert(...) (z-order and Hilbert curves), which interleave several columns so filters on any of them prune reasonably well.

-- Spark: compact and sort yesterday's tick partitions, committing in pieces
CALL lake.system.rewrite_data_files(
  table => 'markets.fo_ticks',
  strategy => 'sort',
  sort_order => 'underlying ASC NULLS LAST, contract ASC NULLS LAST, ts ASC NULLS LAST',
  where => 'ts >= TIMESTAMP "2026-10-13 00:00:00" AND ts < TIMESTAMP "2026-10-14 00:00:00"',
  options => map('partial-progress.enabled', 'true', 'max-concurrent-file-group-rewrites', '4'));
-- Trino: bin-pack files under 128 MB, only for recent data
ALTER TABLE markets.fo_ticks EXECUTE optimize(file_size_threshold => '128MB')
WHERE CAST(ts AS DATE) >= DATE '2026-10-12';

The options worth knowing, with Spark defaults: a file is a candidate if it is under 75% of target size (min-file-size-bytes) or over 180% (max-file-size-bytes); a group with 5 or more files is rewritten regardless (min-input-files); one file group holds at most 100 GB (max-file-group-size-bytes); 5 groups run at once (max-concurrent-file-group-rewrites); partial-progress.enabled is false, so by default the whole job commits once at the end and one failure loses everything; delete-ratio-threshold is 0.3, so a file with 30% or more of its rows deleted becomes a rewrite candidate; output-spec-id lets compaction move old data into a newer partition spec.

Rewrite manifests, position deletes and the rest

  • Rewrite manifests regroups manifest entries so each manifest covers a narrow partition range, which helps planning when many small fast-append manifests exist or when the write order differs from the query order (Spark rewrite_manifests, Trino optimize_manifests). Automatic merging on write is on by default (commit.manifest-merge.enabled, merging once 100 manifests accumulate, into manifests of about 8 MB).
  • Rewrite position delete files compacts many small position delete files into fewer and drops entries that point at files no longer live (Spark rewrite_position_delete_files).
  • Remove dangling deletes drops whole delete files that no longer apply to any live data file. It is a Java action with no SQL procedure; compaction can do it with remove-dangling-deletes.
  • Compute statistics writes distinct-value sketches into a Puffin file for cost-based optimizers (Spark compute_table_stats; Trino ANALYZE, which also collects extended statistics on write by default).
Field notes
  • Compaction increases storage at first. The small files it replaced stay on disk until the snapshots that reference them expire, so a table compacted daily with a 7-day expiry carries roughly a week of pre-compaction copies of its recent data.
  • Expiry and orphan jobs gather file paths on the Spark driver. For large tables set stream_results => true, which the Iceberg docs recommend to avoid driver out-of-memory failures.
  • Orphan detection compares path strings. If metadata says s3a://lake-silver/... and the listing returns s3://lake-silver/..., every file looks orphaned. Spark treats s3a and s3n as s3 by default (equal_schemes) and stops with an error on other prefix mismatches (prefix_mismatch_mode ERROR). Never change that to DELETE to make an error go away.
  • Several Spark procedures (the rollback, cherry-pick and publish family, and rewrite_manifests) invalidate cached Spark plans that reference the table, so long-running notebooks may replan after they run.

Scheduling maintenance with Prefect

Prefect is a Python orchestrator worth considering. A flow is a decorated Python function, a task is a unit inside it with its own retries and state, and a deployment runs a flow on a schedule. Prefect also has global concurrency limits, named slots that code must occupy before running, which is the simplest way to stop ingestion and maintenance from writing the same table at once.

A reasonable order for one table, every night after its last load (my judgement, following the dependencies between jobs):

  1. Compact the partitions that stopped changing (for ticks, yesterday; for positions, dates outside the correction window), applying deletes.
  2. Expire snapshots according to the table's retention, after tagging any month-end snapshot.
  3. Rewrite manifests if the manifest count crossed a threshold.
  4. Recompute statistics for tables used in joins.
  5. Weekly, not nightly: remove orphan files with a window longer than the longest job.
  6. Read health metrics and alert.

from datetime import date, timedelta
import trino
from prefect import flow, task
from prefect.concurrency.sync import concurrency

def run_sql(sql: str):
    # authentication omitted; in practice the service account's credentials come from a secrets store
    conn = trino.dbapi.connect(host="trino.lake.internal", port=8080,
                               user="svc-iceberg-maint", catalog="lake")
    cur = conn.cursor()
    cur.execute(sql)
    return cur.fetchall()

@task
def compact(table: str, since: date):
    # ingestion flows occupy the same named limit, so they never commit to this table at the same time
    with concurrency(f"iceberg-write-{table}", occupy=1):
        return run_sql(f"ALTER TABLE {table} EXECUTE optimize(file_size_threshold => '128MB') "
                       f"WHERE CAST(ts AS DATE) >= DATE '{since.isoformat()}'")

@task
def expire(table: str, keep: str):
    with concurrency(f"iceberg-write-{table}", occupy=1):
        return run_sql(f"ALTER TABLE {table} EXECUTE expire_snapshots(retention_threshold => '{keep}')")

@task
def health(table: str):
    schema, name = table.split(".")
    return run_sql(f"""SELECT count(*) AS files,
                              avg(file_size_in_bytes) / 1048576 AS avg_mb,
                              count_if(content = 1) AS position_delete_files,
                              count_if(content = 2) AS equality_delete_files
                       FROM lake.{schema}."{name}$files" """)

@flow
def nightly_iceberg_maintenance():
    since = date.today() - timedelta(days=2)
    for table in ["markets.fo_ticks", "markets.eq_ticks"]:
        compact(table, since)
        expire(table, "7d")
        health(table)

if __name__ == "__main__":
    nightly_iceberg_maintenance.serve(name="iceberg-nightly", cron="30 1 * * *")

The named concurrency limits must exist before the flow runs (created once with prefect gcl create <name> --limit 1), and every ingestion flow for the table must occupy the same limit, or the guard does nothing. By default a missing limit only logs a warning and the code runs unguarded; pass strict=True to concurrency() to make it fail instead. Each job is safe to rerun: compaction and expiry are commits that either land or do not, and orphan removal only deletes files older than its window. That property matters more than the code, because the orchestrator will retry.

Incidents teams often hit

Incident

Symptom. Nightly compaction of risk.positions_eod fails most nights with a validation error about conflicting files, and the evening correction job sometimes fails with the same kind of error. Commit retries do not help here: a retry only rebases onto the new state, and a failed validation ends the job. Diagnosis. Compaction rewrites the last 7 days of trade_date partitions while corrections run MERGE into the same recent dates all evening. Each commit changes files the other one read, so serializable validation rejects whichever commits second. Fix. Compact only partitions outside the correction window (older than two business days), turn on partial-progress.enabled so finished file groups commit, and make both jobs occupy the same Prefect concurrency limit for the table. Lesson. Commit conflicts are a scheduling and partitioning problem. Writers that never touch the same files never conflict.

Incident

Symptom. Three weeks after go-live, tick ingestion commits that used to take a fraction of a second take several seconds, and every query on the table spends seconds in planning. The metadata/ prefix holds hundreds of thousands of objects. Diagnosis. The loader commits every 10 seconds, which is 8,640 commits a day. Snapshot expiry was never scheduled, write.metadata.delete-after-commit.enabled was false, and each fast append added a manifest. The metadata file carries an entry for every retained snapshot and is rewritten on every commit, so commit and planning cost grew with table age. Fix. Commit once a minute or less (buffer in the MPP engine if fresher data is needed), expire snapshots hourly with a short retention, turn on metadata deletion after commit, rewrite manifests, then run orphan cleanup once to remove the untracked metadata files. Lesson. Commit frequency is a design parameter with a compounding metadata cost.

Incident

Symptom. A backfill of a year of MCX history commits successfully, and within minutes queries on the backfilled months fail with object-not-found (404) errors. Diagnosis. Earlier that afternoon an engineer ran Iceberg's DeleteOrphanFiles Spark action from a notebook with olderThan set to one hour to reclaim space. (The SQL procedure remove_orphan_files would have refused a window under 24 hours; the action API has no such check.) The backfill had been writing data files for six hours without committing, so no metadata referenced them; they looked exactly like orphans and were deleted. The backfill's commit then referenced files that no longer existed. Fix. Roll the table back to the snapshot before the backfill and rerun it. If bucket versioning is on, the deleted objects can be restored instead. Run orphan removal only through a wrapper whose older_than can never be shorter than 3 days or the longest job's runtime, whichever is greater, keep ad hoc use of the raw action out of notebooks, and run a dry run first. Lesson. Orphan detection cannot tell an abandoned file from an uncommitted one; only age can. Trino's 7-day minimum exists for this reason.

Incident

Symptom. A positions table kept current by change data capture (CDC) from the Postgres position-keeping system goes from second-level to minute-level reads over two weeks. $files shows thousands of small equality delete files. Diagnosis. The CDC writer runs in upsert mode and writes an equality delete keyed on position_id at every checkpoint. Every read must load those deletes and check them against every older data file in the same partition, and this table is unpartitioned, so each delete applies to the whole table. Nobody compacts it. Fix. Schedule frequent compaction that applies deletes (rewrite data files with a delete-ratio or delete-count threshold, and remove dangling deletes), partition the table so deletes are scoped, and consider serving current-state reads from the MPP engine's primary-key table while Iceberg receives periodic snapshots. Lesson. Equality deletes save the writer work and charge it to every reader until compaction pays it off. Budget that compaction before choosing CDC into Iceberg.

Incident

Symptom. An auditor asks for the exact position set used to strike the 31 March NAV. Time travel to that date fails because the oldest snapshot the table still holds is a few days old. Diagnosis. Nightly expire_snapshots runs with the 5-day default. Time travel only reaches retained snapshots, and the files March referenced were deleted with them. The opposite failure is also common: a team raises retention to 90 days "for time travel", and storage grows sharply because every compaction's replaced files and every overwrite's old files are kept for 90 days. Fix. Rebuild March from bronze source files if they still exist. Going forward, tag month-end and quarter-end snapshots with a retention set by the compliance policy, keep routine expiry short, and model the as-of dimension in the data (business date plus load timestamp) for anything that must be reproducible for years. Lesson. Snapshot retention is an operational window measured in days. Regulatory history needs tags or an explicit history design, and the requirement should come from compliance in writing.

Iceberg catalogs

A catalog is the small service that turns a table name into the table's current state and makes every commit atomic. Every engine, pipeline and AI agent on-prem would pass through it, so it is also where namespaces, permissions, storage credentials and audit records live. It holds very little data, yet it is one of the few lake decisions that is hard to reverse, so it deserves a deliberate choice.

What a catalog does

In Iceberg terms a catalog is any component that can answer "where is the current metadata file of risk.positions_eod?" and can change that answer atomically. Production catalogs do six jobs.

  1. Name to pointer. It maps namespace.table to the location of the current metadata.json. A namespace is a folder-like grouping of tables, for example markets, risk, credit, mf and infra for the data domains.
  2. Atomic commits. It performs the compare-and-swap that makes a commit visible, so it is the one place where concurrent writers to a table are serialized.
  3. Lifecycle. It creates, drops and renames tables, views and namespaces, and can register an existing metadata file as a table (register_table) or, since Iceberg 1.12, unregister one through the REST API without deleting its files.
  4. Authentication and authorization. It decides who is calling (usually an OAuth2 or OpenID Connect (OIDC) token from an identity provider) and what they may do on which catalog, namespace, table or view.
  5. Credential vending. Instead of giving every engine a long-lived object-store key for the whole bucket, the catalog can hand out short-lived credentials scoped to one table's location (vended credentials, usually minted through the store's Security Token Service (STS) API) or sign each storage request itself (remote signing).
  6. Audit. It can record who loaded, created, committed to or granted access on which table and when; some catalogs also accept the scan metrics engines report.
Field notes
  • A catalog sees table loads and commits, never the query. It knows that a principal loaded mf.investor_holdings and received read credentials; it does not know which rows or columns were read. Row filters and column masks must be enforced by a query engine.
  • The catalog is on the commit path, not the data path. If it is down, no commits and no new table loads happen; queries already planned keep reading files, and engines with cached metadata may serve stale reads for a short while.
  • Engines cache catalog answers. Spark's Iceberg catalog caches each loaded table and, by default, drops an entry only after 30 seconds without access (cache.expiration-interval-ms). A session that queries a table more often than that can keep reading the snapshot it first loaded and miss other writers' commits until it runs REFRESH TABLE or the entry goes idle. Dashboards that must reflect the EOD load immediately need a refresh, a shorter expiry or the cache turned off.
  • Vended credentials depend on the object store offering an STS API. The Polaris docs, for example, describe a stsUnavailable flag for S3-compatible stores without STS (such as a Ceph RGW deployment with STS not enabled): vending is skipped and clients authenticate to the store directly. Lakekeeper, when a client sends no delegation header or accepts both methods, tries vending first and falls back to remote signing when vending is not enabled for the storage profile. Test this with the real store early.

The REST catalog spec

The REST catalog spec is an OpenAPI document in the Iceberg repository (open-api/rest-catalog-open-api.yaml) that defines HTTP endpoints for everything a catalog does. Any server that implements it works with any client that speaks it, much as any S3-compatible store works with any S3 client.

The responses that matter operationally: 409 means a requirement failed (another writer moved the table) and the client may retry; 500, 502 and 504 are defined as CommitStateUnknown, meaning the commit may or may not have been applied; a server must answer 400 if it receives a requirement or update type it does not know. Clients opt into credential delegation with the header X-Iceberg-Access-Delegation: vended-credentials or remote-signing (the server may supply either, or neither), and can send an optional Idempotency-Key so that a server which supports it does not apply a retried request twice.

Why this decouples engines from catalogs: before REST, each engine needed its own client for each catalog (Thrift for HMS, the AWS SDK for Glue, a JDBC driver, a Nessie client), and the commit logic ran inside every engine. With REST the engine needs one client and a URL; commit checks, authorization and credential handling move to the server. The team can change catalog implementation later by re-registering tables, without touching engine code beyond a URI and credentials.

Choosing a catalog

The requirements from the brief: self-hosted, no vendor lock-in, several engines (an MPP database plus Python and probably Spark or Trino), compliance and audit, and later AI agents with governed access. My recommendation, which a POC should confirm:

  • Use the REST protocol. It is the only option that keeps engines and catalog independent and puts authorization, credential handling and audit in one place.
  • Short-list Apache Polaris and Lakekeeper, both persisted on a highly available Postgres the team already knows how to run. Polaris brings Apache governance and a conventional RBAC model; Lakekeeper brings OpenFGA's fine-grained, hierarchical permissions and a remote-signing fallback for stores without STS.
  • Keep the alternatives for specific needs. Nessie if atomic publication across many tables is a hard requirement; Gravitino if federating metadata from many non-Iceberg sources matters more; SeaweedFS's built-in catalog for a quick POC if SeaweedFS is the store, accepting that it couples catalog and storage; HMS only for Hive compatibility.

High availability

A reasonable default (my judgement): two or three stateless catalog replicas behind a load balancer; Postgres with a synchronous standby managed by a failover tool such as Patroni; continuous archiving of the write-ahead log (WAL) for point-in-time recovery to storage outside the lake. The catalog database is tiny, but losing it, or restoring it to an old point, changes what every table means.

AI agents

For internal AI agents, give each agent its own principal so every action is attributable, grant read-only roles on specific gold namespaces, and keep write privileges away from agents entirely. Prefer that agents query through the MPP engine, which can apply row filters and column masks and keeps a query log, over receiving vended file credentials, because file-level access exposes every column in those files. Audit is then a join of catalog events and engine query logs on the agent's identity.

Incidents teams often hit

Incident

Symptom. At 18:40 every EOD load fails with catalog errors (HTTP 503 or connection timeouts). Dashboards keep working for a few minutes, then new queries fail to load tables. Diagnosis. The catalog replicas are healthy, but the Postgres primary's disk is full: a replication slot left behind by a decommissioned standby has been retaining WAL for weeks. Without its database the catalog can neither read nor swap pointers, so the whole lake is read-mostly and write-nothing. Fix. Drop the stale slot, free space, confirm the standby, and replay the failed loads; idempotent loads make the replay safe. Lesson. The catalog database is tier-zero infrastructure. Monitor disk, replication lag, replication slots and connection pools, and design ingestion to buffer and retry when commits are refused.

Incident

Symptom. Trino shows positions up to 12 October while StarRocks shows 13 October for the same table. A week later Trino queries on that table fail with missing files. Diagnosis. During a migration the table was registered in the new REST catalog with register_table, pointing at the same metadata file, while the old Hive Metastore entry stayed. Writers moved to REST, so HMS's pointer froze at an old metadata file. Then snapshot expiry through REST deleted files that the stale HMS pointer still referenced. Fix. Choose one catalog of record, remove the table from the old catalog without purging data (a DROP TABLE with purge would delete the files), and point every engine at the catalog of record, or federate the old catalog read-only to it. Lesson. A table has exactly one catalog that accepts commits. Registering it in a second catalog creates a fork, and maintenance in one fork corrupts the other.

Incident

Symptom. After the catalog database is restored from the previous night's backup, the day's loads have vanished from every table, although their Parquet files are on the store. Diagnosis. The restore rolled each table's pointer back to the previous night's metadata file. The day's commits wrote metadata files that nothing points to any more. If orphan cleanup runs now with a short window, it will delete them. Fix. Freeze maintenance, find each table's newest metadata file under its metadata/ prefix, check its lineage, and re-register it before allowing writes. Then add WAL archiving so a future recovery loses seconds of commits. Lesson. The catalog's recovery point must be close to zero, and orphan and expiry windows must be longer than the time it takes to recover the catalog.

Common mistake

Handing every engine, notebook and agent one object-store key with access to the whole bucket because the catalog's credential vending is fiddly to set up. That bypasses every permission the catalog defines, makes audit impossible, and turns a leaked notebook into a leak of the mutual fund's investor records. A close second: using a JDBC catalog straight from every engine because it is simplest, which spreads database credentials everywhere and leaves no place to enforce permissions.

Putting it together

Senior lens

The catalog is the control plane of the lake, so choose the protocol first and the product second. Standardizing on Iceberg REST keeps the exit open: tables can be re-registered in another implementation, and engines only change a URL. Avoid implementation-specific features (non-main branches in Nessie, product-specific policy objects) unless a requirement needs them. Run the catalog on Postgres because the team can operate Postgres well, and spend the effort on recovery: synchronous replication, WAL archiving and a tested runbook for re-registering tables. For AI agents the catalog is necessary and insufficient: it gives identity, coarse grants and an audit trail, while row- and column-level control and query logging come from the engine in front of it. Finally, ownership: one team owns the catalog, the grant model and the onboarding scripts, and every new domain or agent goes through them.
