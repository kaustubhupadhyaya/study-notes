    The whiteboard: design a self-hosted lakehouse

    This is the question most likely to take half of a design interview: "Design a self-hosted lakehouse and analytical database platform, under 40 TB, so AI agents can later get governed access." The interviewer wants to see you ask the right questions, draw clear layers, pick each component for a reason you can defend, name the runner-up, and say what you would build first. This section walks the answer in the order you would speak it at the whiteboard.

    How the interviewer runs this question

    A system design interview is an open question where you sketch an architecture and the interviewer pushes on your choices. For a senior architect or a CTO, the scoring usually rests on five things: did you clarify requirements before drawing, are the layers clean, can you explain each trade-off, do you think about running it on day 2 (the long period after launch), and do you keep security and compliance in view. Nobody expects one correct answer.

    A time plan that works for a 45 to 60 minute slot (my suggestion):

    1. Clarify, 5 minutes. Ask the questions in the next subsection and write the answers in a corner of the board.
    2. Draw the layers, 10 minutes. Sources, ingestion, storage, tables, engines, consumers, governance, observability.
    3. Choose components, 15 minutes. One pick and one runner-up per layer, with the reason and what would flip the decision.
    4. Day 2 and failures, 10 minutes. What you monitor, what breaks first, backup and disaster recovery.
    5. First 90 days, 5 minutes. What you build first and how you prove it works.

    A few terms first, so the rest reads cleanly. A data lake is a store of files (here, on object storage) that many tools can read. A table format is a set of rules for metadata files that turns a pile of data files into a table with a schema, versions and atomic commits. Apache Iceberg is the table format on the shortlist. A lakehouse is the combination: open files on object storage, a table format on top, and one or more query engines that read the same tables. The 2021 CIDR paper that set out the idea argues that this removes the separate copy most firms keep in a warehouse. An MPP database (massively parallel processing) runs one query on many nodes at once; Redshift and Snowflake are MPP systems you have used, and ClickHouse, Doris and StarRocks are the self-hosted ones on the shortlist.

    Sources: Lakehouse, CIDR 2021

    Walk it left to right:

    • Sources. Exchange and vendor market data (ticks, quotes, end-of-day prices, corporate actions), the order and portfolio management systems that hold trades and positions, risk outputs, structured-credit loan tapes and cash-flow files, PDFs such as loan agreements and trustee reports, toll-road operator reports, and later the mutual fund's daily NAV (net asset value) inputs and investor records.
    • Ingestion and orchestration. Prefect flows pull or receive each source, land the raw file unchanged, validate it, and write typed Iceberg tables.
    • Object store. One S3-compatible store holds everything: raw files in a landing bucket, cleaned tables in silver, business-ready tables in gold. An S3-compatible store is a server that speaks the Amazon S3 HTTP API, so every engine that reads S3 can read it.
    • Catalog. An Iceberg catalog stores, for each table, a pointer to the table's current metadata file. A REST catalog is a catalog that engines reach through the HTTP API defined by the Iceberg project's OpenAPI file, so any engine that speaks it can use any catalog that implements it. Its own state lives in Postgres.
    • Engines. A serving engine answers dashboards and agents fast. Batch compute (Spark, or PyIceberg and DuckDB for small jobs) runs transformations and table maintenance.
    • Consumers. PM dashboards, the risk team, fund accounting for NAV, research.
    • Governance and agents. Agents never get raw storage credentials. They call a gateway that exposes a small set of tools over curated views, under their own identity, with every call audited.
    • Observability. Metrics, logs and alerts for every layer, on infrastructure the team controls.

    Two more definitions you will use constantly. A snapshot in Iceberg is the complete state of a table after one commit; old snapshots enable time travel ("show me positions as they were at 18:00 yesterday") until they are expired. Compaction is the background job that rewrites many small data files into fewer large ones so queries open fewer files.

    The object store, now that MinIO's community edition is archived

    Most self-hosted lakehouse tutorials from 2022 to 2025 used MinIO, so the interviewer may expect it. Know what changed.

    As of Oct 2026

    MinIO removed admin features from the community console in May 2025, stopped publishing pre-built binaries and Docker images in October 2025 ("distributed as source code only"), put the repository in maintenance mode in December 2025, and the GitHub repository now shows as archived (April 2026) with a README that says it is no longer maintained and points to the commercial AIStor product. The code is AGPLv3. The last community image is RELEASE.2025-09-07T16-13-09Z. Third-party rebuilds exist (Chainguard's cgr.dev/chainguard/minio and the pgsty/minio fork).

    My pick and why. Ceph RGW, with an erasure-coding profile of 4 data and 2 parity chunks spread across hosts. Erasure coding (EC) splits each object into k data chunks and m parity chunks so that any m chunks can be lost; 4+2 survives two lost chunks at 1.5 times the raw size, against 3 times for three full copies. Ceph's pieces, briefly: an OSD (object storage daemon) manages one drive; MONs (monitors) keep the cluster map by majority vote, so you run three or five; RGW (RADOS Gateway) is the stateless S3 front end you put behind a load balancer. The reason is maturity for a system of record, multisite replication for the DR site, and the fact that the team can buy support if it is small.

    Runner-up. SeaweedFS, if the team cannot staff Ceph. It is easier to reason about and its table buckets could even replace a separate catalog for a small team, but fewer engineers in the market have operated it, and that matters when you hire your second on-call engineer.

    Common mistake

    Choosing the object store from a throughput benchmark. At 40 TB almost any of these stores can saturate a few 25 GbE links. What separates them is how they behave when a drive dies at 10:00 on an expiry Thursday, how long a rebuild takes, how upgrades work, and whether you can hire someone who has done it before. Ask those questions in the proof of concept (POC), by pulling a drive under load.

    Table format and catalog

    Iceberg, on format v2 for now. The Iceberg spec has versions 1 to 3 complete. Version 3 adds deletion vectors (a compact bitmap of deleted rows), row lineage, the variant type, default column values and nanosecond timestamps. Those are useful for tick data with nanosecond exchange timestamps. But a table's format version is a promise to every reader, and upgrades are one-way. As of Oct 2026, Trino treats v3 as experimental (no row-level operations or OPTIMIZE on v3), ClickHouse supports v3 only partially, and the Java library still defaults to v2. My view: stay on v2 until every engine that must read a table reads v3, then upgrade table by table.

    Iceberg Java defaults worth saying aloud. Target data file 512 MB, Parquet row group 128 MB, zstd compression, and copy-on-write for deletes, updates and merges. Copy-on-write rewrites every data file that contains a changed row; merge-on-read writes small delete files instead and makes readers apply them. Positions tables that change all day suit merge-on-read with regular compaction; append-only tick tables need neither.

    The catalog. The catalog is the one component every read and every write passes through: an engine asks it where the current metadata file is, and a commit is a compare-and-swap of that pointer. If the catalog is down, nothing commits and most queries cannot plan. That makes it tier-0, with the same availability bar as the object store.

    Three ways an engine gets storage access through a catalog, worth defining because agents depend on them. With static keys, every engine holds a long-lived S3 key. With credential vending, the catalog checks the caller's permission on a table and returns short-lived credentials scoped to that table's path; on S3-compatible stores this needs the store to implement STS, which Ceph RGW does. With remote signing, the engine asks the catalog to sign each S3 request, so it never holds a key at all; Lakekeeper supports this. My pick is Polaris for its Apache governance and role model, with Lakekeeper as the close runner-up; I would run both in the POC for two weeks against StarRocks, Spark, PyIceberg and DuckDB (DuckDB writes Iceberg only through a REST catalog).

    Field notes
    • Iceberg cleans up nothing on its own by default. Snapshot expiry (Java default: snapshots older than 5 days, keep at least 1), orphan-file removal (default: files older than 3 days) and compaction are jobs you schedule and monitor.
    • Old metadata.json files are kept unless write.metadata.delete-after-commit.enabled is true; write.metadata.previous-versions-max defaults to 100. A table committed every minute accumulates them fast.
    • Iceberg's built-in encryption works only with Hive and REST catalogs and only for Parquet and Avro, and metadata.json stays unencrypted. Plan for that if the MF investor tables must be encrypted at the table level.
    • Registering the same metadata.json in two catalogs can corrupt a table, per the Iceberg docs. During a catalog migration, unregister from the old one first.

    The serving engine: StarRocks, Doris, ClickHouse or Trino

    Terms first. In StarRocks and Doris, the FE (frontend) holds metadata, accepts SQL connections and plans queries; you run three for a majority vote. The BE (backend) stores data on local disk and executes queries. A CN (compute node) in StarRocks is a BE without permanent data: it executes queries and caches hot data locally. Shared-nothing means each node owns a slice of the data on its own disks. Shared-data means the durable copy lives in shared object storage and compute nodes are stateless apart from their cache.

    Why StarRocks first. In shared-data mode it has only two node types, so there is no FoundationDB cluster to learn and back up. It reads Iceberg through an external catalog with the same cache, so the lake stays the source of truth. It has native tables for the few things that need sub-second answers, such as an intraday positions view. History helps you sound informed: StarRocks began in 2020 as a fork of Apache Doris and has rewritten much of the code since, so the two share concepts (FE, BE, tablets, bucketing) and differ in optimizer, execution and storage details.

    Why Doris is a close second. Its Iceberg write support is broader today (UPDATE, DELETE, MERGE), which matters if engineers want to correct positions in SQL. Its compute groups give documented BE-level isolation over one copy of data: each BE belongs to one group, and a group's queries run only on its own BEs. The cost is FoundationDB, one more distributed system with its own failure modes.

    Why ClickHouse is the runner-up for ticks only. MergeTree on local NVMe is excellent for time-series scans, such as "all NIFTY option trades for this expiry between 14:00 and 15:30, by strike". But the open-source build has no SharedMergeTree (that powers ClickHouse Cloud only), so true compute-storage separation is not available self-hosted; its Iceberg writes are beta and catalog integration is mostly read-only. If the main workload were tick research by a quant team, I would revisit this.

    Where Trino fits. Trino is a query engine with no storage, strong at federating many sources. It is a reasonable later addition for ad-hoc joins across the lake and operational databases. Its default retry-policy is NONE, so a lost worker fails the query.

    Incident

    Symptom. A few weeks after go-live, the team upgrades the positions table to Iceberg format v3 to get deletion vectors. Next morning a research notebook on Trino and a ClickHouse report both fail on that table, while StarRocks dashboards still work. Diagnosis. The format upgrade is one-way, and two of the readers support v3 only experimentally or partially. Nobody had an inventory of which engine reads which table. Fix. Write a v2 copy of the table under a new name (for example a CREATE TABLE AS SELECT in Spark with format-version 2) and move the affected readers to it; keep the v3 table for the engines that support it. Do not register the old v2 metadata.json as a second table: the Iceberg docs warn that two catalog entries over the same files can lose data or corrupt the table. Lesson. Keep a reader inventory per table and gate format upgrades on it, the same way you gate a schema change.

    Incident

    Symptom. At 10:40 on a weekday, every Prefect flow that writes Iceberg fails and half the dashboards show "table not found". Diagnosis. The catalog's Postgres ran as a single VM on a host that rebooted for a firmware update. With the catalog down, engines could not load table metadata unless it was already cached. Fix. Move catalog Postgres to a three-node high-availability setup with a synchronous standby, run at least two catalog replicas, and add the catalog to the change calendar as tier-0. Lesson. The catalog is small in bytes and huge in blast radius. Size its availability by blast radius.

    Shared-data or shared-nothing at under 40 TB

    Size does not force the decision: a few modern servers can hold 40 TB of flash. So argue from the other forces.

    My view: shared-data, because the lake in Iceberg is the system of record that every engine and later every agent reads, and because isolating the overnight risk batch, the morning dashboards and the agents from each other is worth more than the last few milliseconds. The design rule that follows: anything inside the engine's native tables must be derived and rebuildable from Iceberg, since you cannot BACKUP and RESTORE it in this mode. If a latency target were truly strict (say a sub-100 ms intraday screen), I would put that one workload on a small shared-nothing table set and keep everything else shared-data.

    Senior lens

    The decision that matters most here is organisational: how many distinct distributed systems a three-to-five person team can run well. Ceph, an MPP engine, a catalog, Postgres, Prefect and Kubernetes are already six. Each one added (Kafka, FoundationDB, Trino, ClickHouse Keeper) is another upgrade calendar, another failure mode and another skill to hire for. A senior keeps the count low in year one, buys support for the system of record, and writes down the conditions under which a new system earns its place. The second lever is open formats: if the data lives in Iceberg on an S3 API, the engine can be swapped later without a migration project, which is the practical meaning of "no vendor lock-in".

    Orchestration and ingestion

    Prefect in Airflow terms. A Prefect flow is a decorated Python function, the equivalent of a DAG. A task is a unit inside it. A deployment attaches a schedule and parameters to a flow. A work pool describes where runs execute (a process, Docker, Kubernetes), and a worker polls the pool and starts runs, much like the scheduler handing a KubernetesPodOperator task to a Kubernetes cluster. The self-hosted server stores state in a database; to run several API servers you need Postgres 14.9 or later, Redis for event messaging and a load balancer. Two run states to know: Late means the scheduled start passed without the run reaching Pending (15 seconds by default), and Crashed means the run failed because of infrastructure. The latest stable release is 3.8.8 (6 Oct 2026).

    Ingestion patterns by source. Every pattern below is idempotent: rerunning the same date produces the same table, using overwrite-by-partition or merge on a natural key, which is what lets on-call engineers rerun safely at 06:00.

    • A writer that commits once a minute through the NSE session makes 375 commits a day per table (09:15 to 15:30). That is fine for Iceberg if you compact and expire snapshots; it is a problem if you forget.

    Governance for AI agents, designed in from day one

    "internal AI agents" will put software agents in front of positions, P&L, loan documents and investor data. Treat each agent as a principal with an identity, the narrowest permissions that do its job, and a full audit trail. The layers, from the agent inward:

    1. Identity. Each agent has its own service identity in the identity provider, and every call also carries the human user it acts for. Without the second identity, audit logs say "the agent did it", which a compliance officer will not accept.
    2. A gateway with tools. The Model Context Protocol (MCP) is an open protocol through which an AI application calls tools exposed by a server. The gateway exposes a short list such as get_positions(fund, as_of), get_pnl(desk, date) or search_loan_documents(deal, query), each backed by a curated gold view, with row limits and timeouts. A free-form SQL tool, if offered at all, runs under a tightly scoped role.
    3. Engine permissions. RBAC (role-based access control) grants rights to roles; a row-level policy filters rows by who is asking (a desk sees only its book); column masking hides or hashes sensitive columns (an investor's PAN, India's tax identifier, or bank account). StarRocks gets row filters and masking through Apache Ranger; Doris has CREATE ROW POLICY and masks through Ranger.
    4. Catalog permissions. Catalog roles decide which namespaces and tables a principal can even load; the agent's principal never sees the investor namespace.

Answers carry an as-of timestamp and the source table, so a PM can see that "exposure to RELIANCE" came from the 18:00 snapshot.

    Back-of-envelope sizing, with every assumption stated

    After the design, a good interviewer asks "so how many servers?" This section works the arithmetic from "under 40 TB" to drives, nodes and network links, with each assumption labelled so you can swap in the real numbers. The point to show is method: the interviewer cares that you know which factors multiply and which failure cases set the floor, more than about the final count.

    The method in one picture

    Back-of-envelope sizing is a rough calculation done in a few minutes to get the order of magnitude right. You state assumptions, multiply through, and then check the result against failure cases. The chain:

    flowchart TD
  A["Logical data today: 40 TB"] --> B["Split by data type"]
  B --> C["Compress each type"]
  C --> D["Add layers: landing, silver, gold, AI"]
  D --> E["Add Iceberg snapshot and rewrite overhead"]
  E --> F["Grow for 3 years"]
  F --> G["Multiply by erasure coding 1.5x"]
  G --> H["Divide by 70 percent fill ceiling"]
  H --> I["Raw TB to install"]
  I --> J["Drives and nodes, checked against one node failure"]

    Two terms used below. Logical size is the size of the data as the user sees it, before durability copies. Raw size is what the drives must hold after erasure coding or replication. A rule of thumb is a practitioner's approximation; each one below says where it comes from, and each should be replaced by a measurement on the data during the POC.

    • Vendor ratios are measured on vendor data. Quote them as a starting range, never as a plan.

    Erasure coding 4+2 with one chunk per host needs at least 6 hosts; a 7th lets the cluster re-create lost chunks on a healthy host after a failure. So 7 storage nodes is the floor, set by the failure domain. Capacity then decides drives per node. Two options with 7.68 TB NVMe drives:

Option A held into year 3 is exactly the trap the 70% rule exists for: one node failure pushes survivors toward 90%, Ceph stops backfilling, and the cluster sits degraded while the next failure could lose data.

    Memory and CPU for storage nodes. Ceph's osd_memory_target defaults to 4 GiB per OSD, so three OSDs need about 12 GiB before the gateway, monitors and page cache; 128 GB per node is a comfortable choice (my judgement). Run three MONs on three of the seven nodes, and two or three RGW gateways behind a load balancer.

    Rebuild time, the number people forget. In year 3 each node holds about 82.0 / 7 = 11.7 TB of chunks. Rebuilding a lost chunk in 4+2 reads 4 surviving chunks, so recovering one node reads about 4 x 11.7 = 46.8 TB and writes 11.7 TB. If recovery is limited to 2 GB/s across the cluster during market hours (an assumption to protect queries), that is 46,800 / 2 = 23,400 seconds, about 6.5 hours of reduced redundancy. At 5 GB/s overnight it is about 2.6 hours. This is the real argument for NVMe, for 25 GbE, and for deciding the recovery priority in advance.

    Incident

    Symptom. A storage cluster that has crept to 81% raw usage loses one node to a failed motherboard. Six hours later Ceph reports OSDs as backfillfull, recovery stops, and health stays in warning with degraded placement groups for two days. Diagnosis. The survivors had to absorb one seventh of the data and crossed the 90% backfill threshold. Usage had grown past the planning ceiling because nobody owned the capacity forecast, and a snapshot-expiry job had been failing quietly, leaving old files in place. Fix. Run snapshot expiry and orphan removal to free space, install spare drives that were on the shelf, and only as a last resort raise the backfill ratio a little with someone watching. Lesson. The fill ceiling is a failure budget. Forecast against it monthly and alert at 70%, well before Ceph's own 85% warning.

    SLIs, SLOs and error budgets in plain words

    An SLI (service level indicator) is a measured number, such as "share of dashboard queries answered in under 2 seconds". An SLO (service level objective) is the target for that number over a window, such as "95% of them, each trading day". An SLA (service level agreement) is a promise with consequences, usually to a customer; an internal platform mostly needs SLOs. The error budget is the room the SLO leaves: a 99.9% availability SLO over a 30-day month allows 43.2 minutes of failure; counted only over market hours (about 22 days x 375 minutes = 8,250 minutes), it allows about 8 minutes. When the budget is spent, risky changes stop until it recovers.

    Capacity reviews

    Run one every month, in 30 minutes, with a fixed agenda:

    1. Storage. Raw use of the fullest OSD and of the cluster; growth by bucket and by Iceberg namespace; top 10 tables by growth; the date the forecast hits 70%.
    2. Order trigger. Order hardware when the 70% date minus the vendor's lead time minus a month of buffer arrives. With colo hardware this can be months ahead.
    3. Compute. CPU and memory p95 per compute group in market hours; spill; cache hit ratio against the hot-set size; queued queries.
    4. Metadata. Catalog database size and latency; FE heap; number of tables, partitions and files.
    5. Network. Peak link utilisation, especially during compaction and rebuilds; DR replication lag.

    Quarterly, add a load test with recorded production queries at 1.5 times the peak concurrency, and a DR drill.

    Upgrades without touching trading hours

    The calendar constrains everything. NSE trades 09:15 to 15:30 IST and MCX non-agricultural contracts trade until 23:30 or 23:55 IST, so the weekday window is roughly midnight to early morning, and weekends are better for anything risky. Freeze changes around month-end, quarter-end, expiry days and NAV deadlines.

    • Ceph. Rolling upgrades through the cephadm orchestrator (ceph orch upgrade), which restarts managers first, then monitors, then the other daemons (OSDs, gateways), each only when Ceph says the cluster will stay available. For planned host reboots such as OS or firmware patches, set noout so Ceph does not start moving data for a planned restart.
    • StarRocks. The docs say: upgrade BEs and CNs first, then the follower FEs, then the leader FE; they strongly recommend going one minor version at a time; run ALTER SYSTEM CREATE IMAGE between consecutive upgrades and wait for the image to reach every follower. Downgrade runs the other way round for node types: FEs first (followers, then the leader), then BEs and CNs, again one minor version at a time. A 4.1 cluster can be downgraded only to 4.0.6 or later. CNs restart with cold caches, so warm key tables before the open.
    • Iceberg. Library upgrades inside engines are routine; table format-version upgrades are one-way, so gate them on a reader inventory.
    • Catalog and Prefect. Back up Postgres before any schema migration; roll stateless replicas one at a time; pin client and server versions.
    • Staging. Keep a small staging copy (three storage nodes, one FE, one CN, one catalog) to rehearse every upgrade with production-like data.

    The subtle part is consistency between layers at the DR site. The catalog is replicated through Postgres, the files through RGW multisite, and the two lag differently. After a failover, a table pointer may name a metadata.json whose data files have not arrived yet. The DR runbook therefore checks each critical table: confirm its current metadata and manifests exist, and if not, roll the pointer back to the newest snapshot whose files are all present. Rehearse it quarterly, and time it, because that number is your real RTO.

    Field notes
    • Restore drills usually fail first on something small: a missing grant, a hard-coded endpoint, a secret that exists only at the primary site.
    • Versioned buckets keep every overwritten object. Without a lifecycle rule that expires noncurrent versions, the landing bucket quietly doubles.
    • Change one layer per maintenance window. When storage and engine change on the same night and something breaks, nobody can tell which change caused it.
    • After any CN restart, the cache hit ratio is the metric to watch for the next hour.
    Senior lens

    A senior turns "we have backups" into three tested numbers: RPO, RTO and the date of the last successful restore drill. They also notice cross-layer coupling: Iceberg maintenance settings (expiry age, orphan window) are part of the DR design, because they decide whether an older catalog state still has its files. And they make the engine disposable on purpose, keeping all truth in Iceberg, so the DR plan for StarRocks is "rebuild from the lake with a script we run every quarter", which is simpler and more reliable than backing up a system whose decoupled mode does not support it.

    Cost visibility when the hardware is already bought

    On-prem cost is mostly fixed: servers, colo space and power, support contracts and people. Visibility still matters, for two reasons: to justify the next purchase with evidence, and to find waste (a research job that fills the cache every weekend, an agent that scans two years of ticks to answer a one-day question). This is showback: reporting usage by team without billing them; chargeback actually bills.

    • Who ran it. One engine user or role per team and per agent, and resource groups or compute groups per workload.
    • Why it ran. A tag on every query: app, environment, run id, team or agent. ClickHouse has log_comment, which lands in system.query_log; for StarRocks and Doris, the user, role and resource group in the audit log carry most of it, and the gateway adds request ids.
    • What it cost. CPU-seconds and bytes scanned per query from the audit log, multiplied by a blended rate: annual cost of the compute group divided by (cores x hours in a year x target utilisation).
    • What it stores. Bytes per namespace and table from Iceberg's files metadata tables, and per bucket from RGW usage statistics.
    • What it orchestrates. Prefect run tags and durations per team.

    Sources: ClickHouse log_comment · Doris audit log

    On-call for a small platform team

    • Rota. A weekly primary and secondary. With three to five people, that is on call every few weeks, so the pager must be quiet enough to sleep through most nights.
    • Severity. Sev 1: trading, P&L or NAV affected. Sev 2: degraded with workaround. Sev 3: ticket.
    • Runbooks. One per alert, linked from the alert, written as steps a tired person can follow at 06:00.

    Incident drills across every layer

    These are realistic, typical scenarios of the kind teams running this stack often hit. Practise telling each one in under a minute: symptom, diagnosis, fix, lesson.

    Incident

    Symptom. At 10:05 on an expiry day the positions dashboard's p95 rises from about 1 s to 6 s, and Ceph reports degraded placement groups. Diagnosis. An NVMe drive failed at 09:58 and recovery started. During weekend maintenance someone had set osd_mclock_profile to high_recovery_ops to speed a rebalance and never reset it, so recovery is taking most of the drives' capacity, and every CN cache miss now waits on a busy store. Fix. Set the profile to high_client_ops for market hours (or back to the default, which is balanced in current releases), let recovery run faster after the MCX close, then replace the drive. Lesson. Decide the recovery policy per time window in advance, write it in the runbook, and alert when a cluster setting drifts from its baseline.

    Incident

    Symptom. From 02:10, every write from one rack's workers fails with HTTP 403 RequestTimeTooSkewed, and Ceph warns of clock skew on a monitor. Diagnosis. A firewall change cut that rack's NTP servers from their upstream, and clocks drifted. S3 signature version 4 rejects requests whose timestamp is off by more than about 15 minutes, and Ceph monitors tolerate only 0.05 s of drift by default. Fix. Restore time sync, configure several internal time sources per rack, and alert on offset well before either limit. Lesson. Time is a dependency of authentication and of consensus. Monitor it like a service.

    Incident

    Symptom. Around 11:00, hourly tick appends start failing with CommitFailedException, and intraday data falls 40 minutes behind. Diagnosis. A new compaction job was rewriting today's still-open partition. Every append's commit conflicted with the rewrite, and Iceberg retries a failed commit 4 times by default before giving up. Fix. Compact only closed partitions (yesterday and older) during the session, enable partial progress for large rewrites so they commit in pieces, and schedule full compaction after the close. Lesson. Iceberg's optimistic concurrency is cheap when writers touch different files. Design schedules so they do.

    Incident

    Symptom. On Monday some partitions of a two-year MCX tick backfill fail with "file not found", although Sunday's backfill reported success. Diagnosis. On Saturday night an engineer ran orphan-file removal with older_than set to one hour to free space. The backfill had already written files that it had not yet committed; they looked like orphans and were deleted, and the later commit pointed at missing files. The Iceberg docs warn that a retention shorter than the longest write can corrupt a table. Fix. Roll the table back to the snapshot before the backfill and rerun it; wrap orphan removal in a script that refuses anything under the 3-day default. Lesson. Maintenance jobs are production writes. Give them guard rails and owners.

    Incident

    Symptom. Object-store usage grows by 4 TB in a month while logical data grows by 0.5 TB. Diagnosis. The snapshot-expiry flow ran every night and reported success, but after a namespace rename it was expiring tables that no longer existed. The positions table, rewritten every 15 minutes under copy-on-write, kept every snapshot and every old file. Fix. Point the job at the catalog's live table list, alert on progress (snapshots expired and bytes freed per run, oldest snapshot age per table), and switch the positions table to merge-on-read with daily compaction. Lesson. A green job and a working job are different things. Measure what the job changed.

    Incident

    Symptom. At 11:30 the PM dashboards start queueing, and some time out. Diagnosis. In the agent pilot, an SQL tool generated a join of the full tick table with positions without a date filter. The query scanned two years of data and took most of the memory in the compute group that dashboards also used. Fix. Kill the query; move agent traffic to its own compute group or resource group with memory and time limits; expose curated views that require a date and fund filter; cap rows returned by each tool. Lesson. Agents generate queries nobody reviewed. Give them a sandbox sized for mistakes.

    Incident

    Symptom. The morning P&L shows several F&O positions with zero mark-to-market. Diagnosis. The vendor's EOD file arrived truncated, with about half the option contracts. The flow checked the schema, which was valid, but never checked completeness, so missing prices became missing marks. Fix. Add a completeness check against the expected contract count from the instrument master (with a tolerance), compare file size and checksum with the vendor manifest, and block promotion to gold on failure. After the vendor resent the file, the idempotent flow overwrote the partition. Lesson. The dangerous failure is missing rows. Test for them explicitly.

    Incident

    Symptom. At 00:00 on a Saturday every engine, flow and catalog call to the object store fails with TLS handshake errors. Diagnosis. The certificate on the RGW load balancer, issued by the internal CA a year earlier, expired. Nothing monitored its expiry date. Fix. Issue a new certificate, then automate issuance and renewal, and alert at 30 and 7 days before expiry. Lesson. Certificates are scheduled outages unless something renews them.

    Seven openers, one per HR topic

    The topics for the round were listed up front. Expect each one to open with a broad prompt such as "tell me about shared-data versus shared-nothing", followed by two or three probing follow-ups. Below is a 60-second answer for each, at the level of a strong mid-level engineer: it defines the idea, names the mechanism, states a trade-off and a failure mode, is honest that you have not operated the system, and ends on what it means for the business.

    The shape of a 60-second answer

    Spoken English runs at roughly 130 to 160 words a minute (a common rule of thumb), so each opener below is about 150 words. Each one follows the same five beats, which makes them easy to remember under pressure:

    1. Define the idea in one sentence a non-specialist would follow.
    2. Mechanism: how it works, with one concrete detail (a default, a number, a component name).
    3. Trade-off: what you gain and what you pay.
    4. Failure mode: what you would watch, phrased as "the thing I'd watch for is...".
    5. Business tie-in: one sentence tying it to their data or their plan.

    Say the honesty line once per answer, early and plainly, then move on. Repeating it sounds like apology; skipping it risks being caught out on a follow-up.

    1. Distributed database: hosting

    Say this

    "I haven't hosted a self-managed MPP cluster; I've worked with managed systems, and I'd be honest about what I have operated. Here's how I'd host one. Split the roles: coordinators that hold metadata, like StarRocks or Doris FEs, run as three for a majority vote; workers scale with the workload. Spread them across failure domains: racks, power feeds, top-of-rack switches. Use NVMe for anything latency-sensitive and at least 25 GbE. I'd keep storage and the engine on bare metal in year one and put stateless services, the catalog, Prefect and an agent gateway, on a small Kubernetes cluster. Upgrades follow the documented order, for StarRocks BEs and compute nodes first, then follower FEs, then the leader. The thing I'd watch for is maintenance colliding with trading. That means changes after the MCX close or at weekends, and no single point of failure in front of the 09:15 open."

    Likely follow-ups. "Why not run everything on Kubernetes?" (operators exist for StarRocks and for Ceph through Rook; my view is to add them once the team has run the systems on bare metal and knows their failure modes). "How many FEs, and why odd?" (three; a majority of three survives one loss, and a fourth adds cost without tolerating a second failure).

    2. Iceberg tables and catalog

    Say this

    "Iceberg is a table format: rules for metadata files that turn Parquet files on object storage into a table with snapshots, schema evolution and atomic commits. The catalog holds one pointer per table to the current metadata file, and a commit is a compare-and-swap of that pointer, so two writers can't both win. The AWS Glue Data Catalog is a managed cousin, but I haven't operated an Iceberg REST catalog. Three things I'd watch. The catalog is tier-0, so it needs highly available Postgres behind it. Maintenance is a job you own, since by default Iceberg expires nothing and compacts nothing; the Java defaults are 5-day snapshot expiry and a 3-day orphan window when you run them. And the format version must match every reader: I'd stay on v2 because Trino treats v3 as experimental and ClickHouse supports it partially. A REST catalog like Polaris or Lakekeeper gives every engine one source of truth and is where agent permissions start."

    Likely follow-ups. "What happens when two jobs commit at once?" (both write files; the first swap wins; the second re-reads, re-applies its change if it does not conflict, and retries, 4 times by default). "Why REST over Hive Metastore?" (a standard HTTP API with central authorisation and credential vending, independent of any one engine).

    3. Shared data versus shared nothing

    Say this

    "Shared-nothing means each node owns a slice of the data on its own disks, like classic Redshift or self-hosted ClickHouse; Stonebraker's 1986 paper set out the idea. Shared-data means the durable copy lives in shared storage and compute nodes are stateless apart from a local cache, like Snowflake or Redshift RA3. Shared-nothing gives the lowest latency and the fewest dependencies. Shared-data gives one copy of the data, compute you can add without moving data, and separate compute groups for separate workloads. At under 40 TB, size doesn't force either. Both styles are common in managed systems, though I haven't operated either self-hosted. I'd still lean shared-data, because the lake in Iceberg is the system of record and isolation between the risk batch, dashboards and agents matters most. The failure mode I'd watch is cold cache after a restart or scale-out. And neither StarRocks nor Doris supports BACKUP and RESTORE in that mode, so all truth has to live in Iceberg."

    Likely follow-ups. "Where does shared-disk fit?" (shared-disk means every node sees the same block storage, as in Oracle RAC; it needs cluster-wide locking, and shared-data on object storage avoids that by making files immutable). "When would you pick shared-nothing?" (a strict latency target on a small hot table, or an object store the team does not trust yet).

    Sources: Stonebraker 1986 · Snowflake SIGMOD 2016 · Redshift Re-invented 2022 · StarRocks backup and restore · Doris backup and restore

    4. Compression and encryption

    Say this

    "Columnar compression is two layers. Encodings such as dictionary, run-length and delta exploit the shape of a column; then a general codec like LZ4 or zstd squeezes the pages. Tick data sorted by symbol and time compresses well; StarRocks' planning guide uses 3:1 to 5:1, but I'd measure on a week of representative ticks. Iceberg's Java default is zstd. For encryption: TLS in transit everywhere, including between nodes; at rest, drive or object-store encryption covers stolen disks. Iceberg 1.11 added envelope encryption of data and manifest files through a KMS, with limits: Hive and REST catalogs only, Parquet and Avro only, metadata.json stays clear, and the built-in KMS clients are AWS, GCP and Azure, so on-prem means writing a client for Vault or OpenBao. Compress first, then encrypt, since encrypted bytes don't compress. I haven't run a KMS in production. The hard part is key custody: an HA KMS and separate keys for mutual-fund investor data."

    Likely follow-ups. "What does encryption cost in performance?" (AES with CPU instructions is cheap next to decompression and I/O; the bigger costs are KMS availability and key rotation operations). "Does encryption at rest stop an insider with SQL access?" (no; that is the job of RBAC, row policies and masking, so encryption and access control are separate controls).

    Sources: Iceberg encryption · Iceberg releases · Parquet encodings · Parquet modular encryption · StarRocks cluster planning

    5. Independent scaling and performance considerations

    Say this

    "Independent scaling means adding compute without buying storage, and the reverse. Snowflake's virtual warehouses work this way: they resize without touching storage, and Redshift RA3 works the same way; on-prem it means a shared-data engine on top of an object store. Adding compute is quick because CNs hold no durable data, but new nodes start with empty caches, so the first queries read from the object store. Adding storage in Ceph means new drives or nodes and a rebalance, which costs network and belongs outside trading hours. The performance considerations I'd watch: cache hit ratio against the hot-set size, network to the store, where 25 GbE is about 3.1 GB per second per node, object-store latency for small reads, and planning time on tables with too many small files. I haven't operated this myself; these are the numbers I'd put on the dashboard first. The reason to want independent scaling is isolation: the overnight risk batch, morning dashboards and agents each get compute over one copy of data."

    Likely follow-ups. "How much did elasticity matter in practice?" (Snowflake's NSDI 2020 paper, using 14 days of February 2018 data, reported that about a fifth of virtual warehouses were ever resized and 82% never were, so isolation is often the bigger win). "How do you warm a cache?" (StarRocks has CACHE SELECT since 3.3; run it for key tables before the open).

    Sources: Snowflake NSDI 2020 · StarRocks cache warmup · StarRocks shared-data FAQ

    6. Factors that define performance in an MPP database

    Say this

    "For me it comes down to three questions: how much data a query reads, how evenly the work is spread, and how much data moves between nodes. Reading less comes from columnar storage, partition pruning, sort keys and zone maps, which are per-block min and max values, so a query for one NIFTY expiry touches a few files. Even spread comes from bucketing on a high-cardinality key, because the slowest node sets the query's time. Less movement comes from colocated or broadcast joins instead of shuffling big tables, chosen by a cost-based optimizer that needs fresh statistics. Then the engine itself: vectorised execution, parallelism, memory and spill, and concurrency limits. Query tags and QUERY_HISTORY-style attribution are a useful pattern; I'd read StarRocks query profiles with the same habit of measuring before tuning, though I haven't tuned one in production. Morning P&L dashboards under concurrency are mostly a data-layout and cache problem."

    Likely follow-ups. "How would you find a straggler?" (in the query profile, compare the maximum and the average time of each operator across instances; a big gap means skew). "What makes a good bucket key for positions?" (high cardinality and even distribution, such as an instrument or position id; a fund id with one dominant fund is a classic skew).

    Sources: CMU 15-721 Spring 2024 · Trino cost-based optimizer

    7. Object storage and a suitable lake setup: performance

    Say this

    "Object storage is a flat key-value store over HTTP: PUT, GET, LIST, DELETE, no rename and no append, which is why table formats exist. I've used managed object storage, but I haven't run a self-hosted store. Since MinIO's community edition is archived and ships as source only, I'd evaluate Ceph RGW first for maturity and SeaweedFS as the lighter option. Setup: erasure coding 4+2 across at least six hosts plus one to self-heal; buckets per zone, landing, silver and gold, plus a restricted one for mutual-fund investor data; versioning and object lock on landing. For performance: data files of a few hundred megabytes, Iceberg targets 512 MB by default; compaction behind any streaming writer; avoid LIST-heavy access; 25 GbE; stateless gateways behind a load balancer. The failure mode I'd watch is a rebuild on a cluster that's too full, which is why I'd plan to a 70% ceiling. This store is the system of record."

    Likely follow-ups. "Is there a request-rate limit like S3's?" (AWS S3 documents at least 3,500 writes and 5,500 reads per second per partitioned prefix; on-prem there is no such per-prefix figure, and gateway CPU and the bucket index set the limits). "Why not HDFS?" (it needs a NameNode that holds all file metadata in memory and is a different API from the S3 one every engine now speaks).

    Two stories to have ready

    Interviewers often ask "what could go wrong?" after an opener. These two typical scenarios fit the encryption and MPP-performance topics, which the operate drills cover less.

    Incident

    Symptom. At 09:05, queries on the encrypted mutual-fund tables fail, while every other table works. Diagnosis. The KMS cluster lost quorum after two of its three nodes were patched together. Engines could not unwrap the data keys, so encrypted files could not be read. Fix. Restore quorum, then patch KMS nodes one at a time, monitor the KMS like tier-0, and allow short-lived caching of unwrapped keys where the security policy permits. Lesson. Encryption moves part of your availability into the key service. Its SLO must be at least as strict as the data it protects.

    Incident

    Symptom. A positions query that should take a second takes eight, and adding CNs does not help. Diagnosis. The table is bucketed by fund id, and one flagship fund holds most positions. The query profile shows one instance doing most of the scan while the others idle. Fix. Rebucket on a high-cardinality key such as position or instrument id, and keep fund as a filter column. Lesson. In MPP systems the slowest instance sets the time; more nodes cannot fix uneven work.
