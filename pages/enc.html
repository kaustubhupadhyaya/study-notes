    File formats: rows, columns and Parquet inside out

    A file format decides how a table's values are laid out as bytes on disk or in object storage. In an analytics lake that layout sets how much data each query must read, how well the data compresses, and which engines can open it. the lake will almost certainly keep Parquet files under Iceberg tables, so ClickHouse, Doris, StarRocks, Trino and Python tools will all spend most of their scan time inside Parquet.

    Row storage and column storage, from what you already know

    Row-oriented storage keeps all the columns of one row next to each other. Postgres works this way: a table is a heap of 8 KB pages, and each page holds whole rows. Inserting one trade writes to one place. Fetching one position by its key costs one index lookup and one page read. This suits OLTP (online transaction processing): many small reads and writes of individual records, such as booking a trade or updating an investor's address.

    Column-oriented storage (also called columnar storage) keeps all the values of one column next to each other. This suits OLAP (online analytical processing): queries that scan many rows but touch few columns. A typical risk question is "total market value by desk for 13 October 2026". Against a 40-column positions table, that query needs 3 columns: desk, as_of_date and market_value. A row store must pull all 40 columns' bytes off disk to get at those 3. A column store reads only the 3.

    Some illustrative arithmetic makes the gap concrete. Take 50 million position rows of 40 columns at about 8 bytes each: 320 bytes per row, 16 GB in total. The 3-column query reads 3 × 8 × 50 million = 1.2 GB in a column store before any compression, against 16 GB in a row store. Compression widens the gap further, because a column of similar values compresses far better than a row of mixed types (the next section explains why).

    Two terms describe how engines exploit this. Projection pushdown (or column pruning) means the reader fetches only the columns the query names. Predicate pushdown means the filter in the WHERE clause is handed down to the storage reader, so it can skip blocks of data that cannot match. A third term explains why columnar engines are fast once data is in memory. Vectorized execution processes a batch of values from one column (a few thousand at a time) in a tight loop, often with SIMD instructions (single instruction, multiple data: one CPU instruction applied to several values at once). ClickHouse, Doris, StarRocks and DuckDB are built around vectorized execution; Trino also processes data in columnar batches, called pages.

    Parquet is a hybrid. It first cuts the rows into large groups, then stores each column separately inside each group. The research literature calls this layout PAX (Partition Attributes Across). The practical consequence: a writer can stream rows and flush one group at a time, and a reader can still fetch one column at a time.

    Field notes
    • SELECT * is the most expensive query you can run on columnar data, because it reads and reassembles every column. Analysts do it out of habit and AI agents do it by default. Put row limits and column lists in the tools that agents call.
    • Columnar systems dislike single-row changes. Correcting a trade booked yesterday becomes "mark the old row deleted, insert a new one", and the cleanup happens later in compaction. Design correction flows as batches.
    • Wide tables are cheap in columnar storage when queries are narrow. That reverses the Postgres habit of splitting wide tables to keep rows small. A 200-column risk results table is fine if each report reads ten columns.

    Parquet anatomy, from the outside in

    Apache Parquet is an open columnar file format. It is self-describing: the schema travels inside the file, so no outside service has to tell a reader what the columns are. Here are its parts, from the largest to the smallest.

    1. Magic bytes. Every plain Parquet file starts and ends with the four bytes PAR1. Files whose footer is encrypted use PARE instead (see the encryption section).
    2. Row groups. A row group is a horizontal slice of the table, for example one million NIFTY option trades. Row groups are independent of each other, so parallel readers usually divide work by row group.
    3. Column chunks. A column chunk is all the values of one column inside one row group, stored contiguously. A reader that wants the price column of row group 3 makes one ranged read for that chunk.
    4. Pages. A page is the smallest unit inside a column chunk. Encoding and compression are applied page by page. Most pages are data pages. When a column is dictionary-encoded, the chunk begins with a dictionary page holding each distinct value once (for example every symbol that appears in that row group).
    5. Footer. The footer (file metadata) sits at the end of the file. It holds the schema, the list of row groups, and for every column chunk its type, encodings, compression codec, byte offsets and statistics: minimum, maximum and null count. The last eight bytes are the footer length and the closing PAR1, so a reader always reads the tail of the file first.
    6. Page index. The optional page index adds two structures per column chunk. The ColumnIndex stores min, max and null information for every page. The OffsetIndex stores where each page starts and the number of its first row. Together they let a reader jump straight to the pages that can match, without reading every page header.
    7. Bloom filters. An optional Bloom filter per column chunk is a compact bit array that answers "definitely not in this chunk" or "probably in this chunk". It never gives a false "no". Parquet uses split block Bloom filters made of 256-bit blocks. They help equality lookups on high-cardinality columns, such as one ISIN (International Securities Identification Number) or one order ID, where min/max ranges are too wide to exclude anything.

    Nulls and nested data use two small extra streams per column, called definition levels (how much of a nested path is present, which also marks nulls) and repetition levels (where a list starts again). The idea comes from Google's Dremel paper. The practical point: flat, typed columns read faster than deeply nested JSON-like structures.

    The footer sits at the end because the writer only knows each chunk's offset after writing it. One consequence matters operationally: a writer that crashes before it closes the file leaves a file with no footer, and no reader can open it. Table formats such as Iceberg protect readers from this, because a data file only becomes visible when a commit lists it in table metadata.

    You can inspect all of this without a cluster. DuckDB reads the footer of any Parquet file and returns one row per column chunk:

    SELECT row_group_id, path_in_schema, row_group_num_rows,
       compression, encodings,
       stats_min_value, stats_max_value,
       total_compressed_size, total_uncompressed_size
FROM parquet_metadata('nse_fo_trades_2026-10-13.parquet')
WHERE path_in_schema IN ('symbol', 'ts', 'price')
ORDER BY row_group_id, path_in_schema;

    Four things to read from that output. First, rows per row group: a few thousand means a streaming writer flushed too early. Second, whether the min/max of symbol overlap across row groups: if every row group spans the whole alphabet, the file is unsorted and stats will skip nothing. Third, the encodings list: a mix of dictionary and PLAIN in one chunk means the dictionary overflowed. Fourth, compressed versus uncompressed size per column, which tells you which column is eating the bytes.

    Field notes
    • On object storage, opening a Parquet file costs at least two round trips: one ranged GET for the tail (the footer), then GETs for the column chunks. Many small files therefore pay many round trips before any data arrives.
    • Page indexes and Bloom filters are optional on both sides. A writer may not produce them, and a reader may not use them. Confirm in the engine's query profile, which reports figures such as pages skipped or row groups pruned.
    • Writers truncate statistics for long strings. Iceberg's own per-file metrics keep only the first 16 characters by default, which is enough for most symbols and ISINs (an ISIN is 12 characters).
    • The footer of a very wide file (hundreds of columns, many row groups) can itself reach megabytes. Engines cache footers for that reason, and a cold cache shows up as slow first queries.

    How an engine uses each level to skip data

    Skipping is the single biggest performance lever in a lake. The fastest byte is the one never read. Follow one query through the levels. The table md.nse_fo_trades is an Iceberg table partitioned by day of ts and written sorted by underlying, expiry, strike, then ts.

    SELECT ts, price, qty
FROM md.nse_fo_trades
WHERE ts >= TIMESTAMP '2026-10-13 10:00:00'
  AND ts <  TIMESTAMP '2026-10-13 10:05:00'
  AND underlying = 'NIFTY'
  AND expiry = DATE '2026-10-27'
  AND strike = 25000
  AND opt_type = 'CE';
    1. Partition pruning. The Iceberg partition spec (the rule that groups files, here "day of ts") lets the planner keep only files for 13 October. Every other day disappears before any file is opened.
    2. File pruning from table metadata. Iceberg manifests store, for each data file, lower and upper bounds per column. Because files were written sorted by underlying, only files whose underlying range includes NIFTY survive. This happens in the planner, from metadata alone.
    3. Row group pruning. Inside each surviving file, the reader checks footer stats for strike and ts and drops row groups whose ranges cannot match.
    4. Page pruning. With a page index on ts, the reader fetches only the pages covering 10:00 to 10:05.
    5. Dictionary and Bloom checks. If 25000 sits inside a chunk's min/max range but appears in neither its dictionary nor its Bloom filter, the chunk is skipped.
    6. Late materialization. Late materialization means reading the filter columns first and fetching the other columns (price, qty) only for rows that passed. Most modern engines do some form of it.
    flowchart LR
  Q["Query with filters"] --> P["Partition pruning by day"]
  P --> M["File pruning by manifest bounds"]
  M --> R["Row group pruning by footer stats"]
  R --> G["Page pruning by page index"]
  G --> B["Dictionary and Bloom checks"]
  B --> L["Late materialization of price and qty"]

    Every step after the first depends on one thing: similar values sitting together. If ticks are written in arrival order, each file and row group holds a slice of time across all instruments, so every underlying range runs from the first symbol alphabetically to the last. Steps 2 to 5 then skip nothing. Sorting (next subsection) is what makes statistics useful.

    Iceberg also limits which columns get file-level metrics. By default it collects metrics for the first 100 columns only (write.metadata.metrics.max-inferred-column-defaults = 100) and truncates string bounds to 16 characters (write.metadata.metrics.default = truncate(16)). Both can be changed per column.

    Field notes
    • The first diagnostic for a slow scan is the ratio of data read to data returned. Trino shows physical input bytes and splits per query; StarRocks and Doris query profiles show how many rows zone maps and other indexes filtered out; ClickHouse EXPLAIN indexes = 1 shows how many parts and granules survived the primary index.
    • Engine-native formats repeat the same ladder under other names. Doris segment files keep a zone map (min, max, has-null) per page of about 64 KB, plus optional Bloom filters. ClickHouse keeps a sparse primary index with one entry per 8,192-row granule by default.
    • Filters wrapped in functions often defeat pruning. WHERE CAST(ts AS DATE) = ... or WHERE upper(symbol) = 'INFY' may stop the planner from using bounds, depending on the engine. Filter on the raw column.
    Incident

    Symptom. A filter on risk_bucket in a 220-column risk results table scans every file, although the data was written sorted by that column. Other filters on the same table prune well. Diagnosis. risk_bucket is column 140. Iceberg collected file-level metrics only for the first 100 columns, so the manifests hold no bounds for it and the planner cannot exclude files. This is a common trap with wide, generated tables. Fix. Set write.metadata.metrics.column.risk_bucket to truncate(16) or full, or move the column earlier in the schema, then rewrite the affected files so their manifests carry the new bounds. Lesson. Pruning needs both clustered data and metadata about that column. Check the second before blaming the first.

    Why sort order inside files matters

    Sorting rows before writing has three effects, and all three help analytics:

    • Tight statistics. A row group sorted by symbol covers a few symbols, so its min/max excludes almost every other symbol.
    • Long runs. Repeated values sit next to each other, so run-length encoding stores "INFY, 40,000 times" instead of 40,000 entries.
    • Small differences. Sorted timestamps or sequence numbers differ by small amounts from row to row, and delta encodings store those small differences in a few bits each.

    Pick the sort key from the filters people actually run. Lead with the column most often filtered by equality, then the range column, usually time:

    EOD prices (bhavcopy style)Month or year (small data)symbol, trade_datePrice history of one instrument
    Positions and P&Las_of_datefund, book, instrument_idOne fund's book on one date
    Structured-credit loan cash flowsDeal vintage or reporting monthdeal_id, loan_id, pay_dateCash flows of one deal or one loan
    Mutual fund NAV (net asset value per unit)Yearscheme_code, nav_dateNAV history of one scheme

    When several filters matter equally, a single sort key favours the first column and does little for the others. Z-ordering interleaves the bits of several columns so that rows close in all of them land close together. Each column then gets partial pruning. It costs more CPU at write time and helps less than a plain sort on the leading column.

    How to declare it:

    -- Spark with Iceberg extensions: writers sort by this order
ALTER TABLE md.nse_fo_trades WRITE ORDERED BY underlying, expiry, strike, ts;

-- Trino: sort order as a table property
CREATE TABLE md.nse_fo_trades (...)
WITH (partitioning = ARRAY['day(ts)'],
      sorted_by    = ARRAY['underlying', 'expiry', 'strike', 'ts']);

-- Spark: re-sort existing files during compaction
CALL lake.system.rewrite_data_files(
  table      => 'md.nse_fo_trades',
  strategy   => 'sort',
  sort_order => 'underlying ASC, expiry ASC, strike ASC, ts ASC');

    The engines on a typical shortlist have the same idea in their native tables. ClickHouse sorts each part by the table's ORDER BY. StarRocks and Doris sort by the key columns (and StarRocks accepts a separate ORDER BY sort key: on primary key tables since 3.0, on the other table types since 3.3). The trade-offs are also the same. Sorting needs memory and usually a shuffle at write time. There is only one physical order per copy of the data. And streaming writers naturally write in arrival order, so the sort usually happens later, in compaction.

    Incident

    Symptom. A team turns on nightly compaction to fix a small-files problem. File counts drop as planned, but next morning queries for one underlying are slower than before. Diagnosis. The compaction used the bin-pack strategy, which rewrites small files into files of about 512 MB without sorting. Before, each small file happened to hold a narrow slice of symbols. Now every large file spans all symbols, so manifest bounds and row group stats exclude nothing and each query reads far more data. Fix. Declare a table sort order and switch compaction to the sort strategy for this table. Lesson. Compaction changes data layout. Check pruning metrics (files and row groups scanned per query) before and after any compaction change.

    ORC, Avro and CSV: where each fits

    ORC (Optimized Row Columnar) is Parquet's sibling from the Hive world. It splits a file into stripes (64 MB by default), keeps lightweight indexes every 10,000 rows (the row index stride), and ends with a footer and a small postscript. It has strong type support and was the base of Hive's transactional tables. ORC's own Java library now defaults to ZSTD compression, while Iceberg's ORC writer defaults to zlib (as of Oct 2026). Spark and Trino handle ORC well. Several newer writers are Parquet-first: StarRocks writes Iceberg tables in Parquet only. My view: for a new lake there is no reason to choose ORC unless an existing Hive estate already uses it.

    Avro is a row-oriented binary format. Each file starts with a header holding the schema as JSON, followed by blocks of records separated by 16-byte sync markers. Its strength is schema evolution: a reader can decode data written with an older schema by resolving the writer's schema against its own. That makes Avro the usual format for record-at-a-time streams, such as Kafka messages with a schema registry. Iceberg also uses Avro for its own metadata: manifests and manifest lists are Avro files (Iceberg's default codec for Avro data files is gzip). Avro is poor for analytics scans because every column of every row must be read.

    CSV and JSON lines are landing formats. They carry no types, no statistics and no column boundaries. A gzip-compressed CSV cannot be split for parallel reading, so one reader must decompress the whole file. Vendor loan tapes, exchange EOD files and registrar investor files will arrive in these formats (and PDFs for structured-credit documents). Keep the raw file for audit, then convert it to Parquet with an explicit schema in the first pipeline step.

    Querying the landing format directly "for now". A folder of daily CSV loan tapes queried through an external table works on day one. A year later every query re-parses every file, types drift between vendor versions (a date column arrives as text one month), and nothing can be skipped. Convert at ingest, validate the schema at that moment, and let analysts query only the Parquet tables.

    Why these settings interact with memory: a Parquet writer buffers a whole row group in memory for each file it has open, and flushes it when the buffer reaches the row group size. Memory therefore grows roughly with (open files) × (row group size), less whatever compression saves. A job that writes to many partitions at once holds many buffers at once.

    Why they interact with object storage: each column chunk read is usually one ranged GET. Small row groups mean small chunks and many requests. AWS documents at least 5,500 GET/HEAD requests per second per partitioned prefix for S3. A self-hosted store has its own limits set by its metadata layer and disks, and the request rate is usually the first wall a small-files workload hits.

    When streaming writers produce tiny row groups

    A streaming or micro-batch writer commits on a timer: every minute, every checkpoint, every N records. Each commit closes the files it has open, because a Parquet file is only readable once its footer is written. If the commit interval is short and the data rate per partition is modest, each file ends up with one small row group of a few thousand rows.

    The costs pile up in five places:

    • Compression. Each column chunk is compressed and dictionary-encoded on its own. Small chunks give the codec little context, so ratios fall.
    • Requests. Every file costs a footer read plus chunk reads. Ten thousand small files cost tens of thousands of requests for data a few large files would serve in hundreds.
    • Planning. Each file is an entry in a manifest. Iceberg's planner also counts each file as at least 4 MB of work when sizing splits (read.split.open-file-cost), so tiny files inflate the number of tasks.
    • Metadata growth. Each commit creates a snapshot, a manifest list and usually a manifest. Thousands of snapshots make the table's metadata slow to load until they are expired.
    • Engine-side merges. In ClickHouse the same pattern appears as too many small parts. By default (as of Oct 2026) inserts are delayed when a partition reaches 1,000 active parts and rejected at 3,000.

    Illustrative arithmetic: the NSE equity and F&O session runs from 09:15 to 15:30, which is 375 minutes. A flow that appends ticks to an Iceberg table once a minute, with 4 parallel writer tasks, creates 375 × 4 = 1,500 files and 375 snapshots per day. Over 60 trading days that is 90,000 files and 22,500 snapshots for one table. A one-month query plans over roughly 30,000 small files.

    The fixes, roughly in order of preference:

    1. Separate the hot path from the lake. Let the MPP engine absorb real-time ticks in its native tables (it is built for frequent small inserts and merges in the background). Write to Iceberg in larger batches, for example every 15 minutes or at end of day. The interval is a judgement call between freshness and file size.
    2. Commit less often where a direct lake write is required, so each file reaches tens or hundreds of MB.
    3. Compact on a schedule: Spark's rewrite_data_files, Trino's ALTER TABLE ... EXECUTE optimize, or the compaction API StarRocks added in 4.0. PyIceberg 0.12 can expire snapshots but has no compaction yet, so a Python-only stack still needs one of these engines for this job.
    4. Expire snapshots and remove orphan files so metadata stays small.
    -- Trino: how bad is it? Iceberg exposes metadata tables.
SELECT count(*) AS files,
       avg(file_size_in_bytes) / 1048576 AS avg_mb,
       sum(record_count) AS rows
FROM md."nse_fo_trades$files";

-- Trino: compact files below 100 MB into larger ones
ALTER TABLE md.nse_fo_trades EXECUTE optimize(file_size_threshold => '100MB');
    Incident

    Symptom. Queries over the last month of ticks take a long time before the first row appears, even for tiny result sets. CPU on the workers is low. Diagnosis. A Prefect flow appends each minute's ticks with PyIceberg. The $files metadata table shows tens of thousands of files averaging well under 1 MB, and the $snapshots table shows tens of thousands of snapshots. Time goes to loading manifests and opening footers. Fix. Batch the lake writes to 15 minutes (ticks for the current day are served from the MPP engine), run a nightly Spark or Trino compaction with a sort order, and expire snapshots older than a retention window agreed with compliance. Lesson. In a lake, write frequency is a design parameter. Choose it together with compaction, and monitor average file size as a first-class metric.

    Incident

    Symptom. A backfill job that rewrites three years of EOD and corporate-action data into a new table is OOM-killed on its Kubernetes pod. Smaller test runs worked. Diagnosis. The new table is partitioned by symbol. Each writer task sees rows for hundreds of symbols, keeps one open file per partition, and buffers a row group for each. 500 open files × a 128 MB buffer is 64 GB in the worst case. Fix. Repartition the input by the table's partition key before writing (Iceberg's hash distribution mode does this in Spark), so each task holds few open files, and reconsider the partition key: symbol partitions are too many and too small for EOD data. Sort by symbol inside yearly partitions instead. Lesson. Writer memory scales with open partitions times row group size. Partition by time and sort by entity.

    Field notes
    • Average data file size per table is the single best health metric for a lake. A reasonable alert, in my view: average under 32 MB on a table larger than 100 GB.
    • Bin-pack compaction fixes counts and breaks clustering; sort compaction fixes both but costs more CPU. Run sort compaction on the tables people filter by entity.
    • Compaction is itself a writer. It creates new snapshots, conflicts with concurrent deletes or updates on the same files, and needs retries. Schedule it away from end-of-day loads.
    • Expiring snapshots removes time travel to those snapshots. Agree the retention with whoever owns audit and reproducibility of NAV and risk numbers before setting it.
    Senior lens

    File format settings outlive the people who chose them. Once 30 TB of Parquet is written with a given layout, changing it means rewriting 30 TB. The senior moves are organisational. First, put one shared writer library (or one ingestion service) in front of the lake, so every pipeline writes with the same codec, row group size, sort order and metrics settings, and a change is a one-place edit. Second, make average file size, files per partition and snapshot count visible on the platform dashboard next to query latency. Third, keep the lake as the open source of truth and let each MPP engine keep its own native copy of hot data: the lake answers "no lock-in", and the engine answers "sub-second dashboards". Finally, be explicit that compaction is a scheduled production job with an owner, an SLA and alerts, the same as the ingestion it cleans up after.

    Say this

    "I haven't run a self-hosted lake, so this is how I reason about it. Parquet is a columnar file in layers: row groups, column chunks, pages, and a footer with min, max and null counts, plus optional page indexes and Bloom filters. An engine skips data at every layer: Iceberg partitions and manifest bounds first, then row group stats, then pages, then dictionary or Bloom checks. All of that only works if similar values sit together, so I'd sort tick data by underlying, expiry, strike and time inside daily partitions, and positions by fund and book inside as-of-date partitions. The failure I'd watch for most is small files from frequent commits: it hurts compression, request counts and planning. I'd keep real-time ticks in the MPP engine, write the lake in larger batches, run sort compaction nightly, and track average file size as a platform metric. And I'd standardise writer settings in one library, the way a single connection layer does on a well-run platform."

    Compression and encoding: smaller columns without starving the CPU

    Compression shrinks data so that less of it moves from disk, object storage or network into memory. Every codec trades CPU time for fewer bytes, and the right trade depends on where a query spends its time. It decides how many disks the colo racks need for 40 TB with replicas, how fast tick queries run, and how much CPU is left for AI agents and risk runs.

    Encoding versus compression

    Two different steps are often both called "compression". Keeping them apart makes every later discussion clearer.

    An encoding is a type-aware transformation of a column's values into a more compact representation. It knows that it is looking at integers, strings or floats. Examples: replace each symbol string with a small integer from a dictionary, or store each timestamp as the difference from the previous one. Engines can often work on encoded data directly, for example comparing dictionary codes instead of strings.

    A compression codec (general-purpose compression) treats its input as plain bytes and finds repeated byte patterns. LZ4, Snappy, ZSTD and gzip are codecs. Data must be decompressed before the engine can use it.

    In Parquet, Doris segment files and ClickHouse parts the order is the same: encode first, then compress, page by page or block by block. Reading reverses it.

    flowchart LR
  V["Column values, e.g. ts or symbol"] --> E["Encoding: dictionary, delta, RLE, byte split"]
  E --> C["Codec: LZ4, ZSTD, Snappy, gzip"]
  C --> X["Optional encryption of the compressed page"]
  X --> P["Page written to file or part"]

    Why columnar data compresses so well comes down to entropy, the amount of genuine unpredictability in the data. A column holds one type with a narrow range of values. A symbol column for one day has a few thousand distinct values repeated millions of times. A timestamp column rises in small steps. A quantity column is mostly multiples of a lot size. Each of those is highly predictable, so it can be stored in far fewer bits than its raw width. Sorting makes it more predictable still: after sorting by symbol, the symbol column becomes long runs of one value, and timestamps within each symbol rise steadily.

    Sources: Parquet encodings · Doris data compression

    Two small examples show the mechanics. A dictionary-encoded symbol column for a day of equity trades might hold 2,000 distinct strings in its dictionary page; each of millions of rows then stores an 11-bit code instead of a string of up to 20 bytes. A timestamp column with ticks arriving microseconds apart stores, after delta encoding, differences such as 120, 85, 310: a few hundred fits in 9 bits instead of 64.

    Dictionary fallback is the behaviour to understand best. A writer builds the dictionary as it goes. If the dictionary grows past the dictionary page size limit (1 MB in parquet-java, 2 MB in Iceberg and PyIceberg), the writer stops using it and writes the rest of that column chunk as PLAIN. The Parquet specification describes exactly this fallback. You then see two encodings listed for one chunk.

    Which encodings a writer uses is the writer's decision. Many writers pick dictionary with a PLAIN fallback by default; parquet-java, for example, generally chooses the DELTA_* encodings only in its v2 writer mode (parquet.writer.version, default PARQUET_1_0). Check what your files actually contain with parquet_metadata before assuming an encoding is in use. Parquet has also added an ALP encoding for decimal-like floats, marked as preview in the specification (as of Oct 2026).

    Field notes
    • Store money and prices as DECIMAL or as scaled integers (for example paise, or price × 10,000 as INT64). It is correct for money, and integers encode and compress far better than doubles.
    • Dictionary encoding also speeds up filters: an engine can test symbol = 'RELIANCE' once against the dictionary and then compare small integer codes.
    • High-cardinality string IDs (order IDs, loan IDs, keys derived from PAN, India's tax identifier) waste dictionary effort. Turn dictionary off for those columns (Iceberg: write.parquet.dict-encoding-enabled.column.order_id = false) and add a Bloom filter if people look them up by exact value.

    Gorilla and DoubleDelta come from Facebook's Gorilla time-series database paper (VLDB 2015), which compressed timestamps with delta-of-delta and values with XOR. A tick table in ClickHouse might look like this:

    CREATE TABLE md.nse_ticks
(
    ts          DateTime64(6, 'Asia/Kolkata') CODEC(DoubleDelta, ZSTD(1)),
    symbol      LowCardinality(String),
    price_paise Int64   CODEC(GCD, Delta, ZSTD(1)),
    qty         UInt32  CODEC(T64, ZSTD(1)),
    exch_seq    UInt64  CODEC(Delta, ZSTD(1)),
    iv          Float64 CODEC(FPC, ZSTD(1))
)
ENGINE = MergeTree
PARTITION BY toDate(ts)
ORDER BY (symbol, ts);

    Two notes on that sketch. LowCardinality(String) is ClickHouse's dictionary encoding for strings. And because the table is ordered by (symbol, ts), timestamps within each symbol are monotonic, which is what makes DoubleDelta effective. Treat the codec choices as starting hypotheses to test on real data. ClickHouse also has an experimental enable_adaptive_codec_selection MergeTree setting that, for columns without an explicit CODEC, tries specialised codecs per block during merges and mutations (as of Oct 2026).

    To see what each column costs, ask the server:

    SELECT name,
       compression_codec,
       formatReadableSize(data_compressed_bytes)   AS on_disk,
       formatReadableSize(data_uncompressed_bytes) AS raw,
       round(data_uncompressed_bytes / nullIf(data_compressed_bytes, 0), 1) AS ratio
FROM system.columns
WHERE database = 'md' AND table = 'nse_ticks'
ORDER BY data_compressed_bytes DESC;

    ClickHouse compresses each column in blocks of 64 KB to 1 MB of uncompressed data (min_compress_block_size and max_compress_block_size defaults). Changing a codec with ALTER TABLE ... MODIFY COLUMN ... CODEC(...) affects newly written parts; old parts keep their codec until a merge or mutation rewrites them.

    Field notes
    • Gorilla shines on slowly changing series. Raw trade prices jump between bid and ask, so XOR of consecutive values is often not small. Scaled integers with Delta or GCD usually do better on traded prices. Measure both.
    • DoubleDelta on an unsorted timestamp column can be worse than plain ZSTD. It needs monotonic input, which comes from the ORDER BY.
    • The column ranking from system.columns is usually lopsided: one or two columns hold most of the bytes. Tune those and leave the rest on defaults.

    General-purpose codecs and the CPU versus I/O trade

    The main codecs, from fastest to strongest:

    • LZ4: very fast compression and the fastest decompression; moderate ratio. ClickHouse's self-managed default. In Parquet, use LZ4_RAW; the older LZ4 codec value is deprecated because of an undocumented framing scheme that writers implemented inconsistently.
    • Snappy: Google's fast codec; similar ratio to LZ4 with slower decompression. Spark's and DuckDB's default for Parquet.
    • ZSTD (Zstandard): a much better ratio than LZ4 at its low levels, with tunable levels. The command-line tool accepts levels 1 to 19 (default 3), up to 22 with --ultra, and negative "fast" levels. ClickHouse accepts ZSTD(1) to ZSTD(22) with default level 1.
    • gzip/zlib (DEFLATE): older; a decent ratio with slow compression and decompression. Still Iceberg's default codec for Avro data files (gzip) and for its ORC writer (zlib).
    • Brotli: strong ratio, slow; rare in data lakes.
    • None: sensible for data that is already compressed or encrypted.

    The zstd project publishes a single-core benchmark on the Silesia corpus (a standard set of mixed files that contains no market data). It shows the shape of the trade:

    Codec (lzbench, i7-9700K, one core)RatioCompressDecompress
    zstd 1.5.7, level 12.896510 MB/s1,550 MB/s
    zlib 1.3.1, level 12.743105 MB/s390 MB/s
    lz4 1.10.02.101675 MB/s3,850 MB/s
    snappy 1.2.12.089520 MB/s1,500 MB/s

    Two facts from that page carry most of the practical judgement. First, ZSTD level 1 gives a clearly better ratio than LZ4 or Snappy at similar compression speed. Second, the zstd authors note that decompression speed stays roughly the same at every level. So a higher ZSTD level mostly taxes the writer, while readers pay about the same. That is why "compress once, read many times" data such as historical ticks can use higher levels.

    Whether a stronger codec makes queries faster depends on the bottleneck. Illustrative arithmetic, with assumed figures: a query must scan 200 GB of raw column data on one node with a 10 GbE link (about 1.25 GB/s) to the object store. At a 4:1 ratio it pulls 50 GB, about 40 seconds of network. At 6:1 it pulls 33 GB, about 27 seconds. Decompression at roughly 1.5 GB/s per core (the zstd level 1 figure above) across 16 cores handles 200 GB of output in under 10 seconds. Here the network is the bottleneck, so the stronger codec wins. If the same data sat in the node's memory cache, the network term would vanish and the lighter codec, with less CPU per byte, would win instead.

    Data temperatureExample on-premWhere the time goesReasonable default (my view)
    Hot, interactiveToday's ticks, intraday positions, dashboardsCPU and memory; data cached locallyLZ4, or ZSTD(1)
    WarmLast 1 to 2 years of ticks and P&L in the lakeObject store and network readsZSTD at low levels (1 to 3)

    Field notes
    • Benchmark codecs on your own data with a cold cache and a warm cache. A codec that wins with a warm cache can lose when data comes from object storage, and the reverse.
    • Compression ratio multiplies with replication. Three replicas of data at 5:1 still occupy 0.6 × raw. On a shared-data design with erasure coding the multiplier is lower. Do storage sizing with both numbers.
    • ZSTD at levels 1 to 3 is the usual landing zone in lakes. Levels above roughly 9 are mostly for archives, and their write cost rises steeply (rule of thumb from the zstd benchmark curves).

    Ratios on tick and EOD data: rules of thumb and how to measure

    No published benchmark covers the data, and I have not measured it, so treat every ratio here as a rule of thumb to be replaced by a measurement in week one.

    • Whole-table ratios. StarRocks's deployment planning guidance quotes 3:1 to 5:1 for sizing, and the Doris columnar storage page says ZSTD typically shrinks a table 5x to 10x. These are vendor sizing figures on generic data. My working assumption for sorted market data in Parquet with ZSTD is the upper half of that range, to be confirmed.
    • Per column, the spread is wide. Sorted timestamps and sequence numbers compress extremely well. Dictionary-encoded symbols cost a few bits per row. Quantities in lot multiples do well. Raw double prices and random IDs compress poorly and often dominate the bytes.
    • EOD data is small. One row per instrument per day is megabytes per year. Codec choice does not matter for its cost; choose for simplicity. Ticks, F&O quotes and loan-level cash flows are where codec choice moves the hardware budget.

    A measurement plan that fits in a day: take one representative week of ticks; write it as Parquet with LZ4_RAW, ZSTD(1), ZSTD(3) and ZSTD(9), sorted and unsorted; record file size per column (from parquet_metadata), write throughput per core, and the p50 and p95 of five real queries with cold and warm caches. Repeat in the chosen engine with system.columns (ClickHouse) or SHOW DATA (StarRocks, Doris).

    -- DuckDB: bytes per column across a folder of Parquet files
SELECT path_in_schema,
       sum(total_compressed_size)   / 1e9 AS gb_on_disk,
       sum(total_uncompressed_size) / 1e9 AS gb_raw,
       round(sum(total_uncompressed_size) / sum(total_compressed_size), 1) AS ratio
FROM parquet_metadata('ticks_week/*.parquet')
GROUP BY path_in_schema
ORDER BY gb_on_disk DESC;

    Parquet's "uncompressed size" is measured after encoding and before the codec. The ratio above therefore shows what the codec added on top of encoding. Compare total file size against the raw CSV size for the end-to-end figure.

    What goes wrong: three common incidents

    Incident

    Symptom. On a new tick table, the price column takes about half the bytes on disk and compresses barely better than 1.3:1, while every other column compresses several times over. Diagnosis. Prices are stored as DOUBLE. Values such as 1523.45 have no exact binary representation, and derived prices (VWAP, the volume-weighted average price, or the bid-ask mid) carry a full 52-bit mantissa of noise, so neighbouring values share few bytes. Trade prices also jump between bid and ask, which defeats XOR-based codecs. This is a very common outcome when a feed handler passes floats straight through. Fix. Store traded prices as scaled integers (Int64 in paise or price × 10,000) or DECIMAL(18,4). In ClickHouse add GCD or Delta before ZSTD; in Parquet let dictionary or delta encodings work on the integers. Keep genuinely continuous floats (Greeks, implied volatility) as doubles with BYTE_STREAM_SPLIT in Parquet or FPC in ClickHouse, and measure. Lesson. Data types are a compression decision. Fixed-point for money is right for correctness and for bytes.

    Incident

    Symptom. Daily Parquet files for the order log grow far faster than order counts on F&O expiry days, and scans of the client_order_id column slow down. Diagnosis. parquet_metadata shows RLE_DICTIONARY and PLAIN listed together for that column: the dictionary hit the 2 MB dictionary page limit early in each row group and the writer fell back to plain encoding for the rest. On quiet days the column stayed under the limit, so the problem only showed with volume. Teams often hit this with order IDs, loan IDs and investor folio numbers. Fix. Turn dictionary encoding off for unique-ID columns (write.parquet.dict-encoding-enabled.column.client_order_id = false), let the codec handle them, and add a Bloom filter for exact-match lookups. For columns of moderate cardinality that genuinely benefit, such as option contract symbols on expiry day, raising write.parquet.dict-size-bytes can keep them dictionary-encoded. Lesson. Check encodings per column after the first busy day, and treat "two encodings in one chunk" as a signal to decide the column's encoding explicitly.

    Incident

    Symptom. After a change "to save disk", ingestion falls behind at market open. Writer CPU sits at 100%. In ClickHouse, active parts climb towards the 1,000-part insert-delay threshold and inserts start to slow. Diagnosis. Someone set ZSTD(19) on the tick table (or write.parquet.compression-level = 19 on the lake table). High ZSTD levels compress many times slower than level 1 while saving a modest extra fraction of space, and decompression barely changes. Every merge also recompresses at that level, so merges fall behind as well. Fix. Return the ingest path to ZSTD(1) or LZ4. Recompress data once it is cold: a ClickHouse TTL RECOMPRESS rule after three months, or a lake compaction job for old partitions that writes with a higher level. Lesson. Compression level is a write-side CPU budget. Spend it where data is written once and read for years, and keep the hot path cheap.

    Common mistake

    Choosing a codec by compression ratio alone, from a benchmark on someone else's data. The ratio decides disk cost; the query and ingest costs depend on CPU per byte and on whether the workload is bound by I/O or by CPU. Measure ratio, write throughput and query latency together, on your own data, with cold and warm caches.

    Senior lens

    On-prem, compression is a capital expense decision. Disks for 40 TB raw are bought up front in racks the team manages, multiplied by replicas, divided by compression ratio, plus headroom. A ratio of 3:1 versus 6:1 can halve or double the storage purchase. CPU is also bought up front, and in this design it is shared by ingestion, merges or compaction, interactive queries, overnight risk runs and, later, AI agents that issue many small queries. A senior engineer sets tiers (cheap codecs where data is hot and cached, ZSTD where data is read from object storage, heavy ZSTD only for cold archives), writes them into the shared writer library and table templates, and measures before tuning. They also keep codecs boring: every engine on the shortlist reads ZSTD and LZ4 Parquet, while exotic choices can make files unreadable to the next tool the team adopts.

    Say this

    "I separate encoding from compression. Encodings are type-aware: dictionary for symbols and books, delta for timestamps and sequence numbers, byte-stream-split for floats. Codecs like LZ4 and ZSTD then squeeze the bytes. Columnar data compresses well because each column is one type in a narrow range, and sorting makes it better. The trade is CPU against I/O: if queries read from object storage over the network, a stronger codec usually wins; if data is cached locally and CPU is the bottleneck, LZ4 or ZSTD level 1. ZSTD's decompression speed is about the same at every level, so higher levels mostly cost the writer, which suits cold history. Defaults differ: ClickHouse self-managed uses LZ4 with per-column codecs like DoubleDelta and GCD, StarRocks uses LZ4 with the codec fixed at create time, Iceberg writes ZSTD. I haven't measured the data, so I'd benchmark a week of ticks across three codecs in the first sprint, and I'd store prices as scaled integers or decimals, because raw doubles are the usual reason a price column compresses badly."

    Encryption: at rest, in transit, and what it cannot do for AI access

    Encryption turns data into ciphertext that only holders of the right key can read. It protects data on stolen or discarded disks, on networks that someone can tap, and from storage administrators who should not see contents. With on-prem racks in a vendor's colo, investor records for a new mutual fund and AI agents on the roadmap, the hard parts are choosing the layer, keeping keys available, and remembering that encryption does nothing against a caller who holds valid credentials.

    The threat model in plain words

    A threat model is a written list of who might attack, what they could reach, and which control stops each one. Without it, teams switch on encryption everywhere and still miss the real risk. Three terms first. Data at rest is data stored on disks or in an object store. Data in transit is data moving over a network. Data in use is data in memory while a process works on it; protecting that needs special hardware and is out of scope here.

    Encryption at rest, layer by layer

    Encryption at rest can be applied at four layers. Each layer protects against a different set of people, and the higher the layer, the more of the stack it protects against and the more operational work it creates.

    flowchart TB
  A["Application or table format layer: Parquet columns, Iceberg files"] --> E["Engine-native layer: ClickHouse encrypted disk or codec"]
  E --> O["Object store layer: server-side encryption"]
  O --> D["Disk layer: LUKS or self-encrypting drives"]
  D --> H["Physical NVMe drives in the colo rack"]

    Disk layer

    LUKS (Linux Unified Key Setup) is the standard Linux disk encryption format, implemented by the kernel's dm-crypt. The whole block device is encrypted; LUKS2 defaults to AES (the Advanced Encryption Standard cipher) in XTS mode, a mode designed for disk sectors. The volume is opened at boot with a passphrase, a key sealed in the TPM (Trusted Platform Module) chip, or a key fetched from a network key server, and from then on every process on the host sees plaintext. Self-encrypting drives (SEDs) do the same inside the drive's firmware, often under the TCG Opal standard. A 2019 IEEE Security and Privacy paper reverse-engineered several SSD models and found that many hardware encryption implementations could be bypassed, with the authors advising against relying on drive encryption alone. Disk encryption is cheap and protects against lost, returned or decommissioned drives. It does nothing against someone with root on a running server.

    Object store layer

    Server-side encryption (SSE) means the object store encrypts objects as it writes them and decrypts as it serves them. Three S3 variants exist, and self-hosted S3-compatible stores copy the names:

    • SSE-S3: the store manages the keys itself. AWS has applied it to all new objects by default since January 2023.
    • SSE-KMS: keys are held in a key management service, which allows key policies, audit and separation of duties.
    • SSE-C: the client sends its own key with every request; the store never keeps it. AWS now disables SSE-C by default on new general purpose buckets (rolled out in April 2026); its FAQ says most modern use cases have moved to SSE-S3 or SSE-KMS because they are more flexible. A key that must accompany every request is also hard to share safely across users and services.

    On-prem, Ceph's object gateway implements all three: SSE-KMS with HashiCorp Vault, a KMIP server (KMIP is the Key Management Interoperability Protocol) or OpenStack Barbican as the key store, and SSE-S3 with Vault only. Released versions up to Tentacle (v20.2) encrypt with AES-256-CBC, and the development docs add AES-256-GCM for the next release, Umbrella (as of Oct 2026). SeaweedFS has a -s3.encryptVolumeData flag that encrypts volume data. SSE protects against stolen disks and against someone reading raw volumes on storage nodes, and it is transparent to engines. It does not protect against anyone who holds a valid S3 credential, because the store decrypts for them.

    Application layer: Parquet modular encryption

    Parquet modular encryption encrypts inside the file, on the client, before anything reaches storage. The storage server never sees plaintext data, metadata or keys. Its main properties:

    • Per-column keys. Each column, and the footer, can use its own key, share a key, or stay unencrypted. Investor pan, mobile and bank_account columns can use a "PII" key while nav and units stay readable to analysts.
    • Encrypted footer mode. The footer is encrypted too, hiding the schema and row counts. Files start and end with PARE, and readers without Parquet encryption support cannot open them at all.
    • Plaintext footer mode. Files keep PAR1, so older readers can read the unencrypted columns. Statistics of encrypted columns are moved out of the plain footer, and the footer is signed (a 28-byte nonce and tag) so tampering is detected.
    • Two algorithms. AES_GCM_V1 encrypts every module with AES-GCM, which is authenticated encryption: it detects tampering as well as hiding contents. AES_GCM_CTR_V1 encrypts data pages with AES-CTR, which is faster but unauthenticated, and uses GCM for metadata.
    • Anti-swapping. Each GCM-encrypted module carries additional authenticated data built from a file identifier and the module's position, so pages cannot be swapped between files or row groups unnoticed.
    • Overhead. The design estimates about 1 byte of size overhead per 30,000 bytes of data. Encryption works on whole pages, so AES runs at full speed when the CPU has hardware AES support.

    Table-format layer: Iceberg encryption

    Iceberg builds on Parquet encryption to encrypt a whole table. As of Oct 2026, in the Java implementation:

    • It works with Hive and REST catalogs only, and with Parquet and Avro data files only.
    • It encrypts and tamper-proofs data files, delete files, manifests and manifest lists. The metadata.json file is not encrypted, because it holds no data or statistics. Manifests and manifest lists start with the magic string AGS1 (AES GCM Stream).
    • It is switched on by a catalog property naming the KMS (encryption.kms-type for the built-in AWS, GCP and Azure clients, or encryption.kms-impl for a custom class) and a table property encryption.key-id naming the master key.
    • Each data file gets its own random key, stored in the parent manifest; each manifest's key is stored in the manifest list; the manifest list's key metadata is wrapped by a key encryption key. Release 1.11.0 added built-in KMS envelope encryption and manifest-list encryption, and 1.12.0 made the encrypting FileIO usable as a delegate FileIO.
    • Catalogs must stop anyone changing or removing encryption.key-id, and must protect the integrity of metadata.json, for example by keeping metadata in trusted storage or verifying checksums.

    Two consequences matter. First, there is no built-in client for HashiCorp Vault or OpenBao (an open-source fork of Vault, covered below), so an on-prem deployment needs a custom KeyManagementClient (an interface with wrapKey and unwrapKey methods). Second, every engine that reads the table must support Iceberg encryption. Trino added read-only support in release 483 (July 2026), but its iceberg.encryption.kms-type property accepts only AWS, Azure and GCP, so it cannot use a custom Vault or OpenBao client today, and it blocks writes to encrypted tables. I have not found documentation showing that StarRocks, Doris, ClickHouse or DuckDB can read Iceberg-encrypted tables as of Oct 2026 (a StarRocks pull request to add it was still open), so on-prem I would treat table-level encryption as limiting the table to engines that can load a custom KMS client, in practice Spark, until vendors document support.

    Engine-native layer

    ClickHouse offers two options. An encrypted disk wraps a local or S3 disk and encrypts every file written to it, with AES_128_CTR as the default algorithm; keys are listed in the server configuration with ids, and current_key_id picks the one for new writes while older keys still decrypt. Separately, encryption codecs (AES_128_GCM_SIV, AES_256_GCM_SIV) encrypt single columns at the end of a codec chain. The ClickHouse docs list their caveats plainly: they use a fixed nonce, so identical blocks produce identical ciphertext; index files are written without codecs, so an indexed encrypted column appears in plaintext on disk; and a value used in a WHERE clause can appear in system.query_log. For open-source StarRocks and Doris I could not confirm a shipped native at-rest encryption feature as of Oct 2026 (a transparent data encryption feature is described for VeloDB's commercial Doris build). Plan on disk-level or object-store encryption for them, and ask the vendor.

    Envelope encryption and key management

    Every serious at-rest scheme above uses the same pattern, called envelope encryption. Four terms:

    • A DEK (data encryption key) encrypts the actual data, for example one Parquet file. It is random and usually unique per file.
    • A KEK (key encryption key), or master key, encrypts DEKs. It never leaves the key service.
    • A KMS (key management service) stores KEKs and performs wrap and unwrap operations on request, with access policies and an audit log. An HSM (hardware security module) is tamper-resistant hardware that can hold the KEKs underneath a KMS.
    • To wrap a key is to encrypt it with another key; to unwrap is the reverse.
    flowchart LR
  W["Writer, e.g. Spark job"] --> G["1 Generate random DEK locally"]
  G --> ENC["2 Encrypt file with DEK"]
  G --> K["3 KMS wraps DEK with KEK"]
  K --> S["4 Store wrapped DEK in file or manifest metadata"]
  ENC --> OS["Object store holds ciphertext"]
  S --> OS
  R["Reader, e.g. Trino"] --> U["5 KMS unwraps DEK if policy allows"]
  OS --> R
  U --> DEC["6 Decrypt file locally"]

    Why this shape: bulk data is encrypted locally at full CPU speed, and only small keys travel to the KMS. Rotating the KEK does not require rewriting data, because only the wrapped DEKs need to be re-encrypted (re-wrapped) under the new KEK version. And a per-file DEK limits the damage if one key leaks.

    On-prem, the usual KMS is HashiCorp Vault or OpenBao, its open-source fork hosted at the Linux Foundation after Vault moved to the Business Source License in 2023. Their Transit secrets engine is "encryption as a service":

    • Named keys with versions. Ciphertext carries the version in a prefix such as vault:v1:, so the service knows which version to use for decryption. The default key type is aes256-gcm96.
    • rotate adds a new key version for future encryptions; old versions still decrypt.
    • rewrap re-encrypts an existing ciphertext under the newest version without revealing the plaintext to the caller. This is how wrapped DEKs move to a new KEK version.
    • min_decryption_version archives older versions so they can no longer decrypt; it can be moved back in an emergency. trim deletes older versions permanently.
    • A datakey endpoint returns a fresh DEK, both plaintext and wrapped, or wrapped only.
    # OpenBao CLI (Vault uses the same paths with the vault command)
bao write -f transit/keys/lake-kek                    # create the KEK
bao write -f transit/datakey/plaintext/lake-kek       # DEK: plaintext + wrapped copy
bao write -f transit/keys/lake-kek/rotate             # new KEK version for new wraps
bao write transit/rewrap/lake-kek ciphertext="vault:v1:..."   # move a wrapped DEK to the latest version
# Only after every wrapped DEK is on the new version:
bao write transit/keys/lake-kek/config min_decryption_version=2

    Three kinds of rotation are often confused. KEK rotation is cheap: new version, re-wrap the DEKs, data untouched. DEK rotation means re-encrypting data, which for a lake means rewriting files (an Iceberg rewrite produces new files with new keys). Credential rotation (passwords, access keys, certificates) is a separate process again.

    Separation of duties means no single person can both reach the encrypted data and use the key. Typical split at a firm of this size: the platform team runs storage and engines; a security or key-custodian role administers the KMS and its policies; data owners (fund operations, compliance) approve who may decrypt PII columns; destructive key operations (deleting or trimming a key) need two people. The KMS audit log records every unwrap, which is often the most useful evidence in an access review.

    Incident

    Symptom. After a planned power maintenance in the colo, every server comes back, but queries on encrypted tables fail with key errors and object reads under SSE-KMS return errors. Unencrypted tables work. Diagnosis. The KMS cluster restarted sealed: Vault and OpenBao start in a sealed state and cannot unwrap anything until unsealed with key shares or an auto-unseal mechanism. Nobody with unseal shares was on call. Readers with cached DEKs worked briefly, then failed as caches expired. Fix. Unseal with the custodians, then add an auto-unseal mechanism where the edition supports one (an HSM, or a separate KMS), a written unseal runbook with named people per shift, KMS health in the platform dashboard, and a startup order so engines wait for the KMS. Run the KMS as a 3 or 5 node cluster across failure domains. Lesson. Once data is encrypted, the KMS sits on the read path of every query. It is a tier-0 dependency and needs the same availability design as the database itself.

    Incident

    Symptom. Weeks after a scheduled KEK rotation, an auditor asks to reproduce a NAV from last quarter. Time travel to that Iceberg snapshot fails with decryption errors, and restoring last month's backup fails the same way. Current data reads fine. Diagnosis. The rotation runbook rotated the key and then raised min_decryption_version to the new version immediately. Current files had been rewritten by compaction with new wrapped keys, but older snapshots and backups still referenced DEKs wrapped under the old KEK version, which could no longer decrypt. Fix. Lower min_decryption_version back (possible only because the old version had not been trimmed), then re-wrap every wrapped key the table metadata and backups reference, verify reads of the oldest retained snapshot, and only then archive the old version. Lesson. Rotation is rotate, re-wrap everything, verify, then retire. Never trim a key version until you can prove nothing that must remain readable (snapshots, backups, archives) still depends on it.

    In transit: TLS everywhere, mTLS between nodes

    TLS (Transport Layer Security) encrypts a network connection and proves the server's identity with a certificate signed by a certificate authority (CA) the client trusts. mTLS (mutual TLS) adds a client certificate, so both sides prove who they are. Inside a private colo, an internal CA issues the certificates.

    Count the hops in the design. Each is a separate place where plaintext could travel:

    flowchart LR
  U["Analysts, BI, AI agents"] --> FE["Engine front end, MySQL protocol or HTTPS"]
  FE --> N["Engine nodes, shuffle and replication"]
  N --> OS["Object store S3 API"]
  N --> CAT["Iceberg REST catalog"]
  N --> KMS["KMS for key unwrap"]
  P["Prefect workers"] --> OS
  P --> CAT
  P --> FE
    • Clients to engines. StarRocks and Doris speak the MySQL protocol; ClickHouse's default TLS ports, once TLS is configured, are 9440 for the native protocol and 8443 for HTTPS.
    • Node to node. Shuffles, replication and metadata traffic between engine nodes. ClickHouse has a TLS inter-server port (9010) and secure Keeper ports. For each engine, check which internal channels support TLS; where one does not, isolate that traffic on a dedicated network segment and record the gap.
    • Engines to the object store. The S3 API over HTTPS. This hop carries the most data and is the one most often left on plain HTTP "because it is inside the rack".
    • Engines to catalog and KMS. REST over HTTPS; these carry credentials and keys, so mTLS fits well.

    Certificates expire, and expiry is the most common TLS outage. Automate issuance and renewal (cert-manager on Kubernetes, or the PKI engine of Vault or OpenBao), keep lifetimes short, and alert well before expiry. One on-prem gotcha: S3 clients default to virtual-hosted-style URLs (bucket.s3.lake.local), which need a wildcard DNS record (or one record per bucket) and a wildcard certificate. Many self-hosted setups use path-style URLs instead (s3.lake.local/bucket); Iceberg's S3 client has s3.path-style-access for this.

    # First checks when a TLS connection fails (the TLS version of nc -zv and ssh -vvv)
openssl s_client -connect s3.lake.local:443 -servername s3.lake.local -showcerts
curl -v https://s3.lake.local/    # handshake and HTTP status from a plain request
openssl x509 -in node.crt -noout -subject -issuer -dates -ext subjectAltName
    Field notes
    • Most TLS failures are one of four things: expired certificate, hostname not in the certificate's subject alternative names, client missing the internal CA in its trust store, or a TLS-terminating load balancer forwarding plain HTTP to a backend that expects HTTPS.
    • Runtimes keep separate trust stores. Java engines (Trino, Spark, the StarRocks and Doris front ends) read the Java trust store, and many Python clients read their own CA bundle. Adding the internal CA to the operating system alone leaves some clients failing, which is confusing until you know it. Add the CA to every runtime image.
    • Ceph's object gateway requires HTTPS for server-side encryption requests, so keys and secrets are never sent in plaintext; behind a TLS-terminating load balancer it must be told to trust forwarded HTTPS.

    Compress, then encrypt, and what encryption really costs

    Good encryption output looks like random bytes. Random bytes have no repeated patterns, so a codec run after encryption finds nothing to remove. The order is therefore always encode, then compress, then encrypt. Parquet does exactly this per page; ClickHouse's docs say encryption codecs only make sense at the end of a codec chain (for example CODEC(Delta, LZ4, AES_128_GCM_SIV)); and object-store SSE encrypts Parquet files that were compressed by the writer. Two practical consequences: compressing encrypted backups or encrypted volumes wastes CPU, and a dataset encrypted as a whole file before landing (common with files exchanged with outside parties) must be decrypted before any engine can read its columns.

    There is one subtle exception worth knowing. Compressing secret data together with attacker-controlled data can leak the secret through the compressed size. That is how the CRIME and BREACH attacks worked against compressed TLS and HTTP, and TLS 1.3 removed compression for this reason. It rarely matters for lake files, but it is a good answer to a "why not compress after" follow-up.

    The CPU cost of AES is usually modest. Modern x86 and ARM server CPUs have AES instructions (AES-NI on x86), and Parquet encrypts whole pages so AES runs at full speed. The Parquet design notes that overhead depends on whether AES runs in hardware or software. To get a real number, measure the actual servers with openssl speed -evp aes-256-gcm. My rule of thumb, from practitioner experience: on hardware with AES instructions, encryption is rarely the bottleneck next to decompression and query work.

    The real costs are operational:

    • Key availability. Every read of encrypted data needs an unwrap, so a KMS outage blocks reads (see the incident above).
    • KMS request volume. Illustrative arithmetic: a query that touches 20,000 Parquet files, each with its own wrapped DEK, needs 20,000 unwraps unless keys are cached. Caching DEKs in engine memory with a time limit reduces load; Ceph's development docs (for the release after Tentacle) describe an object gateway KMS secret cache with separate TTLs for hits, misses and transient errors for the same reason. In the cloud, S3 Bucket Keys exist to cut SSE-KMS calls.
    • Tool compatibility. Encrypted footers lock out readers without encryption support, and Iceberg encryption is limited to Java engines today (Trino 483 reads it only with cloud KMS types).
    • Debuggability. You cannot inspect an encrypted file with parquet_metadata unless the tool has the keys. Build a keyed diagnostic tool before you need one.
    Common mistake

    Saying "the data is encrypted at rest, so the AI agent cannot leak PII". Server-side and disk encryption decrypt for any authorised caller, and an agent running under a broad service account is an authorised caller. Encryption at rest answers stolen media and storage-level access. Agent safety comes from identity, least privilege, masking, row filters and audit.

    Governed access for AI agents, and the compliance angle

    "internal AI agents" means software agents querying the lake on behalf of people. The controls that make that safe sit beside encryption:

    • Identity per agent. Each agent gets its own service identity, and each request carries the human it acts for. No shared "ai_user" account.
    • RBAC (role-based access control): roles per desk, fund and function, granted to people and agents. The credit-research agent gets read access to loan cash flows and structured-credit documents, nothing on investor records.
    • Column masking: a policy that returns a masked value (for example only the last four characters of a PAN) unless the caller holds an unmasking role.
    • Row policies (row-level security): a filter added to every query for a given role, such as book IN ('CREDIT'). ClickHouse implements this with CREATE ROW POLICY; other engines and policy tools such as Apache Ranger provide equivalents; check each engine version.
    • Audit logs: every query recorded with agent id, on-behalf-of user, purpose and tables touched, shipped to a store the platform team cannot edit.
    • Guardrails: resource groups or workload limits, row limits, timeouts, and read-only connections, so an agent's runaway query cannot starve the morning risk run.
    • The catalog as a policy point. REST catalogs can decide which tables a caller may load and hand out scoped storage credentials (Polaris has its own RBAC; Lakekeeper uses OpenFGA for authorisation, as of Oct 2026).

    Compliance in one breath: SEBI's Cybersecurity and Cyber Resilience Framework (circular of 20 August 2024, with later clarifications) applies to SEBI-regulated entities including AIFs and mutual funds and includes data protection controls such as encryption. SEBI has also amended its Intermediaries Regulations and its stock exchange and clearing corporation regulations (notifications dated early February 2025) so that registered intermediaries and market infrastructure institutions using AI or machine learning tools are solely responsible for the tools' output, for the privacy, security and integrity of the investor data they use, and for legal compliance.

    Senior lens

    A senior engineer starts from the threat model and the operating cost, and adds layers only where a named threat justifies them. A defensible baseline: LUKS on every disk (stolen and returned drives are the likeliest physical risk in a vendor colo), SSE-KMS on the object store with a highly available OpenBao or Vault cluster, TLS on every hop with automated certificates and mTLS for service-to-service traffic, and Parquet column encryption only for a short list of PII columns in investor data. Iceberg table encryption is attractive for "storage admins must not read anything", but today it narrows engine choice to Java and needs a custom KMS client on-prem, so it belongs in a later phase after a proof of concept. The people side matters as much: a key custodian role separate from platform admins, two-person rules for destructive key operations, rotation runbooks tested on a copy, and unseal procedures drilled like a database failover. Finally, keep encryption and access governance as two separate workstreams in the plan, because the AI programme's risk lives mostly in the second.

    Say this

    "I'd start from the threat model. Disk encryption with LUKS covers drives that leave the colo; object-store encryption with keys in a KMS covers raw access on storage nodes; Parquet column encryption covers storage admins for the few PII columns that need it; TLS and mTLS cover the network. None of those stops a caller with valid credentials, so for AI agents the controls are per-agent identity, RBAC, masking, row policies and audit logs. Underneath, I'd use envelope encryption: per-file data keys wrapped by a master key in OpenBao or Vault, so rotating the master key only re-wraps the small data keys and leaves the data files untouched. The big operational risk is key availability: the KMS is on the read path of every query, so it needs three or five nodes, an unseal plan and monitoring. I haven't run Vault or OpenBao myself; the same rules carry over from managed secret stores: no keys in code, scoped access, one integration point and a tested rotation."
