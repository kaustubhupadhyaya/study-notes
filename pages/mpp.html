MPP Performance

Scaling compute and storage independently, and the factors that decide how fast a massively parallel query runs.

    Independent scaling of compute and storage

    Independent scaling means you can add CPU without buying disks, and add disk without buying CPU. It is the central promise of the shared-data modes in StarRocks and Doris, and it is the reason Snowflake felt elastic when you used it. The business cares because its load is spiky (month-end NAV, risk runs, backtests, AI agents firing ad-hoc SQL) while its hardware is a fixed set of colo racks, so the design decides how well that fixed pool is used.

    Start from what you know: the words

    Every database has two kinds of resource. Compute is the CPU cores and RAM that run query operators such as scans, joins and aggregations. Storage is where the bytes of a table live durably, so that they survive a crash or a reboot. A single Postgres server holds both in one box. When a Postgres table with 50M+ records needs more speed, the options are a bigger box (scale up, also called vertical scaling) or better schema, indexes and partitions.

    An MPP database (massively parallel processing) spreads one table across many servers, called nodes, and runs each query on all of them at once. Adding nodes is scale out; removing them is scale in. The next section explains how an MPP query runs. Here the question is narrower: when you add a node, what are you forced to add with it?

    Two families answer that differently.

    • Shared-nothing: each node owns a slice of the data on its own local disks and shares no disk and no memory with other nodes. Stonebraker named and argued for this design in 1986. Classic Redshift (DC2 nodes), StarRocks and Doris in their default mode, and open-source ClickHouse all work this way.
    • Shared-data (also called shared-storage; Doris calls it compute-storage decoupled mode): the durable copy of every table lives in one shared store, usually object storage, and the compute nodes keep only a cache. Snowflake was built this way from the start. Redshift RA3 with Redshift Managed Storage moved to it. StarRocks and Doris offer it as a second deployment mode.

    A few more terms you will need. StarRocks and Doris run two kinds of server process: FE (frontend) nodes parse and plan queries and hold metadata, and BE (backend) nodes store data and execute queries; in StarRocks shared-data mode a CN (compute node) does a BE's query work without owning data. A tablet is the unit StarRocks and Doris cut a table into: one bucket of one partition. It is roughly what a Spark partition is to a DataFrame, with one difference that matters here: a tablet is also the unit of placement (which node holds it) and of replication. A replica is a copy of a tablet on another node, usually three in shared-nothing. Object storage is a store you reach over HTTP with the S3 API (PUT, GET with byte ranges, LIST, DELETE): AWS S3, or on-prem Ceph RGW, SeaweedFS and similar. A stateless compute node is a node whose loss loses no data, because nothing durable lives on it. A metadata service is the component that knows which tablets and files make up each table version and where they are.

    Why shared-nothing ties compute to storage

    In a shared-nothing cluster a tablet lives on a node's local disk, and three replicas live on three different nodes. The planner sends the scan for that tablet to a node that holds it. This gives the design its strengths: scans read local NVMe with no network hop, latency is predictable, and the stack is simple because there is no separate storage system to run.

    The coupling follows directly. If you need more disk, you add a node, and that node comes with CPUs and RAM whether you need them or not. If you need more CPU for one night, you add a node, and the cluster must copy tablets onto it before it can help, because a node can only scan what it holds. That copying is rebalancing (also called tablet migration). Removing a node (decommission) means copying its tablets off first. Losing a node means re-creating its replicas elsewhere. In every case the same nodes that answer queries also move the data.

    A worked example makes the cost concrete. Take 6 BE nodes holding 12 TB of compressed data with 3 replicas: 36 TB on disk, 6 TB per node. Add 2 nodes and the balancer aims for 36 / 8 = 4.5 TB per node, so the two new nodes must receive 9 TB over the network. If the balancer is throttled to an effective 1 GB/s so that queries stay usable, that is about 9,000 seconds, or two and a half hours, before the new CPUs carry their full share. These are illustrative numbers; the arithmetic is the point.

    The 2016 Snowflake paper lists three problems with this coupling: one hardware shape must serve very different workloads (bulk loads want I/O, complex queries want CPU), membership changes force large reshuffles that hurt running queries (the same nodes both move data and answer queries), and online upgrades are hard because everything is tightly coupled and expected to be homogeneous. The same paper adds a remark that matters on-prem: on-premise, with a small fixed pool of nodes, these issues can usually be tolerated, because resizes, failures and upgrades are rare.

    Field notes
    • Rebalancing is never free. Operators throttle it and schedule node additions for quiet hours, which means "add a node for month-end" has to start hours or days early in a shared-nothing cluster, depending on how much data must move.
    • StarRocks colocate joins depend on stable placement. While tablets of a colocation group are being repaired or migrated, the group is marked Unstable and colocate joins silently degrade to ordinary joins; EXPLAIN shows colocate: false, reason: group is not stable. A node failure can therefore make a well-designed join slow until the repair finishes, which can take hours.
    • Three replicas triple your disk bill. My judgement: at this scale (under 40 TB) this is affordable on NVMe, which is one reason shared-nothing stays a serious option.
    • Disk-full on one node usually means skew (one huge tablet), and the fix is a better bucket key, which is a table rewrite.

    How shared-data separates them

    Shared-data splits the system into three layers that scale on their own.

    1. Metadata and planning. In StarRocks the FE nodes plan queries and keep metadata, exactly as in shared-nothing. In Doris decoupled mode the FE plans and a stateless Meta Service keeps metadata in FoundationDB, a separate distributed key-value store you must also run.
    2. Stateless compute. StarRocks replaces BEs with CN (compute node) processes that do everything a BE does except own data. Doris keeps the name BE, but in decoupled mode a BE holds no primary data. Losing one loses only its cache.
    3. Shared storage. Object storage (or HDFS) holds the only durable copy. Durability and replication become the object store's job, so the compute layer stops keeping three replicas.

    Two mechanisms make this fast enough to use. The first is a local cache on each compute node, in RAM and on local NVMe. StarRocks describes a tiered read path: memory, then local disk, then object storage; when the cache is hit, its docs say performance is comparable to shared-nothing. The second is a stable assignment of tablets (or files) to compute nodes, so the same node reads the same data each time and its cache stays useful. Snowflake does this with consistent hashing over table file names, and does it lazily: when nodes are added, no data moves; the cache contents shift over the next queries through LRU (least recently used) eviction.

    The write path changes too. A load commits by writing new files to object storage (StarRocks also writes them to the local cache when caching is enabled). Commits now pay object-store latency, and every load creates objects, so small frequent loads become a request-rate and compaction problem as well as a version-count problem.

    Elasticity on a fixed set of racks

    Elasticity is the ability to change compute capacity quickly and pay (in money or in hardware) only for what you use. In shared-data, StarRocks documents that CN nodes can be added or removed within seconds with no data rebalancing. Typical reasons at a fund: month-end NAV and investor statements, the month-end risk run with all its scenarios, a quarter-end valuation of structured-credit loans, or a research team's ten-year backtest over F&O ticks.

    Snowflake's NSDI 2020 paper gives the only large-scale numbers I know of, from 70 million queries over 14 days. About 20% of clusters used elasticity, and in those the node count changed by as much as two orders of magnitude. Average utilisation was low: roughly 51% CPU, 19% memory, 11% network transmit and 32% network receive. That is the cloud case: rent compute for the spike, release it after.

    the on-prem case is different, and saying so shows judgement. With colo racks bought from a dedicated-hardware vendor, there are no spare nodes to rent at 6 p.m. on the last business day. What shared-data still buys on fixed hardware:

    • Moving a fixed pool between jobs. If CN pods run on the same Kubernetes cluster as Prefect workers, capacity can shift from daytime dashboards to overnight batch by time of day.
    • Failure without re-replication. A dead CN loses its cache only; nothing has to be copied before the cluster is whole again.
    • Storage growth on cheaper nodes. Object-store nodes with large HDDs grow the 40 TB lake without buying more query CPUs.
    • Isolation. Separate compute pools over the same data, covered next.
    • Easier rolling upgrades, because compute nodes hold nothing durable.
    Senior lens

    At under 40 TB on owned hardware, the elasticity argument for shared-data is weaker than vendor material suggests; the Snowflake authors say as much about on-premise pools. My view: choose shared-data on-prem for isolation, failure handling and lake integration, and only after measuring the cache-miss penalty on your own queries. The cost side is real: you now operate an object store, possibly FoundationDB, and a cache tier, and someone must be on call for each. A reasonable middle path is hot, latency-critical tables (today's positions, risk, NAV) in native tables on local NVMe, with history in Iceberg on object storage, queried by the same engine. Decide with measured p95 latency (the 95th-percentile query time) per workload class.

    Workload isolation: warehouses, compute groups, resource groups

    Workload isolation means one workload cannot slow another. The failure it prevents is the noisy neighbour: a backtest scanning five years of ticks makes the portfolio manager's 9:15 a.m. position dashboard crawl. There are two strengths of isolation.

    • Hard isolation: separate machines. Snowflake runs each query on exactly one virtual warehouse and does not share worker nodes across warehouses, so one warehouse cannot steal another's CPU. You saw the warehouse choice when you integration-tested your query tagging on the SMALL warehouse [01].
    • Soft isolation: one pool of machines with quotas inside it. Resource groups (StarRocks) and workload groups (Doris) assign CPU weights, memory limits and concurrency caps. They protect against overload, but queries still share caches, disks and network.

ALTER SYSTEM ADD BACKEND 'cn-batch-01:9050'

    Two details from the Doris docs matter. The isolation covers CPU and memory, and peer cache reads (one group reading another group's cache, on by default) weaken network, disk and cache isolation, so the docs say to switch peer reads off on the BEs when strict isolation is needed. Scaling a group also has a warm-up choice for rebalancing (without_warmup, async_warmup, sync_warmup, peer_read_async_warmup; the setting needs Doris 3.1.3 or 4.0.2 and later), which trades time-to-ready against cache misses.

    The new bottlenecks

    Separating compute from storage moves the bottleneck from local disks to the cache, the network and the services in between. A practitioner watches six of them.

    1. Cold versus warm cache

    A cold cache holds none of the data a query needs, so every block comes from object storage. A warm cache holds most of it. The hit ratio is the share of bytes (or requests) served from cache. The hot set, or working set, is the data your queries actually touch in a typical day: today's and recent positions, the last few months of ticks for active symbols, reference data. The gap between cold and warm is set by the latency ladder below.

    So, as a rule of thumb from the table, the first byte from AWS S3 is roughly 100 to 1,000 times slower than from local NVMe, and from a self-hosted store on a LAN perhaps 10 to 200 times slower. Engines hide this by reading large blocks (StarRocks Data Cache loads blocks on the order of megabytes) and by issuing many requests in parallel, because object stores give high aggregate throughput even when each request is slow. That works for big scans. It works badly for selective queries that need many small reads, which is exactly what dashboards and point lookups do.

    2. Cache sizing and hit ratio

    Size the cache from the hot set; total data size only tells you how much object storage to buy. Snowflake reported 60% to 80% average hit rates, depending on query type, with a small amount of local storage, because warehouse access is skewed and repetitive. Redshift's tiered-storage cache uses a two-level clock policy: a block read for the first time enters the lower level, and only blocks accessed repeatedly are promoted to the upper level; my reading is that this keeps one-off scans from flushing the hot set. StarRocks' block cache supports an SLRU (segmented LRU) policy, which its docs say resists one-off sparse traffic evicting hot data. Doris splits its file cache into TTL, index, normal and disposable queues sized by percentages, and recommends TTL caching to keep small hot tables from being evicted by large queries.

    Two StarRocks settings catch people. A table property, datacache.partition_duration, limits caching to recent partitions; set it too short and older partitions are never cached, so every query on them reads remotely. Disk cache size defaults differ by version and by cache type, so set them explicitly. Also note that since v3.3.2 StarRocks deliberately skips cache population for external lake tables (Hive, Iceberg, Hudi, Delta Lake, Paimon) when a query scans all partitions or all columns (unless the table has only one), a built-in guard against full-table scans polluting the cache.

    Illustrative arithmetic (my assumptions, to be replaced with measured numbers): say the hot set is 2 TB compressed and you run 4 CNs, each with 3 TB of NVMe for cache. Each tablet is cached on the node that owns it, so the cluster holds 12 TB of cache, six times the hot set. That headroom absorbs month-end and research spikes without evicting the dashboard data.

    3. Warm-up and prefetch

    A new or restarted compute node starts cold. Three tools fix that before users notice.

    -- StarRocks (v3.3+): pull the columns dashboards use into the cache
CACHE SELECT instrument_id, trade_ts, price, qty
FROM mkt.trades
WHERE trade_date >= '2026-09-01';

-- Doris decoupled: warm a new group from an existing one, or by table
WARM UP COMPUTE GROUP month_end WITH COMPUTE GROUP dashboards;
WARM UP COMPUTE GROUP month_end WITH TABLE positions_daily AND TABLE nav_daily;

    StarRocks runs CACHE SELECT through the normal query path, so it costs about what a query costs; the docs show running it periodically with SUBMIT TASK (for example at 7 a.m. before an 8 a.m. report) and assigning it its own resource group to limit its impact on regular queries. Warmed data can still be evicted later. Redshift reports that ordering rehydration by hotness gives more than 80% local-disk hit rate at only 20% rehydration, which tells you prioritised warm-up matters more than full warm-up.

    4. Network bandwidth

    On cold reads the NIC becomes the ceiling. A 25 GbE port moves at most 3.125 GB/s (25 divided by 8), and in practice somewhat less; a node with a few modern NVMe drives can read local data faster than that (rule of thumb from drive specs). The same NIC also carries shuffle traffic between nodes. My view: 25 GbE is the floor for shared-data compute nodes, and the object-store cluster's aggregate bandwidth (nodes times NIC times disks) must be sized against the worst case of several compute nodes reading cold at once.

    5. Request rates

    AWS documents at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per partitioned prefix, with HTTP 503 Slow Down while it scales. Self-hosted stores publish no such guarantee; the limit is gateway CPU, the metadata or bucket-index layer, and disk IOPS. Small files multiply requests: a scan over 20,000 small segment files is at least 20,000 GETs. Compaction, larger load batches and sensible tablet counts keep request rates in range.

    6. The metadata service and compaction

    Planning needs tablet and file metadata for every partition a query touches. More partitions times more buckets means more metadata to load and more remote calls. StarRocks 4.0 patch releases batched tablet-location lookups during planning to cut remote calls (4.0.5) and removed per-tablet StarOS calls that had stalled the planner (4.0.10), which shows the cost is real. In Doris, FoundationDB becomes a critical system; my reading of the architecture is that if it is unavailable, metadata changes and commits stop.

    Compaction merges many small data files (one set per load) into fewer large ones. In StarRocks shared-data the FE schedules compaction and the CNs execute it. The adaptive default for concurrent tasks is the number of live CNs times 16, and the docs suggest setting compact_threads to about 25% of a node's cores in production. Compaction therefore competes with queries on the same CPUs, and it writes new files that start cold in every cache that did not write them. Doris writes cumulative-compaction output into the file cache by default, which keeps freshly compacted data warm on that node.

    Field notes
    • The StarRocks shared-data FAQ lists four causes of slow queries, in order: cache miss, insufficient compaction, too few tablets for parallelism, and a bad datacache.partition_duration. Start every investigation there.
    • Compaction score is the number to watch on ingestion-heavy tables. The shared-data FAQ says it should stay below about 10. By default, StarRocks shared-data throttles loads into a partition when its score passes 100 and rejects them at 2,000 (defaults since v3.3.6).
    • If every query in one compute pool times out with "Timeout was reached" or "Deadline Exceeded", the shared-data FAQ says to check whether those nodes can reach the object-store endpoint at all. A new rack or VLAN with a missing firewall rule is one typical way this happens.
    • Benchmarks run twice look great the second time. Always record cold and warm runs separately, and report both.
    • Snowflake drops the warehouse cache on suspend. Aggressive auto-suspend saves credits and costs cache; the self-hosted equivalent is scaling compute to zero overnight and paying a cold start at 9 a.m.

    How you measure it

    Measure at three levels: per query (where did this query's time and bytes go), per node (how is each cache doing), and per system (is the object store healthy). The key derived number is the remote-read share: bytes read from object storage divided by all bytes read, per query and per workload class. It is my preferred single metric for "is the cache doing its job", because it measures what the user feels.

    On the Grafana side, a minimal shared-data dashboard has: cache hit rate per node (last minute and last day), remote bytes per second per node, object-store GET rate, p99 GET latency and 503 or error count, compaction score maximum per table, and p95 query latency per resource group. Put the cache hit panel next to the latency panel; when latency jumps and hit rate falls at the same moment, you have your answer in one glance.

    Field notes
    • A query profile is the only honest timing source. Wall-clock time hides whether the time went to remote I/O, CPU, waiting for a scan thread, or the network.
    • StarRocks does not recommend enabling profiles globally for long periods because of overhead; use big_query_profile_threshold to capture only slow queries.
    • Watch hit rate per workload class, not just per node. A healthy cluster-wide 90% can hide a dashboard class at 50%.
    • Alert on change. A hit rate that drops 20 points in ten minutes means something evicted the hot set or nodes were added; a slowly falling hit rate means the hot set outgrew the cache.

    What goes wrong in practice

    Incident

    Symptom. On the last business day of the month a team adds four CNs to a four-CN shared-data cluster at 5 p.m. to speed up the NAV and risk batch. Instead, the batch and the PMs' dashboards both get slower for the next hour. Diagnosis. Adding nodes remaps tablet ownership; roughly half the tablets now belong to the new nodes, whose caches are empty. Profiles show CompressedBytesReadRemote jumping on half the scan instances, and the slowest instance sets the query's time, so every query waits on cold reads. The StarRocks FAQ lists "tablet migration due to elastic scaling" as a cause of cache misses. Fix. Add capacity the morning before, then warm the month-end tables (CACHE SELECT or Doris WARM UP, or a warm-up rebalance mode). Better still, give the batch its own compute group so the dashboard group's cache is never remapped. Lesson. Scale-out takes seconds and warming the new capacity takes much longer, so put warm-up time into the runbook.

    Incident

    Symptom. Monday 9:20 a.m., the positions and exposure dashboards take 8 seconds instead of under 1. Nothing was deployed. Diagnosis. On Sunday a quant ran an unfiltered scan over five years of NIFTY and BANKNIFTY option ticks in the same compute pool. The Grafana cache panel shows the hit rate falling from the high 90s to about 40% overnight and eviction counters spiking; Monday's dashboard queries read remotely. A plain LRU cache lets one huge scan push out the hot set. Fix. Move research to its own compute group or cluster; add a resource group with big_query_scan_rows_limit for anything left in the shared pool; protect small hot tables with Doris TTL cache or a scheduled warm-up; prefer engines and settings with scan-resistant eviction (SLRU, two-level clock). Lesson. A cache needs admission control as much as a queue does.

    Incident

    Symptom. After backfilling three years of MCX commodity ticks with thousands of small INSERT jobs, queries on that table are slow and new loads begin to stall. Diagnosis. Each load created new files per tablet. information_schema.partitions_meta shows maximum compaction scores in the hundreds; profiles show huge SegmentsReadCount; object-store GET rates are high. Compaction runs on the same CNs as the queries and cannot catch up. Load throttling kicks in at the default threshold. Fix. Re-run the backfill as fewer, larger batches per partition; trigger manual compaction partition by partition overnight; raise compaction threads temporarily. Lesson. In shared-data, small files cost three times: in versions, in object-store requests and in cold cache.

    Common mistake

    Treating "stateless compute" as "instant speed". Adding nodes adds CPU immediately and adds cache misses immediately; whether the query gets faster depends on whether it was CPU-bound or I/O-bound. A related mistake is benchmarking a shared-data POC only on warm runs and then being surprised in production at 9 a.m. after an overnight restart. Measure cold, warm and "after a big scan" runs separately.

    What defines performance in an MPP database

    An MPP database splits every query into pieces that run on many nodes at once, and the query is only as fast as its slowest piece. Performance therefore comes mostly from decisions you make before any query runs: how tables are partitioned, bucketed and sorted, how joins move data, how fresh the statistics are, and how loads arrive. The choice between ClickHouse, Doris and StarRocks, and the table designs for ticks, positions and NAV, will be judged on exactly these factors.

    How an MPP query runs

    You know this shape from Spark. A Spark job is split into stages, and stages are separated by shuffles. An MPP engine does the same with different names.

    • The coordinator parses the SQL, optimises it and builds a distributed plan. In StarRocks and Doris this is the FE; in ClickHouse it is the server that received the query (the initiator); in Trino it is the coordinator node.
    • The plan is cut into plan fragments. A fragment is a chain of operators that can run without moving data between nodes. Each fragment runs as several fragment instances, usually one or more per node.
    • Fragments are joined by exchange operators. An exchange sends rows from one fragment's instances to the next. It can shuffle (send each row to the instance chosen by hashing a key), broadcast (send every row to every instance) or gather (send everything to one instance).
    • Inside a fragment, StarRocks and Doris use a pipeline engine: operators are chained into pipelines, and each pipeline runs as several drivers on a fixed thread pool. The number of parallel drivers per node is the degree of parallelism (DOP).

    Take this query: total traded value per symbol on 30 September.

    SELECT symbol, SUM(price * qty) AS traded_value
FROM mkt.trades
WHERE trade_date = '2026-09-30'
GROUP BY symbol;
    1. The FE prunes to the one partition for 30 September and finds its tablets.
    2. Fragment 1 runs on every node that owns one of those tablets: scan, filter, then a partial aggregation that sums per symbol over the local rows only.
    3. An exchange shuffles the partial sums by hash of symbol, so all partial sums for RELIANCE land on the same instance.
    4. Fragment 2 does the final aggregation: it merges the partial sums for each symbol.
    5. A gather sends the final rows to the coordinator, which returns them.
    flowchart LR
  Q["SQL from client"] --> FE["FE parses and builds cost-based plan"]
  FE --> A["Node A scan and partial sum"]
  FE --> B["Node B scan and partial sum"]
  A -->|"shuffle by symbol"| F1["Final sum instance 1"]
  B -->|"shuffle by symbol"| F1
  A -->|"shuffle by symbol"| F2["Final sum instance 2"]
  B -->|"shuffle by symbol"| F2
  F1 --> G["Gather at coordinator"]
  F2 --> G
  G --> R["Result rows"]

    Two differences from Spark matter in interviews. Most MPP engines stream exchange data through memory and restart the whole query if a node dies, while Spark writes shuffle files to disk so it can retry one stage; MPP trades fault tolerance for latency (Trino's optional fault-tolerant execution mode is an exception that spools exchange data). And the engines differ in how freely they shuffle. ClickHouse's Distributed table sends the query to every shard, lets each shard do partial work (including partial aggregation), and merges intermediate aggregate states on the initiator. For an ordinary JOIN or IN against a Distributed table, each shard evaluates the right side against its own local data; GLOBAL JOIN and GLOBAL IN instead run the right side once on the initiator and send it to every shard as a temporary table, which is a broadcast. StarRocks and Doris plan general shuffles between any fragments. My view, which most practitioners share: ClickHouse is excellent at scan-and-aggregate over one large table, and needs more careful modelling (denormalisation, co-sharding, dictionaries) when two large tables must be joined.

    Data layout

    Partitioning and pruning

    A partition is a coarse slice of a table, usually by date: one partition per trading day for ticks, one per month for slower data. Partition pruning means the planner skips partitions a filter rules out. The same idea appears in Postgres, and Snowflake's query profile shows the same thing as "partitions scanned" against "partitions total" for its micro-partitions. In StarRocks EXPLAIN it appears as partitions=1/1250. A query that says partitions=1250/1250 when the user asked for one week is the first thing to fix, usually because the filter wraps the partition column in a function or casts it.

    Bucket key, skew and tablet size

    Inside a partition, rows are split into buckets by hashing a bucket key (Redshift calls it the distribution key). Each bucket of each partition is one tablet. The bucket key decides three things: how evenly work spreads, whether a filter on the key can skip buckets (bucket pruning), and whether joins and aggregations on that key can avoid a shuffle.

    Data skew is uneven distribution: one bucket holds far more rows than the others, so one instance does far more work. StarRocks' bucketing guide gives three rules of thumb: pick a key whose number of distinct values is about 1,000 times the number of nodes; aim for 1 to 10 GB per bucket; re-shard before tablets pass 5 to 10 GiB. The shared-data FAQ suggests bucket count as total data size divided by 1 to 5 GB. Too few tablets starve parallelism (eight nodes cannot all work on a partition with two tablets); too many tiny tablets inflate metadata, planning time, file counts and, in shared-data, object-store requests.

    StarRocks also offers random bucketing: rows are spread randomly across buckets, so storage skew is avoided by design, and tablets can split automatically as they grow (v3.2+, with the bucket_size property). The price is no bucket pruning, no colocate join and no bucket-shuffle join. It suits log-like tables nobody joins on a key.

    Sort key and indexes

    The sort key orders rows inside each tablet. StarRocks sets it with ORDER BY (Primary Key tables since v3.0, other table types since v3.3); ClickHouse's ORDER BY plays the same role and defines its primary index. Sorting matters because three lightweight indexes depend on it:

    • The prefix index (StarRocks; also called the short key index): one entry per 1,024 rows holding the leading sort-key values, at most 36 bytes and at most three columns. A string column can appear only once and ends the prefix (it is truncated to fit), so put fixed-width columns first. ClickHouse's sparse primary index is the same idea with one entry per 8,192 rows by default (index_granularity).
    • Zone maps: min and max per column per data page or segment, created automatically. A filter like trade_ts BETWEEN '09:15' AND '09:20' skips every page whose range does not overlap. Zone maps only help on columns that are clustered, which usually means sort-key columns.
    • Optional indexes: a bloom filter index answers "is this value possibly here?" for high-cardinality equality filters on non-sort columns (an order ID or ISIN); a bitmap index suits low-cardinality columns (side, exchange segment, option type).

    The sort key is a trade-off between query shapes. Ticks sorted by (instrument_id, trade_ts) make "all trades in NIFTY 25000 CE this morning" a tight range read. The same order makes "every trade between 09:15:00 and 09:15:05 across the market" weak, because each segment holds a full day's time range for its instruments. Pick the order for the queries that pay the bills, and serve the other shape with a materialised view or a second projection.

    Field notes
    • Bucket key and bucket count are effectively permanent. Changing them means rewriting the table (create new table, INSERT SELECT, swap names), so most of the performance budget is spent at CREATE TABLE time.
    • The classic mistake is bucketing by the column people filter on most, such as trade_date or an underlying like NIFTY. Low cardinality plus a popular value gives one hot tablet. Filter columns belong in the partition or sort key.
    • Check skew before choosing a key: count rows per candidate key value for a heavy day (expiry day for F&O) and look at the largest value's share.
    • After loading, compare tablet sizes with SHOW TABLET FROM db.table; a few tablets far larger than the median is skew you will feel in every query.

    Storage and I/O

    Columnar storage keeps each column's values together on disk, so a query reading 4 of 40 columns reads roughly a tenth of the bytes. Parquet (for Iceberg) and the native segment formats of StarRocks, Doris and ClickHouse all work this way. Within a column, two layers shrink data further.

    • Encoding uses the structure of the values. Dictionary encoding replaces repeated strings (symbols, book names) with small integers. Run-length encoding stores "BUY repeated 4,000 times" once. Delta encoding stores differences between sorted values, which suits timestamps and sequence numbers. Bit-packing stores small integers in few bits. Parquet adds BYTE_STREAM_SPLIT, which rearranges float bytes so prices compress better.
    • Compression then applies a general codec to the encoded bytes. LZ4 decompresses very fast with a moderate ratio; ZSTD compresses tighter at more CPU cost. Iceberg's Java default for Parquet is zstd (as of Oct 2026). My rule of thumb: when data comes over the network from object storage, the better ratio usually wins, because fewer bytes travel; for hot data on local NVMe, decode speed matters more.

    Two execution tricks cut I/O further. Predicate pushdown evaluates filters inside the storage layer, so pages that fail are never decoded. StarRocks' tuning guide flags pushdown failure when its PushdownPredicates count stays near zero while ExprFilterRows is high; leading-wildcard LIKE and long OR chains are common causes. Late materialisation reads the filter columns first, then fetches the remaining columns only for rows that survived. A query that filters 200 million ticks down to 50,000 rows should read the wide columns for 50,000 rows only.

    Sources: Parquet encodings · Iceberg configuration · StarRocks tuning recipes

    Execution

    Vectorised execution means each operator processes a batch of rows per call, with each column held as an array, instead of one row at a time. StarRocks processes chunks of up to 4,096 rows. Batches let the CPU use SIMD (single instruction, multiple data) instructions, which apply one operation to several values at once, and they keep data in CPU caches. This is a major reason modern engines beat older row-at-a-time engines on the same hardware.

    Parallelism within a node is the DOP. StarRocks' pipeline_dop defaults to 0, which means automatic; its docs suggest half the physical cores if you fix it. More DOP helps a single big query and hurts when many queries compete, which is why concurrency and DOP are tuned together.

    Memory decides whether big operators finish. Hash joins and hash aggregations build hash tables in RAM. StarRocks' query_mem_limit (per query, per node) defaults to 0, meaning no per-query limit, so the effective limits are the resource group's mem_limit and the process limit. Doris has exec_mem_limit, whose default has changed across versions. When an operator outgrows memory, the engine either fails the query or spills: writes part of its state to local disk and processes it in pieces. Spill is off by default in both StarRocks (enable_spill, v3.0+) and Doris. With StarRocks spill_mode = auto and no resource groups in use, spilling starts when a query passes 80% of query_mem_limit; with resource groups, the group's spill_mem_limit_threshold also applies. Spill keeps queries alive and makes them slower; treat it as a safety net and size memory so it rarely triggers.

    Runtime filters are the most underrated feature. While a hash join builds its hash table from the small side, the engine collects the join keys into a filter (an IN list, a bloom filter or a min-max range) and pushes it to the scan on the big side, which then skips rows and pages that cannot match. StarRocks has local filters for broadcast joins and global filters for shuffle joins (enable_global_runtime_filter, on by default). A join of 200 million trades to 300 positions in one book reads far less when the runtime filter reaches the trades scan.

    Sources: StarRocks tuning recipes · StarRocks session variables · StarRocks resource groups · Doris spill to disk

    Joins and data movement

    A distributed hash join needs matching keys on the same instance. There are four ways to arrange that; the Doris docs give their network cost with T(S) as the row count of the left (probe) table, T(R) that of the right (build) table, and N the number of instances taking part in the join.

    StrategyWhat movesNetwork costWhen it fits
    Broadcast joinThe whole right table goes to every node; the left stays putN × T(R)Right side small after filtering (a symbol master, one book's positions)
    Shuffle join (partitioned)Both sides re-hashed on the join keyT(S) + T(R)Two large tables, keys not aligned with bucketing
    Bucket shuffle joinOnly the right side, sent to match the left table's bucketsT(R)Join key includes the left table's bucket key
    Colocate joinNothing0Both tables in one colocation group: same bucket key types, same bucket count, same replica count

    Broadcast looks cheap until N grows or the "small" table does not stay small, and every node must hold the whole right side in memory. Engines cap it. StarRocks' broadcast_row_limit, a cap on the right side's row count for a broadcast join, defaults to 15,000,000 rows; Trino's join_max_broadcast_table_size defaults to 100 MB and its docs warn that the build side must fit in memory on each node; Spark's spark.sql.autoBroadcastJoinThreshold defaults to 10 MB. Redshift shows the same choice in EXPLAIN: DS_DIST_NONE (collocated, good), DS_BCAST_INNER (broadcast) and DS_DIST_BOTH (both sides shuffled), and AWS's tuning guide calls the last two "not good", usually a sign that tables are not joined on their distribution keys.

    Aggregations move data too. The two-step pattern from the previous example (partial aggregation locally, shuffle, final aggregation) is standard. StarRocks adds three- and four-stage plans for heavy COUNT(DISTINCT). If the table is bucketed by a subset of the GROUP BY columns and the data is colocated, the aggregation can finish in one stage with no shuffle at all. A high-cardinality GROUP BY defeats partial aggregation (every row is its own group), and the profile then shows a huge input row count with little reduction and very large BytesSent at the exchange.

    You can force a strategy with hints, which also disables join reordering for that query:

    SELECT ... FROM trades t JOIN [SHUFFLE] instruments i ON t.instrument_id = i.instrument_id;
-- also [BROADCAST], [BUCKET], [COLOCATE], [UNREORDER]
    Field notes
    • "Accidental broadcast" is the most common join problem: EXPLAIN says BROADCAST and the exchange's BytesSent is enormous. Either the table grew or statistics say it is small when it is not.
    • Colocation is fragile in shared-nothing: when a colocation group is Unstable during repair, joins degrade and EXPLAIN shows the reason. Check colocate: true after any node event.
    • Shuffle skew shows as one instance with a much larger ProbeRows or hash table than the rest. The fixes are a better key or salting (adding mod(id, 16) to spread a hot key), at the cost of an extra merge.
    • In ClickHouse, a JOIN against a Distributed table without GLOBAL gives correct results only when matching keys live on the same shard. Shard both tables on the join key, or accept the broadcast.

    Sources: Doris join strategies · StarRocks join hints · StarRocks session variables · Trino cost-based optimizations · Redshift query plan redistribution · StarRocks colocate join · ClickHouse GLOBAL

    The optimiser and statistics

    A cost-based optimiser (CBO) enumerates plans and picks the cheapest by estimating how many rows flow through each operator, called cardinality estimation. Estimates come from statistics: row counts, distinct counts per column, null counts, min and max, and sometimes histograms for skewed columns. The CBO uses them to choose join order, which side builds the hash table, broadcast versus shuffle, and how many aggregation stages to use.

    Stale statistics are the classic cause of a query that was fast yesterday and slow today with no code change. After a bulk load the table may be ten times bigger than the statistics say; the optimiser then broadcasts it, or builds a hash table from it, or orders joins badly. StarRocks collects statistics automatically; a table counts as unhealthy when its health falls below statistic_auto_collect_ratio (default 0.8), with sampled collection below 0.3. Collection runs on intervals, so a large load can be queried before statistics catch up. Trino goes further: without statistics, its automatic join reordering falls back to only eliminating cross joins, which means the join order is largely the one you wrote.

    -- StarRocks: refresh after a large backfill, and add a histogram for a skewed column
ANALYZE TABLE mkt.trades;
ANALYZE TABLE mkt.trades UPDATE HISTOGRAM ON instrument_id;

    Precomputation and caches

    The fastest query is one whose heavy work already happened. A materialised view (MV) stores the result of a query and refreshes it. StarRocks and Doris have synchronous MVs (rollups, maintained on load, single table) and asynchronous MVs (refreshed on a schedule or on change, can join tables). With query rewrite, the optimiser answers a query from a matching MV even though the user named the base table. ClickHouse's classic (incremental) materialised views are insert triggers that write to a target table, and projections keep an extra sorted or aggregated copy inside the table.

    Good MV candidates on-prem: daily volume and VWAP per instrument from ticks, end-of-day exposure per book and asset class, NAV components per fund per day. These are queried constantly by dashboards and, soon, by AI agents. Poor candidates: ad-hoc research shapes that change weekly. The cost is refresh work and staleness, so each MV needs an owner and a freshness SLA.

    Caches sit at several levels: a page cache of decompressed pages in memory, the data cache for remote blocks (previous section), a query cache that reuses per-tablet partial aggregation results, and result caches that return a whole previous answer. Know each one's invalidation rule before relying on it for anything a regulator might read.

    Sources: StarRocks tuning recipes · CMU 15-721

    Concurrency and workload management

    Single-query speed and many-query throughput are different goals. Admission control decides whether a query may start now, wait in a queue, or be rejected. A resource group (Doris: workload group) assigns queries to a share of CPU and memory based on who sent them. A query queue holds queries when limits are reached.

    StarRocks resource groups match queries with classifiers (user, role, query type, source IP, database, estimated CPU cost) and set CPU weight or exclusive cores, a memory share, a concurrency limit and big-query limits on CPU seconds, scanned rows and memory per node. Query queues are off by default and are enabled per query type (enable_query_queue_select and friends). Without them, a burst of heavy queries all start at once, all compete for memory, and some fail.

    A back-of-envelope capacity model (arithmetic, not a benchmark): 8 nodes with 32 cores each give 256 cores. If a typical dashboard query uses 2 CPU-seconds in total, the cluster can at best complete 128 such queries per second at 100% CPU. Planning for about 60% utilisation gives roughly 77 per second. Measure CPU-seconds per query class from profiles or the audit log, then do this sum for each class.

    AI agents change the picture. An agent writes SQL nobody reviewed, and one bad join can scan the whole tick history. My view: put agent traffic in its own resource group with strict scan-row and CPU-second limits and a short timeout (StarRocks' default query_timeout is 300 seconds), and steer agents to MVs and curated views.

    Sources: StarRocks resource groups · StarRocks query queues · StarRocks session variables · Doris workload groups

    The write path

    Every load into StarRocks or Doris is a transaction that adds a new version (a new rowset of files) to each tablet it touches. Queries must read and merge all versions that compaction has not yet merged, so many small versions mean slow reads. ClickHouse has the same mechanics under a different name: each INSERT creates a part, and background merges combine parts. The compaction score is roughly how many files a query must walk through per tablet; it is the number to watch on ingestion-heavy tables.

    EngineLimit (default)What happens
    StarRocks (shared-nothing)tablet_max_versions = 1000New writes fail with a "too many versions" error. Monitoring guidance: compaction score usually under 100 offline; intervene above 800; above 1000 expect the error
    StarRocks (shared-data)Ingest slowdown at score 100, rejection at 2,000 (since v3.3.6)Loads into a hot partition are throttled, then refused

    The fix is almost always fewer, larger loads: buffer ticks for a few seconds and send one Stream Load per table, use Routine Load with larger batches if Kafka arrives later, or use ClickHouse asynchronous inserts. Fewer buckets on small, frequently loaded tables also helps, because a load with many keys touches most buckets of its partition.

    Upserts add one more cost. StarRocks Primary Key tables keep a primary key index, a hash map from key to row location, loaded into memory during loads so each new row can find and delete its old version. For positions, NAV and investor records that update in place, size memory for that index, or use the persistent index (enable_persistent_index, on by default) on local disk, which shared-data clusters support since v3.1.4, or on object storage, which shared-data clusters support since v3.3.2.

    Hardware

    Hardware sets the ceiling; layout decides how close you get to it. Cores drive scan, decode and hash throughput. RAM holds hash tables, the page cache and the primary key index. NVMe holds the data (shared-nothing) or the cache (shared-data), plus spill. The network carries shuffles, broadcasts and, in shared-data, every cache miss.

    My starting points for an on-prem POC, to be validated with representative queries: identical node specs within one cluster or compute group (the slowest node sets the pace, so a mixed batch of servers from a vendor hurts); 25 GbE or better between query nodes and to the object store; NVMe for cache and spill on separate devices from the OS; memory sized from peak hash-table use seen in profiles, plus the primary key index, plus page cache. The Doris docs recommend a dedicated disk or SSD for spill, and StarRocks' tuning guide treats disk I/O near 80% to 100% during scans as a sign of cold or under-provisioned storage.

    Sources: Doris spill · StarRocks tuning recipes

    Diagnosing a slow query, step by step

    1. Classify it. Is it always slow, or slow at certain times? Sometimes-slow points to concurrency, cold cache or compaction backlog; always-slow points to plan or layout. Check what else was running and which resource group it ran in.
    2. Read the plan (EXPLAIN). Partitions pruned (partitions=), tablets touched (tabletRatio=), join strategies (join op: INNER JOIN (BROADCAST) and the rest), whether runtime filters are built, whether an MV was used, and estimated row counts.
    3. Get the profile. EXPLAIN ANALYZE or a captured profile. Sort operators by time and start with the most expensive one.
    4. Scan checks. Rows read against rows returned; pushdown counts; segments read (compaction); remote bytes (cache).
    5. Skew checks. Compare max against min (or average) for operator time and input rows across instances. One instance at several times the average is skew.
    6. Join checks. Build-side size, hash table memory, exchange bytes sent. A big broadcast or a skewed shuffle shows here.
    7. Memory and spill. StarRocks' guide treats peak memory per node above 80% or spill above 1 GB as red flags.
    8. Estimates against actuals. Large gaps mean statistics; run ANALYZE and re-plan.
    9. Fix the cheapest layer first: rewrite the query, refresh statistics, add a hint or session setting, then an MV, then a layout change (re-bucket, re-sort), and hardware last.

EXPLAIN SELECT ...;                       -- plan: pruning, join types, estimates
EXPLAIN ANALYZE SELECT ...;               -- runs it and returns the profile
SHOW PROFILELIST LIMIT 5;                 -- recent captured profiles
ANALYZE PROFILE FROM '<query_id>';      -- text analysis of one profile
SHOW TABLET FROM mkt.trades;              -- tablet sizes: look for outliers

SELECT instrument_id, COUNT(*) AS n,

    • Practitioners read profiles top-down: total time, then the slowest fragment, then the slowest operator in it, then max against min across its instances. Most problems are visible in the first five minutes.
    • A query that is fast alone and slow in production is a concurrency or cache problem, and tuning its plan will not help.
    • Keep a "before" profile. After any change, compare operator by operator; a fix that moves time from scan to exchange did not fix much.
    • Snowflake's profile shows the same split you will want here: Processing, Local Disk IO, Remote Disk IO, Network Communication, plus bytes spilled locally and remotely.

    Worked example: trades, NIFTY options and a colocated join with positions

    Two tables. mkt.trades holds exchange trade prints for NSE cash and F&O: one row per trade, with the contract (instrument_id), its underlying (underlying, such as NIFTY or RELIANCE), timestamp, price and quantity. pm.positions_daily holds end-of-day net positions per book and contract. A liquidity question joins them: "for each position over the last quarter, what share of that day's traded volume did it represent?"

    For the arithmetic, assume (illustrative numbers, to be replaced with measured ones) 200 million trade rows a day, about 6 GB compressed, an 8-node cluster, and an expiry day on which NIFTY option contracts make up 40% of trade rows.

    Bucket keyBalanceBucket pruning on instrument_id = ?Join with positions
    HASH(trade_id)Perfect: unique keyNone: every bucket scannedNeeds shuffle or broadcast every time
    HASH(underlying)Bad: a few hundred values, and NIFTY's 40% lands in one bucketPartialColocation possible only if positions also hashed by underlying
    HASH(instrument_id)Good: tens of thousands of contracts; check the largest single contract's shareYes: one tablet per partitionColocate with positions hashed the same way

    The skew cost is simple arithmetic. With 8 buckets, a balanced bucket holds 12.5% of the day. Bucketing by underlying puts 40% in NIFTY's bucket, so that one instance does 0.40 / 0.125 = 3.2 times the balanced share, and the whole query takes about 3.2 times longer than it needs to, however many nodes you add. Adding nodes does not help, because the hot bucket is still one tablet.

    Bucket count follows tablet size. At 6 GB per daily partition, StarRocks' 1 to 10 GB guidance suggests at most about 6 buckets (1 GB each); 8 gives one tablet per node for single-day queries at about 750 MB each. That small deviation from guidance is my judgement call for parallelism, and the kind of trade-off you should say out loud.

    -- StarRocks-style DDL (illustrative)
CREATE TABLE mkt.trades (
  trade_date    DATE          NOT NULL,
  instrument_id BIGINT        NOT NULL,
  trade_ts      DATETIME      NOT NULL,
  trade_id      BIGINT        NOT NULL,
  underlying    VARCHAR(32),
  price         DECIMAL(18,4),
  qty           BIGINT
)
PARTITION BY date_trunc('day', trade_date)
DISTRIBUTED BY HASH(instrument_id) BUCKETS 8
ORDER BY (instrument_id, trade_ts)              -- 8 + 8 bytes: fits the 36-byte prefix
PROPERTIES ("colocate_with" = "by_instrument");

CREATE TABLE pm.positions_daily (
  as_of_date    DATE          NOT NULL,
  instrument_id BIGINT        NOT NULL,
  book_id       INT           NOT NULL,
  net_qty       BIGINT
)
PRIMARY KEY (as_of_date, instrument_id, book_id)
PARTITION BY date_trunc('day', as_of_date)
DISTRIBUTED BY HASH(instrument_id) BUCKETS 8    -- same key type, same bucket count
PROPERTIES ("colocate_with" = "by_instrument");

-- the liquidity question
SELECT p.as_of_date, p.book_id, p.instrument_id, p.net_qty,
       SUM(t.qty) AS day_volume,
       p.net_qty / SUM(t.qty) AS share_of_volume
FROM pm.positions_daily p
JOIN mkt.trades t
  ON t.trade_date = p.as_of_date AND t.instrument_id = p.instrument_id
WHERE p.as_of_date BETWEEN '2026-07-01' AND '2026-09-30'
GROUP BY p.as_of_date, p.book_id, p.instrument_id, p.net_qty;

    Check the plan. The StarRocks docs show a colocated join in EXPLAIN like this (abridged):

    |   2:HASH JOIN
|   |  join op: INNER JOIN (COLOCATE)
|   |  colocate: true

    If it says colocate: false with a reason such as group is not stable, a node event broke colocation and the engine fell back to a normal join.

    Now the senior part. Positions for a quarter are small (say 20,000 rows a day, about 1.3 million rows), well under the 15 million row broadcast limit, so a broadcast join would also be fine, and colocation buys little for this query. Colocation earns its keep when both sides are large: trades joined to quotes, lot-level positions, or multi-year P&L attribution. And the cheapest version of this query reads neither raw table: an asynchronous MV of daily volume per instrument (tens of thousands of rows a day) turns a 200-million-row scan into a small join. In an interview, walking from "pick the right bucket key" to "this should be an MV" is what shows judgement.

    Senior lens

    Most MPP performance is decided at CREATE TABLE time, and those decisions are expensive to undo, so a senior engineer spends time on a handful of core tables (ticks, positions, risk results, NAV) and lets everything else default. They set p95 targets per workload class (dashboards, month-end batch, research, agents) and design admission control around them. They distrust vendor benchmarks, because TPC-style single-stream runs on warm caches say little about 9:15 a.m. with 40 concurrent dashboards and a backtest. A POC should run representative real queries, at real concurrency, cold and warm, with loads running. They also think about people: analysts and agents will write bad SQL, so guardrails (resource groups, timeouts, curated MVs, query review for anything scheduled) are part of the performance design. Finally, they tie it to cost: on owned hardware, every node bought for a peak sits idle the rest of the month, so isolation and scheduling are often cheaper than more nodes.

    What goes wrong in practice

    Incident

    Symptom. F&O analytics queries are fine most days and three to four times slower on every weekly expiry day (Tuesday for NSE's NIFTY contracts since September 2025). Adding two nodes changes nothing. Diagnosis. The tick table was bucketed by underlying. The profile shows one scan instance with several times the rows and time of the others, and SHOW TABLET shows one huge tablet per expiry-day partition: NIFTY's. Fix. Rebuild the table bucketed by instrument_id (create, INSERT SELECT, swap), keeping underlying as a filter column in the sort key or a bitmap index. Lesson. The fix for skew is a higher-cardinality key checked against the heaviest day; extra nodes leave the hot tablet exactly as hot.

    Incident

    Symptom. A join that took 2 seconds for months now takes 90 seconds and sometimes fails on memory. Diagnosis. The "instrument master" it joins grew from about 50,000 rows to 30 million after loan-level structured-credit records were added to it. Statistics were stale and still estimated it as small, so the optimiser kept broadcasting it. EXPLAIN shows BROADCAST; the exchange's BytesSent is huge and every node builds a 30-million-row hash table. Fix. ANALYZE the table; with correct statistics StarRocks stops choosing broadcast for it, because broadcast_row_limit caps the broadcast side at 15 million rows by default. Bucket it on the join key to get a bucket-shuffle or colocate join, and split loan-level data into its own table. Lesson. "Dimension tables are small" is an assumption that needs a monitor.

    Incident

    Symptom. The 7 a.m. risk report query slows from 10 seconds to 4 minutes the morning after a large historical backfill. Diagnosis. Profile estimates show the newly loaded table at a fraction of its real size; the optimiser chose it as the build side and reordered joins around a wrong estimate. Automatic statistics collection had not run since the load. Fix. Run ANALYZE TABLE as the final task of every bulk-load flow in Prefect, before downstream reports. Lesson. Statistics refresh belongs in the pipeline, next to data quality checks.

    Incident

    Symptom. A new real-time tick ingester runs fine for an hour, then loads fail with "too many versions" and queries on today's partition slow down. Diagnosis. It issued one INSERT per symbol per second. Each load created a new version on every tablet it touched, faster than compaction could merge them; compaction scores climbed past 1,000. The ClickHouse equivalent is "too many parts". Fix. Buffer for a few seconds and send one Stream Load per table per interval; reduce bucket count on the intraday table; watch compaction score in Grafana with an alert well below the limit. Lesson. Analytic engines want batches; the ingestion design must create them.

    Incident

    Symptom. A researcher's query fails with a memory-limit error: "count trades per second per contract for the year". Diagnosis. The GROUP BY has hundreds of millions of distinct groups. Partial aggregation barely reduces rows, and the final hash table outgrows the resource group's memory share. The profile shows the aggregation's hash table and the query's peak memory rising to the limit. Fix. Short term, enable spill for research sessions (session variables enable_spill = true and spill_mode = 'auto'; the research resource group's spill_mem_limit_threshold can make spilling start earlier). Better, restrict the question (one month, or minute buckets), or precompute per-second counts as an MV. Raising memory limits is the last option, because it lets one query take memory from everyone. Lesson. A memory error on GROUP BY is usually a question-shape problem first and a sizing problem second.

    Common mistake

    Choosing the bucket key by "what do people filter on most". That gives low-cardinality keys like trade_date or underlying and hot tablets. Filter columns belong in the partition key and the sort key; the bucket key should be high-cardinality, stable, and ideally the key you join or aggregate on. The second common mistake is adding nodes to fix a slow query before reading its profile.

    Say this

    "I'd group MPP performance into layout, execution, data movement, optimiser and write path, with one rule on top: a distributed query is as fast as its slowest instance. Layout is the biggest lever: partition by date for pruning, bucket on a high-cardinality key you join on, and sort for the main access path so the prefix index and zone maps skip data. For ticks I'd bucket by contract ID; bucketing by underlying would make NIFTY's tablet do several times the work on expiry day. Then joins: broadcast only small sides, colocate the big pairs, and watch for accidental broadcasts when a dimension grows. Statistics freshness decides whether the optimiser gets this right, so ANALYZE belongs in the load pipeline. And loads must be batched, or version counts and compaction hurt everyone. I haven't run StarRocks or Doris in production; the diagnosis loop is the same: plan, profile, skew, joins, memory, statistics, then the cheapest fix."
